# 完成第35课：依赖安全审计与供应链风险

本课为 AI 后端的 CI 增加了生产依赖安全审计步骤，使用 `npm audit --omit=dev --audit-level=high` 阻止高危与严重的生产依赖漏洞进入主分支。审计时发现用户级 npmmirror 源未实现 npm 安全审计接口，因此以一次性指定官方 registry 的方式完成核验，未修改全局镜像配置；当前生产依赖树未发现漏洞。

**思考题回答**：
1. **Q1（强制自动修复风险）**：`npm audit fix --force` 可能跨主版本升级直接或间接依赖，导致 API 行为变化、锁文件大范围漂移，甚至引入新的兼容性问题。暂不升级至少保留了当前已验证的安装树，而强制升级会同时改变许多变量。正确做法是先看漏洞依赖路径和发布说明，只升级确实能解决问题且可验证的最小范围。
2. **Q2（devDependency 风险判断）**：高危漏洞只存在于 devDependency 时，不应机械地让生产部署立即失败，因为它未必随生产镜像或运行时依赖一起发布。仍需看该工具是否会处理不可信输入、CI 是否使用开发依赖、漏洞代码是否可达，以及构建产物是否包含它。生产门槛优先使用 `--omit=dev`，但开发依赖告警应记录、定期复查并在构建链路存在风险时提升优先级。
3. **Q3（锁文件可复现性）**：`package.json` 表达允许的依赖范围，`package-lock.json` 固定本次验证过的准确版本和完整依赖树。只提交前者会让不同机器在相同范围内解析到不同版本，只提交后者又会使声明与安装树脱节。两者一起提交，`npm ci` 才能在本地、CI 和部署环境重现同一份依赖关系。

**Implications**：第36课将学习运行时配置校验与生产环境防御，在应用启动时验证密钥、数据库地址和部署配置，避免错误在收到用户请求后才暴露。
