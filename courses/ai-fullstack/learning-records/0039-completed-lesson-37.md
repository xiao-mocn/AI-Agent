# 完成第37课：配置变更管理与部署前检查

新增 `ai-backend/.env.example`，以无密钥方式记录配置键、格式与安全默认值；真实凭据仍由本地环境或部署平台提供。新增 `scripts/check-config.ts` 与 `npm run check:config`，可在启动 HTTP 服务、队列和 WebSocket 前复用既有 Schema 验证运行时配置。已运行配置检查、TypeScript 类型检查和测试套件，6 项测试全部通过。

**思考题回答**：

1. **Q1（示例清单）**：Schema 只告诉程序哪些输入合法，不能告诉部署人员这次发布新增了哪些配置，或应在何处填写。缺少 `.env.example` 时，代码与平台变量清单会逐渐漂移，部署者只能从失败日志反推缺失项。将示例文件与 Schema 同时提交，才能让变更在代码审查阶段被发现。
2. **Q2（独立检查）**：配置检查的目标是尽早验证外部输入，启动 HTTP 服务、队列或 WebSocket 会引入端口占用、后台任务和外部连接等副作用。副作用会让一次简单的发布前验证变慢且难以清理，也会模糊失败根因。独立脚本失败时不应留下运行中的服务或任务。
3. **Q3（必填规则变更）**：必须同步修改 Schema、`.env.example`、解析测试和部署平台的变量清单。若变量影响应用行为，还应更新发布检查脚本的说明和相关运行文档。生产环境是否显式提供该变量，应作为同一次变更的审查项而不是事后补救。

**Implications**：第38课将学习配置审计与密钥轮换，为配置变更保留可追溯证据，并在密钥泄露或人员变动时安全完成轮换。
