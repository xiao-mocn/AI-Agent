# 完成第 40 课：部署后烟雾测试与回滚判定

完成了 Render 公网服务的部署后烟雾测试。浏览器直接访问 `/health` 返回 `{ "status": "ok" }`，访问 `/ready` 返回 `{ "status": "ready" }`，证明 HTTP 进程可以响应，且新建的数据库已经能够完成就绪检查。此前 Render 免费数据库过期导致服务不可用；本次通过新建免费数据库并重新接入服务恢复了可用性。与此同时，本地完整 `npm test` 通过，共 2 个测试文件、9 条测试。

**思考题回答**：

1. **Q1（探针边界）**：`/health` 与 `/ready` 都通过，只说明进程可响应且关键数据库依赖可查询，不能证明所有经过鉴权、业务规则和外部服务的用户路径都正确。发布后仍可能存在 CORS、令牌、路由或特定业务数据问题。应在准备好合成账号和只读路径后，补充不产生业务副作用的最小业务检查。
2. **Q2（聊天接口风险）**：`POST /api/chat` 需要 JWT，并可能写入会话、调用 DeepSeek 和产生费用，因此不适合无副作用的烟雾测试。将它用于发布验证会把测试本身变成真实业务操作，也会让失败原因混入模型服务或配额等额外变量。烟雾测试应优先选择固定、快速且可判定的探针响应。
3. **Q3（回滚判定）**：偶发成功不能说明系统稳定，可能只是冷启动、短暂网络恢复或依赖抖动后的单次结果。可执行的回滚条件至少要包含观察窗口、检查对象、预期状态和触发动作，例如在观察窗口内 `/ready` 非 200 或响应不是 `ready` 时停止发布并恢复最近一次已验证版本。这样团队能基于证据行动，而不是在故障现场凭感觉判断。

**Implications**：第 41 课将学习发布证据与变更记录，把版本、配置摘要、烟雾测试结果和回滚决策组织成可追溯的发布记录。
