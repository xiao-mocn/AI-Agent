# 完成第 39 课：生产环境健康检查与可观测性边界

本课为已有的健康检查端点补充了两条集成测试：`/health` 精确返回 `200` 与 `{ status: 'ok' }`，`/ready` 在测试数据库可用时精确返回 `200` 与 `{ status: 'ready' }`。两条测试均不携带 JWT，确认探针端点位于 `/api/*` 鉴权范围外。定向测试和完整 `npm test` 均通过，共 9 条测试。

**思考题回答**：

1. **Q1（存活与就绪）**：数据库故障时让 `/health` 失败，会使部署平台把依赖故障误判成 Node.js 进程故障并反复重启实例。重启不能修复外部数据库不可用，反而可能加剧冷启动和恢复期间的请求中断。`/health` 只回答进程是否仍能响应，`/ready` 才决定实例是否应继续接收流量。
2. **Q2（DeepSeek 探测）**：将 DeepSeek API 放进每次 `/ready` 会让高频探针消耗配额，并把第三方短暂抖动放大为应用被摘流。AI 调用也可能耗时较长，降低探针的稳定性和可判定性。就绪检查应只覆盖当前处理业务请求不可缺少且能快速验证的依赖，本项目选择数据库查询。
3. **Q3（公开响应与受控日志）**：平台只需要固定状态码和最小状态文本，例如成功的 `ok`、`ready` 或失败的 `not ready`。数据库连接串、主机名、配置变量、文件路径、驱动错误与异常堆栈可能泄露系统结构，只能写入受控服务端日志。日志应结合请求 ID、时间和部署版本进行排查，而不是从公共探针接口暴露诊断细节。

**Implications**：第 40 课将学习部署后烟雾测试与回滚判定，把健康探针和最小业务请求组合为发布验收流程，并为失败发布建立明确的停止和回滚条件。
