# 完成第29课：前端接入会话列表与切换

`ai-frontend/src/ChatView.vue` 侧边栏从本地假 `sessions` 数组改成 `GET /api/sessions` 拉真实数据，配合新增的后端接口 `GET /api/sessions/:id/messages`（复用第27课的 `getHistory`，过滤掉 `system` 角色消息）实现切换会话时按需拉取历史、用 `messagesCache` 本地缓存；双击标题行内编辑并调用 `PATCH /api/sessions/:id` 重命名，采用乐观更新、失败自动回滚标题；悬浮显示删除按钮，`DELETE /api/sessions/:id` 成功后处理"删的正好是当前激活会话"的边界情况（切到列表第一个，列表空了就起一个新会话 id）。

核对实现时顺带发现一处与本课无关的遗留 bug 并已修复：`ai-backend/src/business/schemas.ts` 里 `ChatSchema.sessionId` 从第20课起就一直是 `z.number().int().positive()`，但第27/28课已经把会话 id 改成 `crypto.randomUUID()` 字符串，导致所有 `POST /api/chat` 请求都会被 400 拒绝。已改成 `z.string().uuid()`，`ai-backend`/`ai-frontend` 两边 `tsc`/`vue-tsc --noEmit` 均已重新跑过确认无报错。

**思考题回答**：
1. **Q1（跨设备缓存过期）**：`messagesCache` 是"缓存过就不再请求"的策略，如果另一台设备给同一个会话发了新消息，回到这个标签页切换过去看到的还是旧快照，容易被误以为"消息没同步/丢了"。解决思路有几种取舍：一是给缓存加 TTL，超时后重新拉取，实现简单但过期前仍有窗口不一致；二是干脆不缓存、每次切换都强制请求，牺牲一点延迟换取始终最新；三是接入 WebSocket（第25课已有基础）做跨设备推送，体验最好但实现复杂度最高；四是折中的 stale-while-revalidate——先用缓存立刻显示，同时后台悄悄发一次请求有更新就替换，用户不用等但仍可能有一瞬间的旧内容闪烁。
2. **Q2（404 vs 空数组）**：现在统一返回 `200 + { messages: [] }`，前端 `switchSession` 里只需要一行 `res.ok ? messages : []`，完全不用区分"这个会话真的没消息"和"会话不存在/不属于我"，分支逻辑更简单。代价是丢掉了"会话确实不存在"这个语义——如果以后想加"提示用户这个会话已被删除"之类的功能，就没法从这个接口直接判断，需要额外查一次 `sessions` 表。
3. **Q3（删除是否适合乐观更新）**：不太合适，至少不能照搬重命名的做法。重命名失败回滚的代价很小，标题"闪一下"变回去不会丢数据；但删除失败回滚意味着"会话短暂消失又复活"，如果用户在这个窗口期已经基于"删除成功"做了后续操作（比如认为清空了就去发新消息），复活这个会话会造成困惑甚至操作冲突。更本质的是删除在 UI 语义上是不可逆的重操作，而乐观更新的前提是"失败代价可控、能悄无声息地纠正"，删除并不满足这一点，所以更稳妥的做法是保持"发请求→等响应→改 UI"，最多加一个删除中的 loading 态。

**Implications**：第30课将学习给后端 API 写自动化测试（Vitest + Supertest）——这几周攒下的接口越来越多，光靠手动点一遍前端已经很难覆盖所有分支（比如"删别人的会话该 404"这种权限边界），是时候补一层自动化测试网了。
