# 完成第 42 课：数据持久化策略与恢复演练

完成了隔离的 SQLite 最小恢复演练，并将证据记录在 [恢复演练记录](../../../docs/recovery/2026-07-26-sqlite-recovery-drill.md)。演练只在系统临时目录创建虚构记录 `id=1`、`label=recovery-drill`，随后经过备份副本和恢复副本验证；恢复副本的查询结果与预期一致。整个过程没有读取、复制、修改或删除项目的 `ai-backend/chat.db`，也没有连接或修改 Render 数据库、线上服务和部署配置，因此它证明的是本地 SQLite 最小恢复链路，而不是线上托管数据库的恢复能力。

**思考题回答**：

1. **Q1（恢复验证）**：看到 SQLite 备份文件存在，只能证明某次复制动作产生了文件，不能证明该文件没有损坏、包含预期数据，或能被当前应用打开。有效的恢复证据应当把备份放入独立恢复副本，用只读连接打开并查询预先约定的虚构记录。这样才能验证文件可读、数据库结构可用且关键数据确实可取回。本次演练以 `id=1` 和 `label=recovery-drill` 作为确定性断言，避免把“文件存在”误当成“可以恢复”。
2. **Q2（RPO 与备份频率）**：若最多允许丢失 1 小时数据，备份间隔不能大于 1 小时，否则一次故障可能造成超过目标窗口的数据损失。还要把备份完成时间、失败结果和备份内容校验纳入记录，确保计划中的频率在实际环境中真的执行。恢复验证也应定期从某个备份副本执行，而不能只验证最新文件的存在。实际频率还需结合写入量、备份耗时、存储成本和可接受的恢复时间共同确定。
3. **Q3（托管数据库边界）**：本地 SQLite 的单文件副本流程无法说明 Render 托管 PostgreSQL 的快照、保留期、导出能力和恢复权限是否可用。两种数据库的存储位置、写入一致性机制、平台责任和恢复入口都不同，尤其不能假设“托管”就自动满足持久化和保留要求。对线上数据库必须根据 Render 实际套餐和文档确认备份能力，并在隔离环境中按它的真实恢复流程演练。当前演练仅为建立恢复证据的最小方法，不替代线上灾难恢复验收。

**Implications**：第 43 课将学习备份自动化与保留策略，把备份频率、命名、保留期、失败可见性和恢复验证组织成可重复执行的日常流程。
