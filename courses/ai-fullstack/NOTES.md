# 教学笔记

## 用户偏好

- 用简体中文交流和教学
- 前端（Vue 3 + React）双栈熟练，TypeScript 有生产项目经验
- 每天 1-2 小时，倾向于每次完成有成就感的小目标
- 目标驱动型：知道"为什么"之后再学"怎么做"更有动力
- 课程规格确认后，默认直接生成并打开下一课；除非用户明确要求，否则不重复询问执行方式。

## 后端教学基线（长期有效）

- 用户的后端基础为零；即使已成功运行过示例，也不能假设理解了 Java、Spring Boot、HTTP、Maven、测试或服务端分层。
- 讲解后端代码时，先说明它解决的实际问题，再解释“为什么需要这样设计”，最后给出操作步骤；不要只提供可复制的代码。
- 第一次出现的语法、注解、依赖、目录、命令和术语，必须用通俗中文解释其含义、所在位置、运行时作用及不这样做会怎样；必要时与用户熟悉的 TypeScript/前端概念类比。
- 每个步骤都要写清楚：新建或修改哪个文件、每段关键代码的职责、执行后预期看到什么，以及如何用测试或 HTTP 请求验证。
- 控制单节引入的新概念数量。代码应从最小可运行版本逐步演进，并明确区分“当前必须掌握”和“暂时知道即可”。
- 课程结束时用简短的回顾和变式练习，帮助用户复述数据流、解释设计选择，而不是仅确认代码能运行。

## eao-api 后端上岗桥接阶段

- 两周桥接阶段的完成标准是在同事或 AI 指导下完成低风险后端修改，不把“独立开发复杂模块”作为近期要求。
- 每条新链路优先从用户熟悉的 `eao-front` API 调用开始，再沿 URL 和 HTTP 方法定位 `eao-api` 的 Controller。
- 第一周固定使用品牌管理链路，反复练习 `Controller → VO → Service → ServiceImpl → Convert → DO → Mapper/XML`，避免频繁切换业务造成额外负担。
- 真实项目负责训练代码导航，`java-backend` 负责可运行的仿真实践；桥接阶段不直接修改 `eao-api` 和 `eao-front`。
- 用户第一次遇到公司 Starter、权限、多租户、多数据源、审计日志或中间件封装时，只解释它在当前链路中的输入、输出和职责，不立即追踪内部实现。
- 卡住时按“目录提示 → 类名提示 → 方法提示 → 代码解释”逐层给出帮助，避免一开始提供完整答案。
- 每节课先做无答案定位和职责判断，再进行动手练习、Git diff 自查和测试或 HTTP 验证。
- 每节课在 24～72 小时后安排一次短复现；无法完成前一课的脱稿定位时，优先补练，不继续增加框架概念。
- 课程中的简化实现必须显式列出与 `eao-api` 真实写法的差异，避免把教学简化误认为公司生产规范。
- 第 53～62 课组成两周桥接主线；第 52 课保留为选修，不删除、不覆盖。

## 节奏建议

- 课程保持短小精悍，每节课给一个明确的"胜利点"
- 解释 Java 后端概念时优先用 TypeScript/Vue 类比降低理解成本，但练习和代码阅读必须回到 Java 与 Spring Boot
- 避免先讲大量理论，尽快让用户跑起来看到效果

## 独立构建能力

- 用户能跟随课程完成实现，但当前不能脱离步骤独立从零写出同类功能；后续不能再把“跟做成功”当作完成标准。
- 每节课先要求用户在不看代码的情况下写出接口、文件职责、数据流或伪代码；随后只提供分层提示，而不是直接给出完整实现。
- 每节课结束后安排一次变式练习，并在 24-72 小时后安排一次脱稿复现或需求变化练习；只有能解释设计选择、完成验收并处理一个变化，才进入下一节。
- 在第 2、4、8 周设置综合脱稿检查。检查未通过时回补对应能力，不继续增加新框架或 AI 概念。
