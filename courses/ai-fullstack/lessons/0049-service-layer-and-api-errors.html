第四十九课：Service 层与统一错误响应

预计 90–120 分钟 · 基于第 48 课已验证的 Spring Boot 项目

目前的 VersionController 既接收 HTTP 请求，又决定业务结果。代码很少时看似没问题；一旦要读取配置、判断输入、处理失败，Controller 会迅速变成难测、难改的“大杂烩”。本课把“业务决定”和“HTTP 翻译”分开。

本课胜利点

  • 能说清 Controller、Service、全局异常处理器各自只负责什么。
  • 把 /version 的业务结果移入 VersionService，并通过构造方法注入使用它。
  • 新增 GET /versions/{releaseLabel}：找不到时返回稳定的 404 JSON，而不是随机的错误页面。
  • 在 @WebMvcTest 中用 @MockitoBean 替换 Service，分别锁定成功与失败契约。

0. 先记住：分层不是为了多建文件

Controller：HTTP 翻译员

接收路径、查询参数、请求体；调用业务；把结果作为 HTTP 响应返回。它不应保存“找不到时怎么办”这类业务决定。

Service：业务决定者

处理规则、组合配置或数据，并在无法完成业务时抛出有业务含义的异常。以后接数据库或 AI 时，复杂性主要放在这里。

Exception Handler：错误翻译员

集中把 Java 异常变成统一 JSON 与正确 HTTP 状态码，避免每个 Controller 手写重复的错误响应。

Test：外部契约守卫

测试客户端真正依赖的 URL、状态码和 JSON 字段。内部类怎么拆可以变化，契约不能悄悄变化。

本课必须掌握 构造方法注入、@Service、404、@RestControllerAdvice。
暂时知道即可 Repository、事务、RFC 9457 的完整错误规范、依赖注入容器的内部实现。

前端类比：Controller 像 Vue 页面事件处理器，Service 像可复用的业务 composable / SDK 层，异常处理器像统一的 HTTP 拦截器错误映射。相同点是职责分开；不同点是 Spring 负责创建并注入这些 Java 对象。

2. 第一步：创建 Service，让 Spring 管理它

1

新建 VersionService.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/VersionService.java

package com.example.ai.java_backend.version;

import com.example.ai.java_backend.config.AppProperties;
import org.springframework.stereotype.Service;

@Service
public class VersionService {
  private final AppProperties appProperties;

  public VersionService(AppProperties appProperties) {
    this.appProperties = appProperties;
  }

  public VersionResponse currentVersion() {
    return new VersionResponse("1.0.0");
  }

  public VersionResponse findForReleaseLabel(String releaseLabel) {
    if (!appProperties.releaseLabel().equals(releaseLabel)) {
      throw new ReleaseNotFoundException(releaseLabel);
    }
    return currentVersion();
  }
}
@Service 是什么？它告诉 Spring：这是业务服务，启动时请创建一个对象（bean）并管理它。Spring 官方将 @Service 视为 @Component 的专用角色；不写它，Spring 默认不会有可注入的 VersionService。
构造方法为什么只有一个参数？参数 AppProperties 表示“这个 Service 依赖配置”。Spring 已在第 48 课创建该配置对象，所以能自动传入。字段设为 final 意味着构造后不再换依赖，便于理解和测试。
2

创建一个有业务名称的异常

路径：java-backend/src/main/java/com/example/ai/java_backend/version/ReleaseNotFoundException.java

package com.example.ai.java_backend.version;

public class ReleaseNotFoundException extends RuntimeException {
  public ReleaseNotFoundException(String releaseLabel) {
    super("找不到发布标签：" + releaseLabel);
  }
}
为什么不直接返回 404？Service 不应该知道 HTTP 的细节；它只表达业务事实：“这个发布标签不存在”。RuntimeException 表示这个方法不在本地恢复该错误，而是交给后面的统一异常处理器翻译为 HTTP。

3. 第二步：让 Controller 只处理 HTTP

3

替换 VersionController.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/VersionController.java

package com.example.ai.java_backend.version;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class VersionController {
  private final VersionService versionService;

  public VersionController(VersionService versionService) {
    this.versionService = versionService;
  }

  @GetMapping("/version")
  VersionResponse version() {
    return versionService.currentVersion();
  }

  @GetMapping("/versions/{releaseLabel}")
  VersionResponse findVersion(@PathVariable String releaseLabel) {
    return versionService.findForReleaseLabel(releaseLabel);
  }
}
新代码作用不这样做会怎样
private final VersionService保存 Controller 需要调用的业务服务。Controller 只能自己实现业务规则，未来每个接口都会重复判断。
构造方法让 Spring 在创建 Controller 时注入 Service。这叫构造方法注入。不注入就没有 Service 可调用；也不应在 Controller 中手写 new VersionService(...)，那会绕过 Spring 的依赖管理。
@PathVariable把 URL 中的 {releaseLabel} 读取为 Java 参数。方法不知道用户请求了哪个标签，无法交给 Service 判断。

4. 第三步：把异常统一翻译成 JSON

4

创建错误响应 record

路径：java-backend/src/main/java/com/example/ai/java_backend/common/ApiError.java

package com.example.ai.java_backend.common;

public record ApiError(String code, String message) { }

客户端不应依赖 Java 异常类名或框架默认错误页面。code 是稳定、便于前端判断的机器标识；message 是给人阅读的说明。

5

创建全局异常处理器

路径：java-backend/src/main/java/com/example/ai/java_backend/common/ApiExceptionHandler.java

package com.example.ai.java_backend.common;

import com.example.ai.java_backend.version.ReleaseNotFoundException;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class ApiExceptionHandler {
  @ExceptionHandler(ReleaseNotFoundException.class)
  ResponseEntity<ApiError> handleReleaseNotFound(
      ReleaseNotFoundException exception) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
        .body(new ApiError("RELEASE_NOT_FOUND", exception.getMessage()));
  }
}
@RestControllerAdvice 是什么？它把类声明为面向 REST Controller 的全局建议器；Spring 会在 Controller 抛异常后寻找匹配的 @ExceptionHandler。它等价于“@ControllerAdvice + 自动写 JSON 响应体”。
ResponseEntity 为什么出现？普通返回对象只描述 JSON body；ResponseEntity 同时描述 HTTP 状态、响应头和 body。这里用它明确返回 404，而不是默认的 500。

6. 第五步：测试 Controller，不让真实 Service 混进来

7

更新 VersionControllerTest.java

路径：java-backend/src/test/java/com/example/ai/java_backend/version/VersionControllerTest.java

package com.example.ai.java_backend.version;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;
import org.springframework.http.MediaType;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

import static org.mockito.BDDMockito.given;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@WebMvcTest(VersionController.class)
class VersionControllerTest {
  @Autowired
  MockMvc mvc;

  @MockitoBean
  VersionService versionService;

  @Test
  void versionMatchesContract() throws Exception {
    given(versionService.currentVersion()).willReturn(new VersionResponse("1.0.0"));

    mvc.perform(get("/version"))
        .andExpect(status().isOk())
        .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
        .andExpect(jsonPath("$.version").value("1.0.0"));
  }

  @Test
  void missingReleaseReturnsStable404Json() throws Exception {
    given(versionService.findForReleaseLabel("missing"))
        .willThrow(new ReleaseNotFoundException("missing"));

    mvc.perform(get("/versions/missing"))
        .andExpect(status().isNotFound())
        .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
        .andExpect(jsonPath("$.code").value("RELEASE_NOT_FOUND"))
        .andExpect(jsonPath("$.message").value("找不到发布标签：missing"));
  }
}
@MockitoBean 是什么？它用 Mockito 生成的假 Service 覆盖测试上下文中的真实 Service。这样这个测试只验证 Controller 的 URL、HTTP 与 JSON 契约，不需要依赖真实配置或业务内部实现。

7. 排错与总结

现象优先检查原因
应用提示没有 VersionService bean@Service、包路径、启动类根包Spring 只会扫描根包及子包中被识别为组件的类。
@WebMvcTest 启动失败测试中是否添加 @MockitoBean VersionService测试切片只加载 Web 层，Controller 的依赖需要用 mock 提供。
找不到标签时返回 500ApiExceptionHandler 的 @RestControllerAdvice 与异常类型没有匹配处理器时，异常会落到框架默认错误处理。
路径访问 404 但没有 JSON请求是否为 /versions/missing；路径变量名称是否一致/version 和 /versions/{releaseLabel} 是两个不同路由。

完成标准

  • /version 的响应保持 {"version":"1.0.0"}。
  • /versions/local 返回 200 与同一 JSON。
  • /versions/missing 返回 404、RELEASE_NOT_FOUND 和可读 message。
  • .\mvnw.cmd test 通过，且 404 契约被测试覆盖。
  • 能不看代码讲出 Controller、Service、异常处理器的职责边界。
