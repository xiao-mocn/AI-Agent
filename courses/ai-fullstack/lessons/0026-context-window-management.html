第二十六课：多轮对话的上下文管理

目标时长 1.5 小时 · 难度 ⭐⭐⭐ · 后端 · AI 集成

本节课你会学到：
  • 为什么"把完整历史都发给 AI"这个从第四课就在用的做法迟早会出问题
  • token 是什么、怎么在不引入重型依赖的前提下粗略估算它
  • 常见的上下文裁剪策略：滑动窗口 vs 按 token 预算裁剪
  • 为什么裁剪要丢"最旧的"而不是"最新的"，以及 system prompt 要特殊对待
  • 裁剪只影响"发给 AI 的这次请求"，不影响数据库里保存的完整历史

一、现在的实现藏着什么问题

回到第四课写的 src/business/chat.ts，核心逻辑是这样的：

const history = await getHistory(sessionId) as ChatMessage[]

const stream = await client.chat.completions.create({
  model: 'deepseek-chat',
  messages: history, // 这个 session 从第一条消息到现在的全部历史
  stream: true,
})

这段代码能跑，是因为学习阶段的对话通常只有几轮。但只要这个 session 活得足够久——比如用户把它当日常助手一直聊下去——history 会无限增长，每次请求都要把从第一句话到现在的所有内容重新发给 AI。这会带来三个实际问题：

  • 超出模型的上下文窗口：每个模型都有 token 上限（比如几万到十几万不等），历史超过这个数直接报错，对话彻底"卡死"
  • 成本线性增长：大部分 AI API 按 token 计费，输入 token 里包含了整个历史，同样一句"你好"，聊到第 200 轮的成本可能是第 1 轮的几十倍
  • 延迟变大：输入越长，模型处理和首字返回的时间通常也越长，用户体验从"秒回"变成"转圈"

二、token 是什么，怎么粗略估算

AI 模型不是按"字"或"字符"计费和计算上下文的，而是按 token——一种介于字符和单词之间的切分单位。英文里一个 token 大约是 3-4 个字符，中文里通常 1-2 个汉字对应一个 token（具体切法取决于模型的分词器，不同模型不完全一样）。

真实项目里，如果要精确计算 token 数，可以装 gpt-tokenizer 或 tiktoken 这类库，调用模型对应的分词器直接算出精确值。这节课为了不引入额外依赖、把注意力放在"裁剪策略"这个核心机制上，先用一个足够用的粗略估算：按字符数除以一个经验系数来近似。这个近似值会有误差，但对于"要不要开始裁剪"这种阈值判断已经够用。

三、裁剪策略：滑动窗口 vs 按 token 预算

策略做法问题
滑动窗口（按轮数）只保留最近 N 轮对话N 轮里如果消息特别长（比如粘贴了一大段代码），照样会超预算；N 轮很短又会浪费还没超预算的额度
按 token 预算从最新的消息往前累加估算的 token 数，累加到预算上限就停止，更早的消息全部丢弃需要自己估算 token，逻辑比数轮数复杂一点

这节课选按 token 预算裁剪，因为它更贴近"到底会不会超模型上限、会花多少钱"这个真实约束，而不是拍脑袋定一个轮数。

裁剪方向千万不能搞反：必须丢弃最旧的消息，保留最新的。AI 需要记住的是"我们刚才聊到哪了"，而不是"这个对话是怎么开始的"。如果不小心写反（比如从数组开头往后截取），效果是 AI 只记得话题最开始的几句寒暄，完全忘了用户刚刚说的话，看起来像是"完全没在听"。

四、动手实践

1新增 src/business/contextWindow.ts：token 估算 + 按预算裁剪 
type ChatMessage = {
  role: 'user' | 'assistant' | 'system'
  content: string
}

// 粗略估算：中文场景下 1 个字符约等于 0.7~1 个 token，这里取保守系数 1.5 字符/token
export function estimateTokens(text: string): number {
  return Math.ceil(text.length / 1.5)
}

// 按 token 预算裁剪历史：永远保留 system prompt，从最新消息往前累加，超预算就停止
export function trimHistory(messages: ChatMessage[], maxTokens: number): ChatMessage[] {
  const systemMsg = messages[0]?.role === 'system' ? messages[0] : null
  const rest = systemMsg ? messages.slice(1) : messages

  let budget = maxTokens - (systemMsg ? estimateTokens(systemMsg.content) : 0)
  const kept: ChatMessage[] = []

  // 从最新的往前挑，直到预算用完
  for (let i = rest.length - 1; i >= 0; i--) {
    const cost = estimateTokens(rest[i].content)
    if (cost > budget) break
    kept.unshift(rest[i])
    budget -= cost
  }

  return systemMsg ? [systemMsg, ...kept] : kept
}
unshift 保证挑出来的消息按原本的时间顺序排列（虽然是倒着遍历挑选的，但插回去的时候插在数组最前面，最终顺序不变）。system 消息永远单独处理、永远保留在最前面——它承载着"AI 该怎么表现"这个贯穿全程的设定，不该被当成普通历史消息一样被挤掉。
2在 src/business/chat.ts 里接入裁剪，只影响发给 AI 的这次请求 
import { trimHistory } from './contextWindow'

const MAX_CONTEXT_TOKENS = 4000

// 读取完整历史（数据库里的记录不受影响，用户刷新页面仍能看到全部消息）
const history = await getHistory(sessionId) as ChatMessage[]

// 只有发给 AI 的这一份做裁剪
const trimmedHistory = trimHistory(history, MAX_CONTEXT_TOKENS)

const stream = await client.chat.completions.create({
  model: 'deepseek-chat',
  messages: trimmedHistory,
  stream: true,
})
注意这里裁剪的是发给 AI 的副本，不是数据库里的 history 本身。写入数据库的 insertMsg 调用完全不受影响，用户的完整对话记录永远都在——AI 只是"记性变短了"，不代表用户的聊天记录也被删了。

五、本课总结

  • 把完整历史无脑塞进每次请求，迟早会撞上模型上限、成本失控、延迟变差三个问题
  • token 是模型计费和计算上下文的真实单位，字符数只是一个够用的粗略估算
  • 裁剪要按 token 预算而不是按轮数，更贴近真实约束；方向上必须丢"最旧"保"最新"
  • system prompt 承载着 AI 的行为设定，永远单独保留在裁剪结果最前面
  • 裁剪只影响这一次请求发给 AI 的内容，数据库里的完整历史不受任何影响
