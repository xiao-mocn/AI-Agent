第四十八课：运行时配置与就绪检查

预计 90–120 分钟 · Java 21 · Spring Boot 4.1.1 · 从第 47 课的 /health 出发

上一课让你的服务能回答 GET /health。这一课要解决一个更真实的问题：即使程序进程启动了，它是否拿到了正确配置，并且真的应该接收用户请求？

本课胜利点

  • 能说清 application.properties 是什么，以及它为什么不应该只被当成“随便放字符串的文件”。
  • 能用一个 Java record 接收配置，并理解每个注解的职责。
  • 能证明：缺少关键配置时，应用会在启动时明确失败，而不是带着空值继续提供服务。
  • 能区分“进程是否该重启”（liveness）和“实例是否该接流量”（readiness）。

0. 先看问题：启动成功，不代表服务正确

想象你要发布一个后端服务。程序确实启动了，端口也在监听；但本次发布的标识 releaseLabel 没有配置，代码拿到的是空字符串。之后某个接口把它写入日志或返回给前端，排查人员无法判断请求来自哪个版本。

这类问题最好的处理时机不是“用户访问接口之后”，而是启动应用时。如果服务缺少安全提供功能所必需的信息，就应该拒绝启动；部署系统会立即显示失败，开发者也能从启动日志定位原因。

本课的核心判断：“尽早失败”不是故意让程序难用，而是把配置错误挡在接收真实请求之前。

1. 先认识本课的四个角色

application.properties

应用的配置清单。这里写“键=值”，例如 app.release-label=local。它不是 Java 代码，而是 Spring Boot 启动时会读取的外部信息。

pom.xml

Maven 的依赖清单。它告诉 Maven：这个项目要使用哪些库。就像前端项目的 package.json，但格式是 XML。

启动类

JavaBackendApplication 是 Spring Boot 的入口。它的 main 方法启动应用；它所在的根包也影响 Spring 默认扫描哪些类。

AppProperties

即将创建的 Java 类型。它把散落在配置文件里的文字，收拢为有字段名、有校验规则的一个对象。

本课必须掌握 配置键、配置绑定、启动时校验、readiness 的含义。
暂时知道即可 Bean Validation 的完整规范、Kubernetes 部署细节、健康组高级定制。

和前端的类比：前端会从环境变量或配置文件读取 API 地址；后端也需要读取配置。区别是后端通常长期运行、会被部署到多套环境，因此更需要在启动边界检查关键配置是否存在。

3. 第一步：告诉 Maven 我们需要哪些能力

1

修改 java-backend/pom.xml

目的：引入生产健康端点和配置校验能力。请保留你已有的 Web MVC 和测试依赖。

在 <dependencies> 中增加下面两段：

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
为什么这样做？一个 starter 是 Spring Boot 打包好的一组常用依赖。Actuator starter 提供生产运行状态端点；Validation starter 提供 @NotBlank 这类校验注解在运行时所需的实现。Maven 会在构建时下载它们，并将它们放到应用的运行 classpath。
不加会怎样？没有 Actuator，就没有 /actuator/health/readiness；没有 Validation，配置字段上的“不能为空”规则无法按本课预期运行。

4. 第二步：把配置从文本变成 Java 类型

2

创建 config/AppProperties.java

新建完整路径：java-backend/src/main/java/com/example/ai/java_backend/config/AppProperties.java

package com.example.ai.java_backend.config;

import jakarta.validation.constraints.NotBlank;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "app")
public record AppProperties(@NotBlank String releaseLabel) { }
代码它是什么为什么需要 / 不写会怎样
package ...config;类所在的包名，相当于 Java 的目录归属和命名空间。它放在启动类根包 com.example.ai.java_backend 的子包中，后面扫描时才能自然被找到。
import ...引入其他库里定义的类型，类似 TypeScript 的 import。不引入就不能简写这些注解的类名，编译器会找不到类型。
recordJava 16 起的简洁数据类型写法。这里它代表“只有一个发布标签的数据”。Java 会自动提供构造方法和 releaseLabel() 读取方法。也可用普通 class，但本课没有额外行为时 record 更直接。
prefix = "app"配置前缀。它告诉 Spring 去寻找 app. 开头的配置。没有前缀，Spring 不知道哪个配置属于这个类型。
String releaseLabelJava 字段，保存配置值。Spring 会把 kebab-case 的 app.release-label 对应到 camelCase 的 releaseLabel。
@Validated要求 Spring 在绑定配置后执行校验。不写时，下面的 @NotBlank 不会按这里期待的方式阻止错误启动。
@NotBlank校验规则：值不能是 null、空字符串或全空格。不写时，空发布标签能悄悄进入程序，错误会被推迟到更难排查的位置。
3

让启动类发现这个配置类型

修改：java-backend/src/main/java/com/example/ai/java_backend/JavaBackendApplication.java

用下面的完整内容替换启动类：

package com.example.ai.java_backend;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationPropertiesScan;

@SpringBootApplication
@ConfigurationPropertiesScan
public class JavaBackendApplication {

  public static void main(String[] args) {
    SpringApplication.run(JavaBackendApplication.class, args);
  }
}
为什么加 @ConfigurationPropertiesScan？你创建了 AppProperties，但 Spring 不会凭空使用它。这个注解表示“启动时扫描根包及子包，找出带 @ConfigurationProperties 的类型并绑定配置”。
为什么路径不能乱放？启动类在 com.example.ai.java_backend，所以 config 必须是它的子包。如果放到平级或无关包，默认扫描范围可能不包含它。这和你上一课修正启动类与 Controller 包路径的原因相同。
4

写入非敏感配置和探针配置

修改：java-backend/src/main/resources/application.properties

spring.application.name=java-backend

app.release-label=local
management.endpoint.health.probes.enabled=true
management.endpoint.health.probes.add-additional-paths=true
配置行本课中的作用
app.release-label=local为 AppProperties.releaseLabel 提供本地开发值。它是演示用的非敏感信息。
...probes.enabled=true启用 Actuator 的 liveness 与 readiness 健康组。
...add-additional-paths=true除了 Actuator 默认路径，也在主应用端口提供 /livez 和 /readyz。
安全边界：这里绝对不要写数据库密码、API Key、Token 或真实密钥。它们应来自受控环境变量或密钥系统；本课只使用 local 这种无敏感性的示例值。

5. 第三步：用“成功”和“预期失败”证明规则有效

5

先正常测试与启动

在 PowerShell 进入 java-backend 目录后，依次执行：

.\mvnw.cmd test
.\mvnw.cmd spring-boot:run

第一条命令运行已有测试；预期末尾出现 BUILD SUCCESS。第二条命令启动应用；看到类似 Started JavaBackendApplication 后，让它继续运行。

另开一个 PowerShell 窗口，验证上一课的原有接口仍然存在：

Invoke-RestMethod http://localhost:8080/health
为什么保留这一步？第 48 课加的是运行时能力，不能悄悄破坏第 47 课已经承诺的 {"status":"ok"} 健康契约。
6

再做一次受控失败

先在运行应用的窗口按 Ctrl + C 停止服务。然后运行：

.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=--app.release-label="

这个命令只对本次启动传入一个空的发布标签；它不会修改 application.properties。预期结果不是启动成功，而是启动失败。日志中应出现 app.release-label 或 releaseLabel 相关的绑定/校验错误。

这证明了什么？配置不是“读到空字符串也算正常”。关键配置缺失会在部署边界暴露，应用不会在不知道版本标识的情况下接收流量。

6. Actuator、/health 与 readiness 分别是什么？

它们都和“健康”有关，但负责回答的问题不同。不要把它们当成三个内容完全相同的 URL。

地址谁提供它在本课中回答什么
/health你在第 47 课写的 HealthController项目的最小 HTTP 契约仍然能返回 {"status":"ok"}。
/actuator/health/readinessSpring Boot ActuatorActuator 的 readiness 健康组认为当前实例是否可以接收流量。
/readyzActuator 的额外主端口路径给部署平台或反向代理更方便的 readiness 地址；它表达同一个就绪语义。
7

验证 readiness 地址

用正常配置重新运行 .\mvnw.cmd spring-boot:run。看到启动完成后，在另一个窗口执行：

Invoke-RestMethod http://localhost:8080/actuator/health/readiness
Invoke-RestMethod http://localhost:8080/readyz

两次结果都应该是 JSON，并包含 "status":"UP"。这里的 UP 表示“当前健康组认为这个实例可以服务”；它不承诺数据库、LLM 或每一种业务请求永远没有问题。

7. 为什么要区分 liveness 和 readiness？

状态它问的问题平台通常采取的动作
Liveness（存活）这个 Java 进程自身是否卡死或进入无法恢复的状态？如果不存活，平台可能重启这个实例。
Readiness（就绪）这个实例现在是否应该接收新的用户请求？如果未就绪，负载均衡器通常暂时不再把新请求分给它。
当前项目的选择：现在不把数据库和 LLM 请求加入 liveness 或 readiness。它们是共享外部依赖；如果数据库短暂故障就导致所有应用实例被重启，故障可能被放大。是否纳入 readiness，要等我们有明确的降级策略和流量策略之后再决定。

8. 常见错误：看到现象后先检查哪里？

看到的现象先检查修正方向
提示找不到 ConfigurationProperties 或 NotBlankpom.xml 是否添加了对应 starter；保存后是否重新执行 Maven 命令。补齐 Actuator、Validation 依赖，再执行 .\mvnw.cmd test 让 Maven 下载依赖。
应用启动了，但配置校验没有生效AppProperties 是否有 @Validated 和 @NotBlank；启动类是否有 @ConfigurationPropertiesScan。逐字检查注解和包名；不要把 config 放到 com.example.ai.java_backend 之外。
提示无法绑定 app.release-labelapplication.properties 中的键是否拼写为 app.release-label。配置键使用 kebab-case；Java 字段使用 releaseLabel，不要写成 release-label。
请求接口时提示无法连接，或启动说端口被占用运行窗口是否仍在启动，或 8080 是否被其他程序占用。确认日志出现 Started；必要时停止旧的 Spring Boot 进程后再启动。不要在未启动服务时期待 HTTP 命令成功。

9. 验收、复述与变式练习

完成标准

  • .\mvnw.cmd test 正常通过。
  • /health 仍然返回第 47 课约定的 {"status":"ok"}。
  • 正常配置下，/actuator/health/readiness 与 /readyz 都有 "status":"UP"。
  • 临时传入空的 app.release-label 时，应用明确启动失败。
  • 没有把任何真实密码、API Key、Token 或数据库凭据写进 application.properties、日志或提交记录。
