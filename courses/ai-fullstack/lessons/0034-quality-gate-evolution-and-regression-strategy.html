第三十四课：质量门槛的演进与回归测试策略

目标时长 1 小时 · 难度 ★★★ · 工程化 · 风险驱动测试

本节课你会学到：
  • 为什么覆盖率门槛应随测试能力演进，而不是一次设到理想数字
  • 如何把认证、资源归属和错误处理识别为高价值回归测试候选
  • 如何在修复问题时留下最小、稳定的回归用例
  • 如何避免脆弱测试和“为了覆盖率而测试”

一、门槛不是数字目标，而是风险承诺

第 33 课让 CI 阻止覆盖率跌破当前基线，但基线并不等于质量终点。真正值得提高门槛的信号是：团队已经为高风险行为补上了稳定测试，新的门槛能防止这些保护在未来悄悄消失。

变化优先动作门槛动作
发现越权、认证或数据泄漏风险先写 API 回归测试测试稳定后再提高 branches
新增正常业务流程覆盖成功路径和主要失败路径观察 statements / lines 基线
大规模重构先确保既有行为测试仍有意义不要为了通过而临时降低门槛
不要把门槛当绩效 KPI。 一个 90% 的项目仍可能漏掉“用户 B 删除用户 A 会话”这样的严重问题；一个 60% 的项目也可能已经覆盖了最危险的权限边界。数字用于发现变化，风险模型决定测试优先级。

二、什么值得成为回归测试

回归测试记录已经确认的重要行为：它可以来自线上故障、代码审查发现、边界条件或安全假设。它必须先在旧代码上失败，再在修复后通过；否则只能说明测试存在，不能证明它能防止同类问题复发。

  • 身份边界：缺少 token、无效 token、用户间资源隔离。
  • 资源状态：不存在的会话、删除后的查询、重复操作。
  • 外部失败：模型调用异常、数据库不可用、超时后的可预期响应。
  • 数据完整性：同一用户的历史记录不会串到另一用户。

三、动手实践

1从报告中选一个高风险缺口

运行 npm run test:coverage，从未覆盖行中优先选择影响身份、资源归属或失败恢复的分支。写下“如果这个分支错误，谁会受到影响、后果是什么”，再开始写测试。

npm run test:coverage
2先写能描述风险的 API 测试

测试名称写清用户视角和预期结果，而不是内部函数名。例如“未携带 token 时不能读取会话列表”。先运行它确认失败原因符合预期，再实现或修正业务代码。

it('未携带 token 时不能读取会话列表', async () => {
  const res = await request(server).get('/api/sessions')
  expect(res.status).toBe(401)
})
测试辅助函数继续只负责环境和重复操作；业务断言保留在测试文件中，才能看清每个回归风险对应的行为。
3确认测试价值而非只看数字

运行普通测试与覆盖率测试，确认新用例稳定、断言针对真实响应，并观察它是否覆盖预期的风险分支。只有在新基线多次稳定后，才考虑提高 vitest.config.ts 中的一个阈值。

npm test
npm run test:coverage
4把门槛调整写进变更理由

当你提高阈值时，在提交说明或 Pull Request 中写出：新增了哪个风险行为测试、当前基线是多少、为什么这条线足以保护本次改动。

不要用忽略文件、空断言或大量 mock 来抬高覆盖率。 这些做法会让 CI 通过，却让真正行为缺少保护，削弱质量门槛的可信度。

四、回归测试的稳定性检查

  1. 只观察对外可见的状态、响应和持久化结果，不断言偶然的内部实现细节。
  2. 每个测试创建自己的数据，并在结束后清理，避免执行顺序影响结果。
  3. 外部 LLM 等不可控依赖使用最小 mock，但权限、路由和数据库行为尽量通过真实应用调用验证。
  4. 失败时先判断是产品行为回归还是测试环境不稳定，不能靠重试掩盖问题。

五、本课总结

  • 覆盖率门槛应跟随稳定的风险测试逐步演进。
  • 高价值回归测试优先保护身份、资源、失败恢复和数据完整性。
  • 一次真实缺陷的最小复现，是最有价值的长期测试资产。
  • 测试的可读性和稳定性比表面百分比更重要。
