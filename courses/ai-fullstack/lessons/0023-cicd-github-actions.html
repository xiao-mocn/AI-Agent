第二十三课：CI/CD 自动化部署

目标时长 1.5 小时 · 难度 ⭐⭐⭐ · 后端 · 部署

本节课你会学到：
  • CI（持续集成）和 CD（持续部署）到底解决什么问题
  • GitHub Actions 的核心概念：workflow、job、step、trigger
  • 写一个 .github/workflows/ci.yml，每次 push 自动跑类型检查、验证 Docker 镜像能否构建成功
  • 为什么这节课选择让 CI 做"质量门禁"，把"部署"这件事交给 Render 自己的 Git 集成
  • 怎么在 GitHub Actions 里管理密钥（Secrets），不把它们写进仓库

一、CI/CD 解决的是什么问题

到现在为止，你的部署流程大概是：本地改完代码 → 手动 git push → 手动登录 Render/Railway 控制台确认部署成功 → 如果构建失败，自己再去看日志排查。这个流程有几个隐患：

  • 忘记验证就推送：改完代码直接 push，没在本地跑一遍类型检查，等平台构建失败了才发现问题
  • "我这能跑"再次出现：第二十二课解决了运行时环境不一致，但如果没人在 push 前确认 Docker 镜像真的能构建成功，一样会把坏的提交推上去
  • 依赖人的记忆力：多人协作时，"push 前记得跑测试"这种约定很容易被忘记，尤其是赶时间的时候

CI（Continuous Integration，持续集成）就是把"验证代码没问题"这件事从"人记得做"变成"每次 push 自动做"。GitHub Actions 是 GitHub 内置的自动化工具，仓库里有个 .github/workflows/*.yml 文件，GitHub 就会在指定的时机（比如每次 push）自动拉起一台干净的虚拟机，按你写的步骤跑一遍。

CD（Continuous Deployment，持续部署）是更进一步——验证通过后自动部署到生产环境。但这节课不会在 workflow 里手写"部署到 Render"的脚本，原因见第三节。

二、GitHub Actions 核心概念

概念说明
workflow一个 .yml 文件就是一个 workflow，定义"什么时候触发"和"触发后做什么"
trigger触发条件，比如 push（有人推送代码）、pull_request（有人开 PR）
job一个 workflow 可以有多个 job，默认并行跑，每个 job 在一台独立的干净虚拟机上执行
stepjob 内部按顺序执行的具体命令，比如"装依赖"、"跑类型检查"
action别人（或 GitHub 官方）写好的可复用 step，比如 actions/checkout 负责把你的仓库代码拉下来

三、写 CI workflow

1新建 .github/workflows/ci.yml 
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-check:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ai-backend

    steps:
      - name: 拉取代码
        uses: actions/checkout@v4

      - name: 安装 Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: 'npm'
          cache-dependency-path: ai-backend/package-lock.json

      - name: 安装依赖
        run: npm ci

      - name: 类型检查
        run: npx tsc --noEmit

      - name: 验证 Docker 镜像能否构建
        run: docker build -t ai-backend:ci .
为什么固定 node-version: '24'：如果不写死版本，setup-node 会用 runner 镜像自带的默认版本，可能和你本地、和 Dockerfile 里的 node:24-slim 都对不上——这正是第二十二课想解决的"环境一致性"问题，CI 里也要保持一致。
2关于"跑测试"这一步

当前 package.json 里的 test 脚本还是占位符（echo "Error: no test specified"），项目还没有真正的测试用例，所以这份 workflow 暂时没加 npm test 这一步——加了反而会让每次 CI 必然失败。等以后写了单元测试（比如用 vitest），只需要在 workflow 里补一步 run: npm test 即可，不需要改动其他部分。

3为什么不在 workflow 里写"部署到 Render"的脚本

Render（以及大多数 PaaS）支持直接在控制台把服务和 GitHub 仓库绑定，之后每次 push 到指定分支，Render 会自己拉代码、构建、部署，不需要你在 GitHub Actions 里手写调用 Render API 的部署脚本。

这样分工更清晰：GitHub Actions 负责"质量门禁"（类型检查、镜像能不能构建成功）——查得不对就直接在 PR 页面标红，挡在合并之前；Render 负责"部署"——它更懂自己的部署环境，出问题时的日志和回滚功能也更完善。避免了自己维护一套本可以交给平台做得更好的部署脚本。
4用 GitHub Secrets 管理密钥（如果以后 CI 需要真实密钥）

如果之后 CI 里需要用到真实密钥（比如跑集成测试要连测试数据库），绝对不要把密钥写进 .yml 文件——仓库里的任何内容都是明文可见的。正确做法是在 GitHub 仓库 Settings → Secrets and variables → Actions 里添加密钥，workflow 里通过 ${{ secrets.密钥名 }} 引用：

env:
  DATABASE_URL: ${{ secrets.DATABASE_URL }}

四、本课总结

  • CI 把"验证代码没问题"从"人记得做"变成"每次 push 自动做"，避免带着明显问题的提交流入生产环境
  • GitHub Actions 的核心是 workflow → job → step 这层结构，触发条件（on）决定什么时候跑
  • CI 里固定 Node 版本，和 Dockerfile、本地开发环境保持一致，避免"我这能跑"再次出现
  • 没有真实测试时不要硬加 npm test 步骤，先做类型检查和镜像构建验证，测试写好了再补
  • "验证"交给 GitHub Actions，"部署"交给 Render 自己的 Git 集成，分工清晰、各自发挥所长
  • 密钥永远放在 GitHub Secrets 里，不写进 .yml 文件
