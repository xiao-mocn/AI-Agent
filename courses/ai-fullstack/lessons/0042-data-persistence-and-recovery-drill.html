第四十二课：数据持久化策略与恢复演练

目标时长 1 小时 · 难度 ★★★ · 数据可靠性 · 恢复能力

本课你会学到：
  • 区分 SQLite 与托管 PostgreSQL 的持久化和恢复责任。
  • 用 RPO、RTO 把“要备份”转化为可讨论的目标。
  • 在独立临时路径验证 SQLite 备份副本可以恢复虚构数据。
  • 记录恢复演练的边界、结果和限制，而不触碰真实数据。

一、能连接数据库，不等于能恢复数据

第 40 节的 /ready 证明服务当前能查询数据库，但它没有回答另一个问题：误删、实例到期或文件损坏之后，数据能否恢复到可接受的状态。恢复能力需要独立证据，至少包括备份副本、一次恢复过程和对恢复结果的验证。

本次免费数据库到期提醒了一个重要边界：服务配置恢复后，空的新库可以让应用重新启动，却不自动带回旧数据。可用性与数据耐久性是两条不同的链路，必须分别验证。

主阅读资源：SQLite 官方文档。SQLite 的单文件特性让本地恢复演练很直观，但不替代托管数据库的备份与恢复策略。

二、存储方案决定恢复责任

维度本地 SQLite托管 PostgreSQL
数据位置应用可访问的单个数据库文件。由托管服务维护的独立数据库实例。
备份责任应用团队负责创建副本、校验和保留。先确认平台提供的备份、保留期和恢复流程。
恢复验证恢复到另一路径并查询虚构或测试数据。在隔离环境恢复，再验证架构和受控测试数据。
常见误区只复制文件却从未打开恢复副本。假设“托管”天然等于永久保存。
不要把正在运行的 SQLite 文件直接当作唯一备份。真实环境还要考虑写入时机、WAL 文件、备份一致性和保留周期。本课只验证一个最小恢复链路，且不读取项目现有的 chat.db。

三、RPO 与 RTO：先决定能丢多少、能等多久

RPO（Recovery Point Objective）是可接受的数据丢失窗口：如果每 24 小时备份一次，最坏情况下可能丢失一天的数据。RTO（Recovery Time Objective）是可接受的恢复时间：从发现故障到服务与数据恢复，最多允许多久。

它们不是大公司的专属术语。对于当前学习项目，可以先写出一个诚实答案：免费数据库到期后没有已验证的旧数据恢复路径，因此 RPO 不可接受、RTO 不确定。下一步的目标不是伪造数字，而是通过备份和演练让这两个目标逐渐变得可测量。

四、动手实践

1划定演练边界

本次只允许操作系统临时目录中的新建文件，数据固定为一条虚构记录。不要读取、复制、移动或删除项目的 chat.db，也不要连接线上数据库。先划清边界，恢复演练才不会变成新的数据事故。

2创建虚构 SQLite 数据

使用 better-sqlite3 在临时目录新建演练数据库，创建一张只有编号和标签的表，并写入 recovery-drill。这条记录不是业务数据，它的唯一用途是成为恢复是否成功的确定性断言。

3备份并恢复到独立副本

将演练库复制为备份副本，再复制为恢复副本，只从恢复副本查询记录。下面的命令已完成本课演练：它在同一进程中验证恢复结果后清理自己创建的临时目录。

node -e "const fs=require('fs'),os=require('os'),path=require('path'),Database=require('better-sqlite3'); const dir=fs.mkdtempSync(path.join(os.tmpdir(),'ai-agent-recovery-')); const source=path.join(dir,'drill.db'),backup=path.join(dir,'backup.db'),restored=path.join(dir,'restored.db'); const db=new Database(source); db.exec('CREATE TABLE drill_records (id INTEGER PRIMARY KEY, label TEXT NOT NULL)'); db.prepare('INSERT INTO drill_records (label) VALUES (?)').run('recovery-drill'); db.close(); fs.copyFileSync(source,backup); fs.copyFileSync(backup,restored); const check=new Database(restored,{readonly:true}); const row=check.prepare('SELECT id, label FROM drill_records').get(); check.close(); if (!row || row.id!==1 || row.label!=='recovery-drill') throw new Error('restore verification failed'); console.log(JSON.stringify({result:'restored',record:row})); fs.rmSync(dir,{recursive:true,force:true});"

成功标准不是“文件存在”，而是恢复副本查询到编号 1 和标签 recovery-drill。

4记录恢复证据与限制

打开 本次恢复演练记录。记录目标、虚构数据、恢复结果、未触碰的系统和限制；不要记录临时绝对路径、真实数据库内容或任何凭据。对恢复不确定的地方先写为限制，并向教师提问后再决定下一步。

五、验收清单

  1. 演练只使用临时目录与虚构数据，没有触碰项目现有数据库或线上服务。
  2. 已从恢复副本成功查询到虚构记录，而不只是确认备份文件存在。
  3. 恢复记录明确写出目标、结果、边界与限制。
  4. 能够说明本地 SQLite 副本恢复不代表托管数据库也已具备恢复能力。
  5. 已为长期数据写下下一步：备份频率、保留周期、恢复目标和演练节奏。

六、本课总结

  • 数据库可连接解决的是当前可用性，恢复演练解决的是未来数据可靠性。
  • SQLite 的副本恢复需要在独立路径打开并验证内容。
  • RPO 定义可接受的数据丢失窗口，RTO 定义可接受的恢复时间。
  • 演练应使用隔离环境和虚构数据，既获得证据，也不制造新事故。
