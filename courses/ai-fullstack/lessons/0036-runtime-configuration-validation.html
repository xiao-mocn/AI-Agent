第三十六课：运行时配置校验与生产环境防御

目标时长 1 小时 · 难度 ★★★ · 工程化 · 运行时安全

本节课你会学到：
  • 为什么环境变量错误应在应用启动时失败，而不是等到请求到来
  • 如何用 Zod 把字符串环境变量解析为可信的运行时配置
  • 如何区分开发便利默认值与生产环境必须提供的密钥
  • 如何让配置错误可定位，同时避免把密钥写进日志

一、配置是应用的第一份外部输入

端口、数据库地址、JWT 密钥和模型 API Key 都在代码之外，却直接决定应用能否安全运行。当前后端的 config.ts 会给 JWT_SECRET 一个开发默认值；本地启动方便，但若部署时忘记覆盖它，应用仍可能启动并使用可预测的密钥。

发现时机后果首选策略
收到第一条请求后用户先看到 500，排查信息分散避免
启动监听端口前部署立即失败，日志指出缺失的配置键推荐
CI 或发布检查时能更早发现部署清单错误作为补充
配置错误不能用“先给一个生产默认值”掩盖。 JWT_SECRET、数据库连接串和第三方 API Key 没有安全的通用默认值。默认值只适合明确无害的本地开发项，例如端口或前端地址。

二、把 process.env 变成受约束的数据

process.env 的所有值都是字符串或未定义。将它散落在路由、数据库和业务模块中，会导致每一处都要猜测类型与缺失行为。集中 Schema 让应用只有一个配置入口，并在模块导入时得到已校验的类型。

import { z } from 'zod'

const configSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production'])
    .default('development'),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  FRONTEND_URL: z.url().default('http://localhost:5173'),
  JWT_SECRET: z.string().min(32),
  DEEPSEEK_API_KEY: z.string().min(1),
})

const result = configSchema.safeParse(process.env)
if (!result.success) {
  const invalidKeys = result.error.issues
    .map((issue) => issue.path.join('.'))
    .join(', ')
  throw new Error(`启动配置无效：${invalidKeys}`)
}

export const config = result.data
错误信息只输出配置键和格式问题，不输出 process.env、完整连接串或 Key 值。运维人员需要知道“缺哪个键”，不需要也不应从日志中看到密钥。

三、动手实践

1列出真正的运行时依赖

先搜索 process.env，把变量按“可公开默认”“必须提供”“仅开发环境使用”分类。不要把测试工具的变量和生产服务凭据混在一个判断里。

Set-Location E:\project\AI-Agent\ai-backend
rg -n "process\.env" src
2创建集中配置模块

在 src/config.ts 中用 Schema 解析原始环境变量，再导出 config。端口使用 z.coerce.number()，因为环境变量最初是字符串；密钥设置最小长度，避免空字符串和明显弱值悄悄通过。

export const PORT = config.PORT
export const JWT_SECRET = config.JWT_SECRET
export const FRONTEND_URL = config.FRONTEND_URL
不要在每个模块里再次读取 process.env.JWT_SECRET。绕过集中配置会重新引入未校验值，也会让测试和部署行为不一致。
3让启动入口先校验，再监听端口

index.ts 已经在启动时加载 dotenv。确保配置模块在调用 serve() 前被导入或显式加载：配置错误应该阻止 HTTP 服务、定时任务和 WebSocket 启动。

import 'dotenv/config'
import { config } from './config'

// 访问 config 会在监听端口之前完成校验
serve({ fetch: app.fetch, port: config.PORT })
4为缺失配置写最小测试

将解析函数导出，并传入对象而不是在测试里直接修改全局 process.env。分别覆盖缺少密钥和非法端口；断言错误包含变量名，但绝不断言或打印测试用密钥。

it('缺少 JWT_SECRET 时拒绝启动配置', () => {
  const result = parseConfig({
    NODE_ENV: 'production',
    PORT: '3000',
    DEEPSEEK_API_KEY: 'test-key',
  })

  expect(result.success).toBe(false)
})

四、生产环境检查

  1. 生产部署清单中是否显式提供每个必需密钥，而不是依赖本地 .env？
  2. 端口是否被解析为 1 到 65535 的整数，而不是任意字符串？
  3. 启动失败日志是否仅包含变量名、环境和修复动作，不包含敏感值？
  4. 配置 Schema 是否在 HTTP 服务、队列和定时任务启动前执行？

五、本课总结

  • 环境变量是外部输入，应在启动期集中校验并转换类型。
  • 生产密钥必须显式提供；开发默认值不能成为生产安全策略。
  • 安全的配置错误信息帮助排查，但不能暴露值本身。
  • 配置解析函数可独立测试，让部署失败从偶发事故变成可验证行为。
