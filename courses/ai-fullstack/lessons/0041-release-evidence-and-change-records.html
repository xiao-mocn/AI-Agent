第四十一课：发布证据与变更记录

目标时长 1 小时 · 难度 ★★★ · 发布工程化 · 可追溯性

本课你会学到：
  • 把一次发布的事实压缩为他人可复查的最小证据。
  • 区分可记录的版本、探针状态与决策，和绝不能记录的凭据、连接信息与用户数据。
  • 为数据库替换这类高风险变更写清风险、回滚点和后续事项。
  • 建立一份能在下一次故障时直接使用的发布记录模板。

一、发布记录不是日志堆栈

发布发生后，最有价值的不是复制一整段控制台输出，而是让之后接手的人能在几分钟内回答：改了什么、何时改的、如何确认可用、失败时回到哪里。日志适合受控排查；发布记录适合留下稳定的决策证据。

这次 Render 数据库到期就是一个真实例子：根因是外部数据库生命周期，不是聊天代码回归；恢复动作是替换数据库并重新部署；验收证据是存活与就绪探针均返回预期状态。把这三个层次分开，复盘时才不会把猜测当成事实。

主阅读资源：Render 官方文档。平台界面会变化，但“记录变更、验证状态、保留回滚点”的原则不变。

二、记录事实，不记录秘密

发布记录要足以复现决策，却不能帮助别人进入系统。一个实用的判断是：这条信息是否能够让不了解系统的人定位“何时、何种变更、是否成功”？若答案是肯定的，它通常可以摘要记录；若它能直接连接服务、冒充用户或暴露个人数据，就不应进入文档。

可以记录原因禁止记录风险
部署日期、版本标识帮助定位变更批次。连接串、访问令牌可直接访问基础设施。
/health、/ready 状态说明最小验收结果。完整日志与异常堆栈可能暴露内部拓扑。
“替换过期免费数据库”说明变更意图和边界。用户消息与账户资料泄露个人或业务数据。
回滚条件和最近可用版本让故障处理可执行。浏览器请求头截图可能含会话或身份信息。
不要把“为了以后方便”当作记录秘密的理由。 任何需要连接或授权才能查看的诊断细节，应留在 Render 的受控界面或团队批准的日志系统里；发布记录只放摘要和入口描述。

三、六个字段让发布可追溯

小型项目不需要复杂的变更管理系统，但需要固定字段。每次发布都填同一组字段，未来才能比较两次发布的差异，也能在出现异常时迅速知道该看哪里的受控日志。

# 发布记录：[简短主题]

## 部署标识与时间
## 变更摘要
## 验收证据
## 风险与限制
## 回滚点
## 后续事项
字段是为了降低遗漏，不是为了写长文。每个字段用 1 到 3 条可验证事实即可；没有证据时写“未验证”，不要把推测包装成通过结果。

四、动手实践

1收集最小发布证据

从这次恢复中只收集四类事实：日期、变更意图、探针状态和本地测试结果。页面状态或探针响应可以记录为 ok、ready，但不要复制平台连接信息、完整日志或截图中的敏感内容。

2写出变更摘要

创建 本次发布记录。变更摘要写“替换过期的免费 Render 数据库并更新服务连接配置后重新部署”，即可说明发生的事情；不需要写任何配置值。读者应能理解影响范围，但不能借此连接系统。

3写清风险与回滚点

本次风险是新库不包含旧数据、免费实例可能再次到期、只验证了探针而未执行写入型业务测试。回滚点不是“再试一次”，而是最近一次已验证可用的服务与数据库组合；触发条件是就绪检查失败或服务不能启动。这样的表述能让下一位处理者直接行动。

4执行敏感信息检查

在项目根目录运行下面的检查。它不会发送网络请求，只在本地扫描发布记录；一旦出现敏感字段，应先删除或改写为安全摘要，再保存。

$record = Get-Content -Raw -Encoding UTF8 'docs\releases\2026-07-26-render-database-recovery.md'
@('DATABASE_URL', 'JWT_SECRET', 'API_KEY', 'postgres://', 'postgresql://', 'Authorization') |
  ForEach-Object { if ($record -match [regex]::Escape($_)) { throw "发布记录包含敏感字段：$_" } }

不确定某段信息是否可记录时，先不要写入；可以向教师提问，再决定保留安全摘要还是将细节留在受控日志系统。

五、验收清单

  1. 发布记录包含部署标识与时间、变更摘要、验收证据、风险、回滚点和后续事项。
  2. 记录明确本次是数据库替换与恢复，而不是代码功能修改。
  3. /health 与 /ready 的成功状态已作为验收证据记录。
  4. 记录不含连接信息、令牌、密钥、用户数据、完整日志或请求头。
  5. 回滚条件是可观察的失败信号，而非主观感受。

六、本课总结

  • 发布记录用最小证据保存决策背景，不替代受控日志。
  • 固定字段能降低遗漏，也让多次发布可以比较。
  • 安全摘要让记录可共享，秘密和用户数据必须留在受控系统。
  • 风险、回滚点和后续事项把一次恢复变成下一次更快的处理能力。

思考题

Q1：为什么发布记录中写“数据库替换完成”还不够？还需要哪些可验证证据？

Q2：如果某段错误日志同时包含排查线索和连接信息，应如何在发布记录中处理？

Q3：免费数据库再次到期时，发布记录中的哪些字段能帮助你更快判断是回滚、恢复还是更换长期方案？
