第五十一课：JPA 实体与 H2 持久化 Repository

预计 90–120 分钟 · 基于第 50 课的 Repository 边界

上一课的 Map 已经证明：Service 不需要知道数据从哪里来。现在把数据源换成真正的数据库，但不改 Service，也不改 URL。这一次你要看清：JPA 负责存储技术，业务 Repository 负责保护上层代码。

本课胜利点

  • 能解释 ReleaseEntity、VersionResponse 和数据库表各自的职责。
  • 用 Spring Data JPA 按 releaseLabel 查询实体。
  • 用 JpaReleaseRepository 将技术实体转换为已有业务返回值。
  • 用 H2 内存数据库和 data.sql 提供 local / 1.0.1 的初始化数据。
  • 通过 JPA 测试和既有全量测试，确认上层契约没有改变。

0. 今天替换的只是最底层

不变：业务边界

VersionService 仍只依赖 ReleaseRepository，空结果仍代表“找不到发布标签”。

不变：HTTP 契约

/version、/versions/local 的 JSON 与缺失时的统一 404 都不变。

替换：数据来源

上一课的 InMemoryReleaseRepository 不再作为 Spring Bean；改由 H2 与 JPA 查询提供数据。

新增：技术适配

JPA 实体不泄漏到 Service。适配器把它映射为业务层早已认识的 VersionResponse。

前端类比：这像把前端的数据层从本地 mock 换成真实 API，但页面仍只调用既有的 getRelease(label)。页面不需要知道请求库、URL 或数据库表；这里的 Service 也不该知道 JPA。

1. 先画出新的数据流

脱稿练习

不看后面代码，写出 GET /versions/local 从 Controller 到 H2 表的对象链。再标出：哪个位置把 ReleaseEntity 变成 VersionResponse？

正确链路：VersionController → VersionService → ReleaseRepository → JpaReleaseRepository → ReleaseJpaRepository → H2 releases 表。查询回来的 ReleaseEntity 在 JpaReleaseRepository 中映射为 VersionResponse。

2. 第一步：加入 JPA 与 H2

1

修改 pom.xml

路径：java-backend/pom.xml，在既有 <dependencies> 中加入下列依赖。

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>
为什么是两个依赖？spring-boot-starter-data-jpa 带来实体映射、Hibernate 和 Spring Data Repository；h2 才是实际运行时可连接的内存数据库。runtime 表示编译代码不直接调用 H2 API。

当前必须掌握暂时知道即可 JPA 让 Java 对象与表对应；本课不引入 MySQL、Flyway、分页、关联映射、事务或 H2 控制台。

3. 第二步：用实体描述表，不描述接口 JSON

2

新建 ReleaseEntity.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/ReleaseEntity.java

package com.example.ai.java_backend.version;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "releases")
public class ReleaseEntity {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(name = "release_label", nullable = false, unique = true)
  private String releaseLabel;

  @Column(nullable = false)
  private String version;

  protected ReleaseEntity() {
  }

  public ReleaseEntity(String releaseLabel, String version) {
    this.releaseLabel = releaseLabel;
    this.version = version;
  }

  public Long getId() { return id; }
  public String getReleaseLabel() { return releaseLabel; }
  public String getVersion() { return version; }
}
代码运行时作用不这样做会怎样
@Entity告诉 JPA：这个类需要被映射为可存储的数据。JPA 不会把它纳入实体管理。
@Id + @GeneratedValue声明数据库主键由数据库生成。JPA 不知道怎样唯一识别一行数据。
@Column(name = "release_label")把 Java 的驼峰字段明确映射到下划线列名。SQL 初始化脚本与实体字段名容易不一致。
实体和 DTO 的区别：ReleaseEntity 有主键、列名和无参构造器，因为它面向数据库；VersionResponse 只有 API 所需的版本字符串，因为它面向调用者。不要让数据库结构决定 API 的形状。

4. 第三步：让 Spring Data 生成查询，再用适配器守住边界

3

新建 ReleaseJpaRepository.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/ReleaseJpaRepository.java

package com.example.ai.java_backend.version;

import java.util.Optional;
import org.springframework.data.jpa.repository.JpaRepository;

public interface ReleaseJpaRepository extends JpaRepository<ReleaseEntity, Long> {
  Optional<ReleaseEntity> findByReleaseLabel(String releaseLabel);
}
为什么接口也能查询？Spring Data 会读取 findByReleaseLabel 这个方法名，并根据实体的 releaseLabel 属性创建查询。你不需要先写 SQL，但方法名必须与实体属性一致。

新建 JpaReleaseRepository.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/JpaReleaseRepository.java

package com.example.ai.java_backend.version;

import java.util.Optional;
import org.springframework.stereotype.Repository;

@Repository
public class JpaReleaseRepository implements ReleaseRepository {
  private final ReleaseJpaRepository releaseJpaRepository;

  public JpaReleaseRepository(ReleaseJpaRepository releaseJpaRepository) {
    this.releaseJpaRepository = releaseJpaRepository;
  }

  @Override
  public Optional<VersionResponse> findByReleaseLabel(String releaseLabel) {
    return releaseJpaRepository.findByReleaseLabel(releaseLabel)
        .map(entity -> new VersionResponse(entity.getVersion()));
  }
}
这个“多一层”的价值：JPA 的 ReleaseJpaRepository 可以随数据库技术变化；而 Service 面对的 ReleaseRepository 不变。适配器也是唯一负责 ReleaseEntity → VersionResponse 的位置。

5. 第四步：移除旧 Bean，配置 H2 与种子数据

4

停用内存实现的 Spring 身份

路径：java-backend/src/main/java/com/example/ai/java_backend/version/InMemoryReleaseRepository.java

删除 import org.springframework.stereotype.Repository; 和类上的 @Repository，其他代码可暂时保留作对照。此时 Spring 只会创建新的 JpaReleaseRepository。

为什么必须做？如果两个类都实现 ReleaseRepository 且都被 Spring 管理，构造 VersionService 时会出现 NoUniqueBeanDefinitionException：Spring 不知道该注入哪个实现。

修改 application.properties

路径：java-backend/src/main/resources/application.properties

spring.application.name=java-backend
spring.datasource.url=jdbc:h2:mem:versiondb;DB_CLOSE_DELAY=-1
spring.datasource.username=sa
spring.datasource.password=
spring.jpa.hibernate.ddl-auto=create-drop
spring.jpa.defer-datasource-initialization=true
spring.sql.init.mode=always

新建 data.sql

路径：java-backend/src/main/resources/data.sql

INSERT INTO releases (release_label, version) VALUES ('local', '1.0.1');
执行顺序为何重要？create-drop 让 Hibernate 创建 releases 表；spring.jpa.defer-datasource-initialization=true 再让 data.sql 插入数据。没有它，脚本可能在表尚未创建时运行。
为什么停机后数据会消失？jdbc:h2:mem: 表示数据库只存在于当前 Java 进程的内存中。它很适合学习与自动测试，不是生产持久化方案。

6. 第五步：先用测试锁定“数据库里真的有数据”

5

先新建 JPA 查询测试

路径：java-backend/src/test/java/com/example/ai/java_backend/version/ReleaseJpaRepositoryTest.java

package com.example.ai.java_backend.version;

import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;

@DataJpaTest
class ReleaseJpaRepositoryTest {
  @Autowired
  private ReleaseJpaRepository releaseJpaRepository;

  @Test
  void findsSeededLocalReleaseByLabel() {
    var release = releaseJpaRepository.findByReleaseLabel("local");

    assertThat(release).isPresent().get()
        .extracting(ReleaseEntity::getVersion)
        .isEqualTo("1.0.1");
  }
}

先只写测试后运行下列命令。此时因为实体和查询接口还不存在，预期会编译失败；这是在确认测试确实能发现缺失实现。

cd E:\project\AI-Agent\java-backend
.\mvnw.cmd -Dtest=ReleaseJpaRepositoryTest test

完成前面所有步骤后，再运行同一条命令，预期该测试通过。最后运行全量回归：

.\mvnw.cmd clean test
@DataJpaTest 测什么？它聚焦 JPA 相关组件，验证实体映射、表创建、data.sql 和查询方法是否能协作。已有的 Service 测试和 Controller 测试仍然保留，它们继续保护业务规则和 HTTP 契约。

7. 运行后如何判断成功

检查点预期若不符合，先检查
定向 JPA 测试ReleaseJpaRepositoryTest 通过依赖、实体扫描、data.sql 的表名与列名。
应用启动没有重复 Bean 错误内存实现的 @Repository 是否真的删除。
/versions/local{"version":"1.0.1"}种子数据是否插入了 local。
/versions/missing原来的统一 404 JSON适配器是否保留空 Optional，而非自行抛出新异常。

变式练习：不用改 Java，增加一个版本

在 data.sql 追加一行：INSERT INTO releases (release_label, version) VALUES ('staging', '1.1.0-rc1');。预测 GET /versions/staging 的响应；再解释为什么 Controller、Service 和 JPA 查询接口都不用改。

完成标准

  • 能说清实体面向存储、VersionResponse 面向 API。
  • VersionService 仍只注入 ReleaseRepository。
  • H2 中有 local / 1.0.1 种子数据，JPA 测试可以查询到它。
  • 内存实现不再是 Spring Bean，应用没有 Repository 注入歧义。
  • .\mvnw.cmd clean test 通过，既有接口契约保持稳定。
