第二十一课：优雅关闭与健康检查

目标时长 2 小时 · 难度 ⭐⭐⭐ · 后端 · 工程质量

本节课你会学到：
  • 为什么直接 kill 掉进程会丢请求、丢数据
  • SIGTERM / SIGINT 信号是什么，容器编排系统怎么用它们
  • 优雅关闭三部曲：停止接新请求 → 等在途请求做完 → 关数据库连接
  • 健康检查的两种语义：存活（liveness）和就绪（readiness）的区别
  • 给项目加上 /health 和 /ready 两个接口

一、直接杀掉进程会发生什么

目前项目的启动方式是 serve({ fetch: app.fetch, port }, ...)，进程会一直跑到被杀死为止。想象一下部署时的场景：你要发布新版本，Railway/Render 之类的平台会给旧进程发一个"该停了"的信号，然后启动新进程。如果旧进程收到信号后立刻退出：

  • 正在处理的 HTTP 请求（比如某个用户的 /api/chat 请求还在等 DeepSeek 返回）会被硬中断，用户收到连接重置错误
  • PostgreSQL 连接池里还有未提交的查询，连接被粗暴掐断，可能留下半吊子的事务状态
  • 如果你的负载均衡器还没来得及把这个实例摘出流量池，新请求可能继续被转发到一个已经死掉的进程

这些问题平时几乎不会被注意到，因为本地开发时你是 Ctrl+C 手动停，连接数为零。但生产环境每次发布都在发生，只是没人把它和"某几个用户偶尔请求失败"联系起来。

二、SIGTERM 与 SIGINT：进程收到的"退出通知"

Node.js 进程可以监听系统发来的信号：

  • SIGINT：你在终端按 Ctrl+C 时发的信号
  • SIGTERM：容器编排系统（Docker、Kubernetes、大多数 PaaS）在"温和地"要求进程退出时发的信号——这是它们的标准做法，不是直接 kill -9
容器平台的典型流程是：先发 SIGTERM，给进程一个"宽限期"（Kubernetes 默认 30 秒）自行清理退出；如果超时还没退出，才会发 SIGKILL 强制杀死——这个信号无法被监听或拦截，所以你必须在宽限期内完成清理。

默认情况下 Node.js 收到 SIGTERM 会直接退出，不会给你机会做清理。要拿到这个"宽限期"，得自己监听信号。

三、优雅关闭三部曲

1监听信号，停止接新请求

@hono/node-server 的 serve() 返回一个原生 http.Server 实例，调用它的 .close() 会停止接受新连接，但等在途连接处理完再回调：

// index.ts
const server = serve({ fetch: app.fetch, port }, (info) => {
  logger.info(`服务器已启动：http://localhost:${info.port}`)
})

function shutdown(signal: string) {
  logger.info({ signal }, '收到退出信号，开始优雅关闭')

  server.close(async () => {
    logger.info('HTTP 服务器已停止接受新连接')
    // 第二步会在这里加：关闭数据库连接
    process.exit(0)
  })

  // 兜底：如果 10 秒内还没关完（比如有请求卡死），强制退出
  setTimeout(() => {
    logger.error('优雅关闭超时，强制退出')
    process.exit(1)
  }, 10_000).unref()
}

process.on('SIGTERM', () => shutdown('SIGTERM'))
process.on('SIGINT', () => shutdown('SIGINT'))
一定要加超时兜底。server.close() 的回调只有在所有连接都结束后才会触发——如果某个请求因为 bug 永远不会结束（比如卡住的流式响应），进程就会永远挂着，白白占满编排系统给的宽限期，最后被 SIGKILL 强杀，反而绕过了你精心写的清理逻辑。
2关闭数据库连接池

项目里 db.ts 用 PG 时维护了一个连接池 pool，进程退出前要显式调用 pool.end() 把连接优雅归还，否则数据库那边会看到一堆"客户端异常断开"的连接，长期攒着可能拖垮连接数上限：

// db.ts 新增一个导出函数
export async function closeDB() {
  if (isPG && pool) {
    await pool.end()
  }
  // better-sqlite3 是同步文件句柄，可选调用 db.close()
}
// index.ts —— 在 server.close() 回调里补上这一步
server.close(async () => {
  logger.info('HTTP 服务器已停止接受新连接')
  await closeDB()
  logger.info('数据库连接已关闭')
  process.exit(0)
})

四、健康检查：liveness 和 readiness 是两回事

容器编排系统和负载均衡器需要定期问你的服务"你还好吗"，但这个问题其实有两层含义，很多人一开始会把它们混为一谈：

类型回答的问题失败后的动作
Liveness（存活）"这个进程是不是卡死了？"重启这个实例
Readiness（就绪）"这个实例现在能不能正常处理请求？"暂时把它从负载均衡的流量池里摘掉，但不重启
区别的关键场景：数据库连接暂时断开时，进程本身没死（liveness 应该是健康的，不该被重启），但它确实处理不了任何需要查库的请求（readiness 应该是不健康的，先别给它转发流量）。如果 liveness 检查里也去查数据库，一次数据库抖动就会触发一连串不必要的重启，反而让故障恢复更慢。
1加 /health（liveness）

只要进程能响应 HTTP 请求，就返回 200——不做任何外部依赖检查：

app.get('/health', (c) => c.json({ status: 'ok' }))
2加 /ready（readiness）

真正探测依赖是否可用——比如数据库能不能查通：

app.get('/ready', async (c) => {
  try {
    if (isPG) {
      await pool.query('SELECT 1')
    } else {
      db.prepare('SELECT 1').get()
    }
    return c.json({ status: 'ready' })
  } catch (err) {
    logger.error({ err }, '就绪检查失败')
    return c.json({ status: 'not ready' }, 503)
  }
})
返回 503（Service Unavailable）而不是 500——这是语义正确的状态码，明确告诉调用方"我现在不是坏了，只是暂时没法处理请求"，负载均衡器和监控系统都会按这个约定识别"临时不可用"。

五、本课总结

  • 直接杀进程会丢在途请求、留下半吊子的数据库连接——优雅关闭是生产可靠性的基本功
  • SIGTERM 是编排系统给你的"清理时间"，监听它并在超时前完成 server.close() + 关闭数据库连接
  • 一定要加超时兜底，否则一个卡死的请求会让优雅关闭变成"永远不关闭"
  • liveness 只回答"进程活着吗"，readiness 才回答"依赖都通吗"——混用会导致依赖抖动时的不必要重启
  • /ready 检查失败时返回 503，这是负载均衡器和监控系统都认识的标准语义
