第二十二课：Docker 容器化

目标时长 2 小时 · 难度 ⭐⭐⭐ · 后端 · 部署

本节课你会学到：
  • 为什么要把应用打包成容器，而不是直接在服务器上装 Node.js 跑
  • 写一个针对本项目的 Dockerfile（多阶段构建）
  • better-sqlite3 这类原生模块在容器里必须重新编译的坑
  • .dockerignore 排除不该打进镜像的文件
  • 把第二十一课的 /health 接口接入 HEALTHCHECK 指令
  • 本地构建、运行、传环境变量的完整流程

一、为什么要容器化

项目目前部署（第十五课）依赖平台（Railway/Render）直接识别 package.json 帮你跑 npm install + npm start。这种方式简单，但有个前提：平台得知道怎么"猜"你的启动方式，而且你本地开发环境和平台的运行环境（Node 版本、系统库）不一定完全一致。

  • "我这能跑"问题：本地 Node 24，平台默认 Node 18，行为可能有细微差异
  • 依赖平台的约定：换一个平台（比如从 Railway 换到自己的服务器），部署方式要重新摸索
  • 原生模块隐患：better-sqlite3 这种依赖 C++ 编译的模块，如果平台的构建环境和你本地不一致，可能直接装不上

Docker 把"运行时环境"本身打包进镜像——你在 Dockerfile 里精确声明用哪个 Node 版本、装哪些系统依赖，镜像在你电脑上、在任何云平台上、甚至在同事电脑上，行为完全一致。这也是为什么几乎所有云平台（Railway、Render、AWS、自建服务器）都支持"给我一个 Docker 镜像，我来跑"这种最通用的部署方式。

二、多阶段构建：为什么不是一个 Dockerfile 走到底

项目用 tsx 直接跑 TypeScript（package.json 里 "start": "tsx src/index.ts"），好消息是 tsx 本身在 dependencies 里，不需要额外的编译步骤——但即便如此，构建镜像时用到的工具（比如给 better-sqlite3 编译原生模块要用的 python3、make、g++）不应该留在最终跑起来的镜像里，那些只在"装依赖"这一步需要，运行时完全用不上。

多阶段构建（multi-stage build）解决的就是这个问题：

阶段一（builder）：装好编译工具，跑 npm ci 把所有依赖（包括原生模块）编译好
阶段二（runtime）：只从阶段一里复制编译好的 node_modules 和源码，不带编译工具，镜像体积小很多

三、写 Dockerfile

1在 ai-backend/ 下新建 Dockerfile 
# ---- 阶段一：builder，装依赖 + 编译原生模块 ----
FROM node:24-slim AS builder
WORKDIR /app

# better-sqlite3 编译需要这些系统工具
RUN apt-get update && apt-get install -y python3 make g++ && rm -rf /var/lib/apt/lists/*

COPY package.json package-lock.json ./
RUN npm ci

COPY . .

# ---- 阶段二：runtime，只留运行需要的东西 ----
FROM node:24-slim
WORKDIR /app

COPY --from=builder /app/node_modules ./node_modules
COPY . .

ENV NODE_ENV=production
EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD node -e "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

CMD ["npm", "start"]
HEALTHCHECK 探测的是 /health（liveness），不是 /ready——原因和第二十一课的道理一样：数据库短暂不可用不该让 Docker 判定容器"不健康"从而重启它，那只是暂时没法处理请求，不是进程本身出了问题。
2为什么 node_modules 必须在容器里装，不能直接复制本地的

better-sqlite3 是一个原生模块，装的时候会针对当前系统（操作系统 + CPU 架构 + Node 版本 ABI）编译一份 .node 二进制文件。如果你在 Windows/Mac 上装好 node_modules 再直接 COPY 进 Linux 容器，这份二进制文件根本对不上容器的运行环境，启动时会直接报错。

这也是为什么 Dockerfile 里是 COPY package.json package-lock.json ./ 再 RUN npm ci，而不是 COPY node_modules ./node_modules——必须让 npm ci 在容器内部跑，针对容器自己的系统重新编译原生模块。
3新建 .dockerignore

和 .gitignore 类似，避免把不该打进镜像的文件带进构建上下文（既浪费构建时间，也可能把敏感文件打进镜像里）：

node_modules
.env
.env.*
chat.db
chat.db-shm
chat.db-wal
.git
*.log
node_modules 必须排除——不排除的话，本地的 node_modules（可能是 Windows 编译的原生模块）会被传进构建上下文，虽然 Dockerfile 里没有直接用它，但会拖慢构建、浪费空间。

四、构建与运行

1构建镜像 
cd ai-backend
docker build -t ai-backend:latest .
2运行容器，传入环境变量 
docker run -p 3000:3000 \
  -e JWT_SECRET=your-secret \
  -e DEEPSEEK_API_KEY=your-key \
  -e DATABASE_URL=postgres://... \
  ai-backend:latest
生产环境不要把密钥写死在 Dockerfile 或镜像里——镜像是要被推送、分发的，写死等于把密钥公开出去。用 -e（或 --env-file）在运行时注入，镜像本身不包含任何密钥。
3验证健康检查 
docker ps
# STATUS 列会显示 (healthy) 或 (unhealthy)，对应 HEALTHCHECK 的探测结果

五、本课总结

  • 容器化解决的是"环境一致性"问题——本地、任何云平台、任何机器上跑起来都一样
  • 多阶段构建把编译工具和最终运行环境分开，减小镜像体积，也减少攻击面
  • 原生模块（better-sqlite3）必须在目标平台（容器）内部重新编译，不能直接复制本地的 node_modules
  • .dockerignore 排除 node_modules、.env、数据库文件，避免污染构建上下文和镜像
  • HEALTHCHECK 探测 /health（liveness）而不是 /ready，语义和编排系统的健康检查保持一致
  • 密钥永远在运行时通过环境变量注入，不写进镜像
