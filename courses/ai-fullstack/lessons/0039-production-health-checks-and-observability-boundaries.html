第三十九课：生产环境健康检查与可观测性边界

目标时长 1 小时 · 难度 ★★★ · 工程化 · 生产可用性

本课你会学到：
  • 区分存活检查（liveness）和就绪检查（readiness）的职责。
  • 为数据库依赖设计快速、稳定且可判定的就绪检查。
  • 让探针暴露服务状态，同时隐藏连接串、环境变量、异常堆栈等内部信息。
  • 用自动化测试锁定状态码和最小响应体。

一、“进程活着”不等于“可以接流量”

生产平台需要两个不同答案：当前进程还能否响应，以及当前实例能否完整处理业务请求。把这两个问题塞进同一个接口，会让恢复动作变得混乱。例如数据库短暂不可用时，重启 Node.js 进程通常解决不了问题；此时应把实例移出流量，而不是不断重启它。

探针回答的问题失败后的典型动作
GET /health进程是否仍能响应 HTTP平台重启实例。
GET /ready关键依赖是否可用，实例能否接收流量平台暂停向实例转发流量。
/health 应尽量轻量，不访问数据库和第三方 AI 服务。否则一个外部依赖故障会被误判成进程死亡，引发无效重启。

二、就绪检查只验证关键依赖

当前项目的业务数据依赖 SQLite 或 PostgreSQL，因此 /ready 调用 checkDBHealth() 执行 SELECT 1。这比读取业务表更稳定：它验证连接和查询能力，却不依赖某条业务数据是否存在。DeepSeek API 不适合作为每次就绪探测的同步依赖，因为高频探针会消耗配额，第三方抖动也可能让整个应用被错误摘流。

就绪检查必须有明确超时。当前查询依赖数据库驱动和连接配置的超时策略；部署生产数据库时，应同步核对连接超时，避免 /ready 长时间挂起。

三、可观测不代表公开内部结构

探针是公开可访问的运维接口，响应应保持低基数、稳定和最小化。客户端只需要知道 ok、ready 或 not ready，详细错误应进入受控日志，由请求 ID、时间和部署版本辅助排查。

不要从探针返回异常对象。 数据库连接串、主机名、驱动错误、环境变量、文件路径和堆栈都可能帮助攻击者绘制内部系统。失败响应使用固定文案，服务端日志再记录诊断上下文。

四、动手实践

1核对现有路由的职责边界

打开 ai-backend/src/utils/app.ts，确认 /health 只返回进程状态，/ready 才调用数据库检查。还要确认两个路由位于 /api/* 鉴权范围之外，否则部署平台无法在没有用户 JWT 的情况下探测实例。

app.get('/health', (c) => c.json({ status: 'ok' }))

app.get('/ready', async (c) => {
  try {
    await checkDBHealth()
    return c.json({ status: 'ready' })
  } catch (err) {
    logger.error({ err }, '就绪检查失败')
    return c.json({ status: 'not ready' }, 503)
  }
})
2核对数据库探测是否足够小

打开 ai-backend/src/utils/db.ts，确认 PostgreSQL 和 SQLite 分支都只执行 SELECT 1，且函数不打印连接信息。使用 PowerShell 搜索时不依赖本机未安装的 rg：

Set-Location E:\project\AI-Agent\ai-backend
Get-ChildItem -Path src -Recurse -File |
  Select-String -Pattern 'checkDBHealth|SELECT 1'

搜索结果应只帮助定位代码；不要为了调试把 DATABASE_URL 或完整配置对象输出到终端。

3为探针补充最小响应测试

在现有测试服务器启动后，为两个成功路径增加断言。使用 toEqual 精确匹配响应体，这不仅验证功能，也能防止未来无意加入数据库类型、路径或错误详情。

describe('健康检查', () => {
  it('进程存活时 /health 返回最小响应', async () => {
    const res = await request(server).get('/health')

    expect(res.status).toBe(200)
    expect(res.body).toEqual({ status: 'ok' })
  })

  it('数据库可用时 /ready 返回就绪', async () => {
    const res = await request(server).get('/ready')

    expect(res.status).toBe(200)
    expect(res.body).toEqual({ status: 'ready' })
  })
})

完成后运行 npm test。失败分支还应保持固定的 503 与 { status: 'not ready' }；后续可通过依赖替身为该分支增加独立测试。

4配置部署平台探针

将存活路径配置为 /health，就绪路径配置为 /ready。间隔、超时和失败阈值要给启动与数据库短暂抖动留出空间；不要把业务聊天接口当探针，因为它需要鉴权、会调用 AI，并可能产生数据和费用。

如果部署平台只支持一个健康检查路径，优先使用 /ready 判断能否接流量，同时通过平台进程管理能力监控进程退出。要记录这个限制，避免团队误以为存活和就绪已被分别处理。

五、验收清单

  1. /health 不访问数据库、AI API 或其他外部依赖。
  2. /ready 成功返回 200，数据库不可用时返回 503。
  3. 两个探针都不要求用户 JWT，也不产生业务数据。
  4. 响应体只有稳定状态，不包含连接信息、配置值、路径、异常或堆栈。
  5. 探针测试精确断言状态码和响应体，npm test 全部通过。

六、本课总结

  • 存活检查决定是否重启，就绪检查决定是否接收流量。
  • 就绪检查只验证处理请求所必需的关键依赖，并保持快速、可超时。
  • 公开响应提供最小状态，详细诊断留在受控日志中。
  • 精确响应测试既防回归，也能守住信息泄露边界。
