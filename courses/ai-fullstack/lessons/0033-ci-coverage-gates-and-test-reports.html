第三十三课：CI 中的覆盖率门槛与测试报告

目标时长 1 小时 · 难度 ★★★ · 工程化 · 持续质量

本节课你会学到：
  • 如何让 GitHub Actions 在每次推送和 Pull Request 中生成覆盖率报告
  • 如何把 HTML 覆盖率报告作为 CI Artifact 保留，而不是只看一段终端日志
  • 如何用 Vitest 的 thresholds 建立循序渐进的质量门槛
  • 如何区分“代码变少导致比例变化”和“真正遗漏了风险分支”

一、覆盖率成为团队反馈，而不是本地习惯

第 32 课的覆盖率报告只在你的电脑上生成。真正的团队协作中，Pull Request 审查者需要知道这次改动是否让关键路径失去测试保护；CI 正是把这个信号固定到每一次代码变更中的位置。

CI 的职责不只是“跑一下测试”：它要在干净环境中重复执行命令、在失败时阻止合并，并保存足以定位问题的证据。覆盖率 HTML 报告适合作为 Artifact，运行日志适合快速判断通过或失败，两者各自解决不同问题。

输出适合回答的问题保留方式
终端摘要测试和门槛是否通过？GitHub Actions 日志
HTML 报告具体哪一行、哪个分支未覆盖？Actions Artifact
阈值失败是否低于项目约定的最低质量线？CI 失败状态
先观察，再设门槛。 当前项目的分支覆盖率仍有明显空白。直接设置很高的全局百分比会把正常开发变成“补数字”，而不是补安全与权限分支。先以当前可重复的基线设线，再随着关键测试增加逐步提高。

二、门槛是一条可维护的工程约定

Vitest 可以在配置中对 statements、branches、functions、lines 设置最低覆盖率。正数表示最低百分比；未达到时命令以非零状态退出，GitHub Actions 随即标记失败。

import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
      thresholds: {
        statements: 65,
        branches: 40,
        functions: 65,
        lines: 65,
      },
    },
  },
})

这些数字只是本项目当前状态下的起点示例，不是通用标准。后续增加错误处理、鉴权和会话权限测试后，应结合风险路径和稳定性调整，而不是机械追逐 100%。

三、动手实践

1新增 Vitest 配置并先观察基线

在 ai-backend/vitest.config.ts 中配置 V8 provider、text 与 html reporter。先不要写 thresholds，运行一次覆盖率命令并记录四项基线；门槛必须来自真实报告而非猜测。

Set-Location E:\project\AI-Agent\ai-backend
npm run test:coverage
Get-ChildItem .\coverage
2为当前项目设置可通过的起始门槛

根据步骤 1 的结果，在 coverage.thresholds 中设置略低于或等于当前稳定基线的数值。四项都要设置，尤其不要漏掉鉴权、404 与权限判断常常影响的 branches。

coverage: {
  provider: 'v8',
  reporter: ['text', 'html'],
  thresholds: {
    statements: 65,
    branches: 40,
    functions: 65,
    lines: 65,
  },
}

再次运行 npm run test:coverage。如果失败，先阅读报告中的未覆盖区域和实际百分比，再决定补测试还是调整一个尚未稳定的基线。

3让 CI 保存覆盖率报告

在 .github/workflows/ci.yml 的 npm test 后，运行覆盖率命令，并使用 actions/upload-artifact 上传 ai-backend/coverage。上传步骤使用 if: always()，这样即使门槛失败，也能下载报告排查原因。

- name: 运行覆盖率测试
  run: npm run test:coverage

- name: 保存覆盖率报告
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: coverage-report
    path: ai-backend/coverage
    if-no-files-found: error
当前 workflow 已设置 working-directory: ai-backend，但 upload-artifact 的 path 相对仓库根目录解析。因此这里使用 ai-backend/coverage，不要只写 coverage。
4检查一次真实 CI 运行

提交并推送后，打开 GitHub Actions 的 CI 运行详情。确认“运行覆盖率测试”和“保存覆盖率报告”两个步骤存在；在 Artifacts 区域下载 coverage-report，解压后打开 index.html 查看未覆盖行。

不要把 coverage/ 提交进仓库。 它是每次测试重新生成的输出，应通过 .gitignore 排除；需要追溯时从 CI Artifact 获取对应那次运行的报告。

四、门槛失败时的排查顺序

  1. 先确认失败的是测试断言，还是 coverage threshold；两者的修复方向不同。
  2. 打开同一次 CI 运行上传的 Artifact，定位未覆盖文件和行号。
  3. 判断缺口是否属于认证、资源归属、数据库错误等高风险分支；高风险分支优先补 API 测试。
  4. 若是重构删除了测试可达代码或报告基线本身不稳定，说明原因后再调整阈值，避免无解释地降低质量线。

五、本课总结

  • 覆盖率报告应在 CI 中生成，使每次提交都拥有可审查的质量反馈。
  • Artifact 保存 HTML 报告，能让失败后的排查回到具体文件与行号。
  • 门槛应来自项目实际基线，并随关键风险分支的测试增加逐步提高。
  • 质量门槛的目标是保护行为，不是制造漂亮的百分比。
