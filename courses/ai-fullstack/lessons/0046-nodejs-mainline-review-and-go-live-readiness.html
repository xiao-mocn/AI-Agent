第四十六课：Node.js 主线复盘与上线验收清单

目标时长 1 小时 · 难度 ★★☆ · 阶段复盘 · 上线决策

本课你会学到：
  • 把“功能做过了”转换为可以定位和复核的上线证据。
  • 用统一状态区分已通过、部分通过、未验证和明确阻塞。
  • 按风险决定哪些缺口阻止上线，哪些可以带负责人进入后续计划。
  • 从 Node.js 实现中提炼 Spring Boot 迁移必须保持的行为基线。

一、课程完成度不等于上线就绪度

Node.js 主线已经覆盖 API、AI 调用、认证、数据库、测试、CI、容器、配置、可观测性与恢复，但“学过”或“文件存在”都不是上线证据。上线判断需要回答：哪条行为被什么命令或记录验证、证据产生于何时、结果是什么、谁负责缺口，以及缺口是否影响用户或数据安全。

证据也有时效性。本地测试通过不能代替部署后的烟雾测试，桌面恢复演练不能代替真实隔离恢复，配置示例文件存在也不能证明部署平台已经正确填写变量。复盘的目标不是制造一个漂亮的全绿表格，而是诚实地暴露尚未验证的边界。

主阅读资源：Google SRE Book：Release Engineering。发布可靠性来自可重复流程和可审计证据，而不是依赖某个人记得检查所有细节。

二、四种状态让结论不再含糊

状态含义上线处理
PASS验收标准明确，当前证据已通过且可复核。记录证据位置和时间。
PARTIAL部分条件通过，但范围、环境或时效不足。说明缺口、负责人和复验方式。
NOT VERIFIED尚无足够证据，不能推断成功或失败。高风险项视为上线阻塞。
BLOCKED已有证据表明不满足标准，或前置条件不可用。修复并重新验收后再判断。

NOT VERIFIED 不是较轻的失败，它表示风险仍然未知。认证边界、运行配置、数据库持久化、健康检查和恢复能力一旦未验证，就应默认阻止正式上线；文档措辞或低风险体验问题可以在影响明确时进入后续计划。

三、证据矩阵要覆盖完整运行链路

领域关键问题候选证据
核心行为注册、登录、对话、会话隔离和错误分支是否符合约定？自动化测试、接口契约和烟雾测试。
安全与配置认证、输入校验、限流和启动配置是否失效关闭？测试、Schema、示例变量和配置检查。
交付与运行CI、镜像、部署、健康检查、日志和回滚是否可复核？工作流、构建记录、探针和发布记录。
数据与恢复数据存在哪里，备份是否可恢复，RPO/RTO 证据属于哪一级？恢复记录、运行手册和演练结果。
迁移基线换成 Spring Boot 后，哪些外部行为必须保持一致？路由、状态码、认证语义、数据模型和日志字段。
不要读取或复制 ai-backend/.env、chat.db、凭据、真实业务数据或线上日志来填清单。不要因为文件存在就标记 PASS；生产部署、备份恢复和用户流量未实际验证时，必须保留其证据级别和限制。

四、动手实践

1刷新本地代码证据

从 ai-backend 目录运行测试与类型检查，记录命令、时间、通过数量或错误摘要。测试证明当前自动化覆盖的行为，类型检查证明静态契约一致；两者都不能替代部署后验收。

npm test
npx tsc --noEmit
2盘点本地候选证据

从仓库根目录运行下面的只读命令。它只检查八个明确路径是否存在，不读取文件内容、环境变量、数据库或网络；输出 8/8 仍只表示候选证据齐全，不能自动把任何领域标为 PASS。

node -e "const fs=require('fs'); const checks=[['test-script','ai-backend/package.json'],['container','ai-backend/Dockerfile'],['ci','.github/workflows/ci.yml'],['config-example','ai-backend/.env.example'],['release-record','docs/releases/2026-07-26-render-database-recovery.md'],['recovery-runbook','docs/recovery/backup-failure-and-restore-runbook.md'],['rto-plan','docs/recovery/rto-drill-plan.md'],['rto-record','docs/recovery/2026-07-28-rto-tabletop.md']].map(([area,path])=>({area,path,present:fs.existsSync(path)})); const present=checks.filter(item=>item.present).length,total=checks.length,result=present===total?'inventory-complete':'inventory-has-gaps'; console.log(JSON.stringify({result,present,total,checks},null,2)); if(present!==total) process.exitCode=1"
3建立上线就绪矩阵并作出判断

新建 docs/releases/nodejs-go-live-readiness.md。为核心行为、安全与配置、CI 与容器、部署与可观测性、数据与恢复分别写：验收标准、状态、证据位置、限制、负责人和复验方式。任一高风险领域为 NOT VERIFIED 或 BLOCKED 时，当前结论必须是 NO-GO；只有所有阻塞项都有新证据后才能重新评审。

4提炼 Spring Boot 迁移基线

在同一文档增加“Java 迁移基线”章节，至少记录：公开路由与状态码、JWT 鉴权和用户隔离语义、输入校验与错误格式、数据库实体关系、/health 与 /ready 语义、请求 ID 和结构化日志字段、现有回归测试。这里只定义必须保持的外部行为，不创建 Java 项目，也不要求内部类名和 Node.js 文件结构一一对应。

五、验收清单

  1. 本地测试和类型检查均有新鲜结果，失败时保留真实错误而不是改写结论。
  2. 候选证据盘点命令只读取固定非敏感路径，并明确“存在不等于通过”。
  3. 就绪矩阵覆盖五个领域，每项都有状态、证据、限制、负责人和复验方式。
  4. 高风险的未验证或阻塞项会导出 NO-GO，没有用平均分掩盖关键风险。
  5. Java 迁移基线描述外部行为与测试，不要求复制 Node.js 内部实现。

六、本课总结

  • 上线判断依赖可复核、带范围和时效的证据，而不是功能清单。
  • 统一状态让未知风险、部分证据和明确失败得到不同处理。
  • 关键安全、配置、数据和运行能力没有证据时，应作出 NO-GO 判断。
  • Node.js 主线的行为契约和回归测试，将成为 Java 重写时的迁移护栏。
