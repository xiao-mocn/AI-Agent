第二十九课：前端接入会话列表与切换

目标时长 1.5 小时 · 难度 ⭐⭐⭐ · 前端 · Vue 3

本节课你会学到：
  • 把 ChatView.vue 侧边栏里那个本地内存造出来的假 sessions 数组，换成 GET /api/sessions 拉回来的真数据
  • 为什么"点击切换会话"光靠前端状态是不够的——还需要补一个按需拉历史消息的接口
  • 双击标题触发行内编辑，调用 PATCH /api/sessions/:id 重命名，以及"乐观更新失败要回滚"这件事怎么落地
  • 悬浮显示删除按钮，调用 DELETE /api/sessions/:id，并处理"删的正好是当前激活会话"这个边界情况

一、现在的侧边栏是"假的"

打开 ai-frontend/src/ChatView.vue 会发现，侧边栏其实早就存在了——sessions 是一个纯前端的 ref 数组，点"＋ 新建对话"会 push 一条本地记录，点某个 session-item 只是切换 activeId。这些数据只活在浏览器内存里：刷新页面就没了，换个浏览器打开也看不到，更别说重命名和删除—— UI 上根本没有对应的按钮。

第二十八课已经在后端把 GET /api/sessions、PATCH /api/sessions/:id、 DELETE /api/sessions/:id 三个接口做出来了，这节课要做的就是把前端这块"假数据"换成真实接口驱动的状态。

二、切换会话时，历史消息从哪来？

这里有一个容易被忽略的缺口：现在的 Session 类型里 messages 是前端自己攒出来的—— 只有你在当前这个浏览器标签页里亲自发过消息的会话，才会有 messages 数组。如果 GET /api/sessions 返回了三个月前创建的一个会话，点击它切换过去，messages 是空的，但这个会话在数据库里其实已经有几十条历史对话了—— 这不是"没有历史"，而是"前端还没去问后端要"。

如果不处理这个缺口：用户点开一个熟悉的老会话，看到的却是一片空白，会以为自己的聊天记录丢了—— 这是一个体验上的"数据丢失"假象，比接口报错更容易让人恐慌。

所以这节课要先在后端补一个小接口：GET /api/sessions/:id/messages，直接复用第二十七课已经写好的 getHistory(sessionId, userId)（归属校验已经写在 SQL 的 WHERE 里了，不用重新写一遍）。 唯一要注意的是把 system 角色的消息过滤掉——那是喂给 AI 的系统提示词，不是用户想在聊天界面里看到的内容。

方案做法取舍
切换会话时按需拉取点击一个会话，如果本地没缓存过它的消息，就发一次 GET /api/sessions/:id/messages首次点击有一次网络往返延迟，但不用一次性把所有会话的全部历史都拉下来，流量和内存都更省
拉列表时把消息一起带回来GET /api/sessions 直接在返回体里嵌套每个会话的全部消息切换会话零延迟，但会话一多、每个会话历史一长，首页加载就会变得很重，多数会话用户可能根本不会点开

这节课选按需拉取：侧边栏列表本身只需要 id/title/updated_at（listSessions 已经是这么设计的），消息内容留到真正点开某个会话时才去要，拉过一次之后缓存在本地，同一个会话反复切换不用重复请求。

三、动手实践

1后端补一个 GET /api/sessions/:id/messages 
// src/business/sessions.ts，新增一个路由，复用已有的 getHistory
import { listSessions, renameSession, deleteSession, getHistory } from '../db'

// 放在 GET /api/sessions 后面即可
app.get('/api/sessions/:id/messages', async (c) => {
  const userId = c.get('userId') as number
  const sessionId = c.req.param('id')

  const history = await getHistory(sessionId, userId) as { role: string; content: string }[]
  // system prompt 不展示给用户
  const messages = history.filter(m => m.role !== 'system')
  return c.json({ messages })
})
这里没有单独判断"会话不存在"返回 404——getHistory 的 WHERE session_id = ? AND user_id = ? 对一个不存在或不属于自己的 sessionId 就是查出空数组，前端拿到空数组直接当"这个会话还没有消息"处理即可， 不需要额外分支。
2页面加载时，用 GET /api/sessions 替换本地假数据 
import { ref, onMounted, nextTick, computed } from 'vue'

type SessionMeta = { id: string; title: string; updated_at: string }

const sessions = ref<SessionMeta[]>([])
const activeId = ref<string>('')
// 消息按 sessionId 分开缓存，切换会话时优先读缓存
const messagesCache = ref<Record<string, Message[]>>({})

async function loadSessions() {
  const token = localStorage.getItem('token')
  const res = await fetch(`${API_URL}/api/sessions`, {
    headers: { Authorization: `Bearer ${token}` },
  })
  if (!res.ok) return
  const { sessions: list } = await res.json()
  sessions.value = list
  // 有历史会话就默认选中最新的那个，没有就留空走"新对话"逻辑
  if (list.length > 0) await switchSession(list[0].id)
}

onMounted(loadSessions)
原来的 sessions.value = [newSession()] 初始值要删掉，改成空数组——不然页面一加载就会有一条 假的"新对话"排在真实列表最前面。
3切换会话：本地有缓存直接用，没有就按需拉取 
async function switchSession(id: string) {
  activeId.value = id
  if (messagesCache.value[id]) return // 缓存过，不用再请求

  const token = localStorage.getItem('token')
  const res = await fetch(`${API_URL}/api/sessions/${id}/messages`, {
    headers: { Authorization: `Bearer ${token}` },
  })
  messagesCache.value[id] = res.ok ? (await res.json()).messages : []
}

const activeMessages = computed(() => messagesCache.value[activeId.value] ?? [])
模板里原来引用 activeSession.value.messages 的地方，改成 activeMessages.value； send() 里往消息数组 push 的地方，改成操作 messagesCache.value[activeId.value]（先用 ?? [] 兜底一个空数组，防止新会话第一次发消息时数组还不存在）。
4双击标题重命名，乐观更新 + 失败回滚 
async function renameSession(s: SessionMeta, newTitle: string) {
  const old = s.title
  s.title = newTitle // 先改界面，用户不用等网络请求就能看到反馈

  const token = localStorage.getItem('token')
  const res = await fetch(`${API_URL}/api/sessions/${s.id}`, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
    body: JSON.stringify({ title: newTitle }),
  })
  if (!res.ok) s.title = old // 请求失败，回滚回原标题
}
"乐观更新"意味着 UI 先假设请求会成功。如果不做失败回滚，一旦 PATCH 因为网络问题或者 401 失败了，界面上显示的标题和数据库里的真实标题就会永久不一致，用户还完全不知情。
5悬浮删除按钮，处理"删的正好是当前会话" 
async function removeSession(id: string) {
  const token = localStorage.getItem('token')
  const res = await fetch(`${API_URL}/api/sessions/${id}`, {
    method: 'DELETE',
    headers: { Authorization: `Bearer ${token}` },
  })
  if (!res.ok) return

  sessions.value = sessions.value.filter(s => s.id !== id)
  delete messagesCache.value[id]

  // 删的正好是当前打开的会话：切到列表里第一个，列表也空了就回到"新对话"的空状态
  if (activeId.value === id) {
    if (sessions.value.length > 0) await switchSession(sessions.value[0].id)
    else activeId.value = crypto.randomUUID() // 空列表，起一个新会话 id，等用户发第一条消息时后端自动建档
  }
}
如果不处理"删的正好是当前激活会话"这个分支，删除后 activeId 还指向一个已经被后端删掉的 sessionId——这时候如果用户直接在输入框发消息，createSessionIfNotExists 会把它当成一个全新会话重新建档（这是幂等设计带来的自愈能力），不会报错，但侧边栏列表在下一次刷新前都不会显示这条新记录，容易让用户以为"删除按钮坏了"。

四、本课总结

  • 后端新增 GET /api/sessions/:id/messages，复用 getHistory 并过滤掉 system 角色
  • 侧边栏列表用 GET /api/sessions 拉真实数据，替换掉本地内存假数组
  • 切换会话按需拉取历史并本地缓存，避免一次性把所有会话消息全部加载
  • 重命名用乐观更新提升响应速度，失败时要显式回滚，不能让界面和数据库状态永久不一致
  • 删除要处理"删的正好是当前激活会话"这个边界情况，否则界面会卡在一个已经不存在的 sessionId 上

思考题

Q1：messagesCache 是"只要缓存过就不再请求"的策略。如果用户在另一个设备上给同一个会话发了新消息，回到这个标签页切换过去，会看到什么问题？有哪几种思路可以解决（不要求写代码，说清楚取舍即可）？

Q2：GET /api/sessions/:id/messages 没有单独判断"会话不存在"就返回 404，而是让 getHistory 查出空数组直接返回 { messages: [] }。这样做和"先查一次 sessions 表确认存在、不存在就 404"相比，前端拿到结果后的处理逻辑会有什么不同？

Q3：重命名用了乐观更新（先改 UI 再发请求），而不是"发请求→等响应→再改 UI"。如果把这个乐观更新策略也套用在"删除会话"上（先从列表里移除，再发 DELETE，失败了再加回来），你觉得合适吗？为什么删除和重命名在"要不要乐观更新"这件事上可能需要不同的判断？
