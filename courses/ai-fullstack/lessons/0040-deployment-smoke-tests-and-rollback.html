第四十课：部署后烟雾测试与回滚判定

目标时长 1 小时 · 难度 ★★★ · 发布工程化 · 生产可用性

本课你会学到：
  • 把健康探针和最小业务检查组合成一套发布后的验收顺序。
  • 区分“能响应”“能接流量”和“关键用户路径可用”三种证据。
  • 在发布前写清继续、停止与回滚条件，避免故障时临场猜测。
  • 用 Render 作为示例，将同一套清单迁移到其他 PaaS 平台。

一、烟雾测试是发布后的最小证据

自动化测试通过只能说明构建产物在测试环境符合预期；部署后，域名、环境变量、数据库连接、反向代理和平台网络仍可能改变实际行为。烟雾测试不是完整回归测试，而是发布后用几分钟回答一个更窄的问题：这个版本是否有足够证据继续保留在生产流量中。

把检查设计得小而固定，才能在每次发布后重复执行并比较结果。先检查不依赖业务数据的端点，再检查一条只读、可撤销或不会产生业务数据的关键路径。不要为了“测得全面”直接发送聊天消息，它会调用 AI、可能计费并写入会话历史。

主阅读资源：Render 官方文档。本课用 Render 的部署记录和日志界面举例，但验收顺序不依赖具体平台。

二、三层验收：存活、就绪、最小业务

三层检查回答的是逐步收窄的问题。前一层失败时，不要继续执行后一层，更不要继续放量；否则得到的只会是噪声，而不是定位线索。

层级检查通过说明失败动作
1GET /health进程与 HTTP 入口仍可响应。停止发布，查看部署是否启动成功。
2GET /ready数据库等关键依赖可用，实例可以接流量。停止放量，核对依赖和平台日志。
3最小只读业务路径关键鉴权、路由与数据读取链路可工作。回滚或保持旧版本，按日志定位。
当前项目没有适合匿名调用的业务读取接口。不要用 POST /api/chat 充当烟雾测试：它需要 JWT、会调用 AI，并可能产生会话数据。若要验证第 3 层，应在受控环境使用专门的合成测试账号和只读请求，同时不在命令历史、截图或课程文件中记录令牌。

三、停止与回滚必须先于发布决定

发布时最危险的不是某一次请求失败，而是团队在失败后才开始讨论“这算不算严重”。把判定写成可观察的条件：探针非 200、响应体不是预期状态、最小业务请求失败、错误日志持续增加，任一项出现就停止继续操作。回滚不是重启或再次部署同一构建，而是恢复到上一个已验证可用的版本。

不要用临时关闭鉴权、跳过数据库检查或打印完整配置来“让烟雾测试通过”。 这些动作改变了被验证的系统，也可能扩大安全问题。保留发布版本、开始时间、检查结果和受控日志链接，才能让回滚决定可复盘。

四、动手实践

1记录本次发布的基线

在 Render 的部署记录中记下提交版本、开始时间和部署状态；为烟雾测试留出 5 到 10 分钟观察窗口。先确认平台显示新部署已启动，再开始 HTTP 检查。平台更换时也保留这四项：版本标识、开始时间、部署日志入口和回滚入口。

2按顺序检查健康端点

将示例域名替换为自己的公开服务地址，但不要在课程笔记中写入任何令牌、密钥或数据库地址。两个请求均不触发 AI，也不会写入业务数据。

$baseUrl = 'https://your-service.example'

Invoke-WebRequest "$baseUrl/health" | Select-Object StatusCode, Content
Invoke-WebRequest "$baseUrl/ready" | Select-Object StatusCode, Content

期望依次看到 200 与 {"status":"ok"}，然后是 200 与 {"status":"ready"}。任一个不符合时停止，不要继续执行下一层。

3选择无副作用的最小业务检查

业务检查必须与真正用户路径相关，但不能制造聊天消息、外部 AI 调用或不可撤销的数据。对于当前项目，先把第 1、2 层作为发布门槛；只有在准备好合成账号、只读接口和日志脱敏规则后，再把受保护的读取请求加入第 3 层。检查后只记录状态码、版本和时间，不记录 Authorization 头或响应中的用户数据。

4执行继续、停止或回滚判定

三层均通过且观察窗口内没有持续错误，才继续保留新版本。若 /health 失败，优先检查启动与路由；若 /ready 失败，检查数据库连接和依赖；若最小业务失败，回滚到最近一次已验证版本并保留日志证据。不要以“刷新后偶尔成功”替代明确的通过条件。

Render 的界面名称可能调整，但部署记录、日志和回滚入口的职责不会变。按照平台文档完成实际回滚操作：https://render.com/docs。

五、验收清单

  1. 已记录发布版本、开始时间、日志入口和观察窗口。
  2. /health 返回 200 与固定的 ok 响应。
  3. /ready 返回 200 与固定的 ready 响应。
  4. 没有用聊天写入接口、AI 调用或真实用户凭据作为烟雾测试。
  5. 停止条件和最近一次可用版本在发布前已知，失败时能直接执行回滚。

六、本课总结

  • 烟雾测试验证的是已部署版本的最小可用性，不替代完整测试套件。
  • 按存活、就绪、最小业务的顺序检查，失败时立即停止向后执行。
  • 回滚条件必须可观察、可复现，并在发布前决定。
  • 发布证据只记录版本、时间、状态和受控日志入口，不泄露凭据或内部诊断信息。
