第二十七课：多会话与用户维度的资源隔离

目标时长 1.5 小时 · 难度 ⭐⭐⭐ · 后端 · 安全

本节课你会学到：
  • 为什么当前 requireAuth 只校验 token 有效性、却没有把 userId 传下去，是一个隐患
  • 为什么 messages 表现在光靠 session_id 查询是不安全的
  • 怎么给 Hono 的 Context 挂上当前登录用户的身份，让业务代码随手可用
  • 怎么给消息表加 user_id 字段，并且 PG / SQLite 两条分支都要改到
  • 为什么"归属校验"必须放进 SQL 查询条件里，而不是查出来之后在代码里 if 判断

一、现在的实现藏着什么问题

第十二课写的 src/middleware/auth.ts 是这样的：

export const requireAuth: MiddlewareHandler = async (c, next) => {
  const authHeader = c.req.header('Authorization')
  if (!authHeader?.startsWith('Bearer ')) {
    return c.json({ error: '未授权，请先登录' }, 401)
  }
  const token = authHeader.slice(7)
  try {
    jwt.verify(token, JWT_SECRET)
    return next()
  } catch {
    return c.json({ error: 'token 无效或已过期，请重新登录' }, 401)
  }
}

它只回答了"这个 token 有没有过期、是不是伪造的"，却把 jwt.verify 解出来的 userId 直接扔掉了，业务代码根本拿不到"这次请求到底是谁发的"。再看 src/db.ts 里的 getHistory：

export async function getHistory(sessionId: string | number) {
  return db.prepare('SELECT role, content FROM messages WHERE session_id = ? ORDER BY id ASC').all(sessionId)
}

只要拿到一个 session_id，任何登录用户都能读到这个会话的全部内容——因为 SQL 里压根没有 user_id 这个条件。这两个问题合在一起，就是一个完整的越权链：

  • 身份信息在鉴权层被丢弃：requireAuth 验证完 token 就不管了，业务代码里想用 userId 却拿不到
  • 数据表没有归属字段：messages 表只有 session_id，不知道这条消息是谁的
  • 越权读取：用户 A 只要能拿到（或猜到）用户 B 的 sessionId，就能通过同一个 /api/chat 接口读到 B 的完整对话历史

二、怎么把身份从鉴权层传到业务层

Hono 的 Context 对象支持 c.set(key, value) / c.get(key)，专门用来在中间件之间传递请求级别的数据。requireAuth 里 jwt.verify 的返回值就是当初 jwt.sign({ userId: user.id }, ...) 签发的 payload，解出来直接 c.set('userId', ...) 存起来，后面的路由处理函数用 c.get('userId') 就能拿到。

这比"每个路由自己重新解一次 JWT"要好：解码逻辑只在 requireAuth 里写一次，业务代码只管拿现成的 userId，符合"鉴权归鉴权、业务归业务"的分层原则。

三、消息表要不要建 sessions 表？

方案做法取舍
给 messages 直接加 user_id每条消息落库时带上当前用户 id改动小，符合现有表结构；但同一个 session 理论上可以被写入不同 user_id（数据一致性靠代码保证，不靠表结构约束）
拆出独立 sessions 表会话归属只在 sessions 表里存一份，messages 通过外键关联结构更严谨，但要多写一次表迁移，对当前只有单表的项目改动偏大

这节课选第一种：直接给 messages 表加 user_id 列，改动范围小、能复用现有的 session_id 分组逻辑。当项目后面需要"会话列表"、"重命名会话标题"这类功能时（下一课会讲），再考虑拆出 sessions 表。

归属校验必须写进 SQL 的 WHERE 条件里，而不是"先查出来，再在 JS 里判断 row.user_id === userId"。后者容易在某次改动中被漏写判断，或者被后来者删掉觉得"多此一举"；写进 SQL 条件里，查不到数据本身就意味着"要么不存在，要么不是你的"，没有中间状态可以被绕过。

四、动手实践

1改造 src/middleware/auth.ts，把 userId 挂到 Context 上 
export const requireAuth: MiddlewareHandler = async (c, next) => {
  const authHeader = c.req.header('Authorization')
  if (!authHeader?.startsWith('Bearer ')) {
    return c.json({ error: '未授权，请先登录' }, 401)
  }
  const token = authHeader.slice(7)
  try {
    const payload = jwt.verify(token, JWT_SECRET) as { userId: number }
    // 把身份挂到 Context 上，后面的路由处理函数用 c.get('userId') 取
    c.set('userId', payload.userId)
    return next()
  } catch {
    return c.json({ error: 'token 无效或已过期，请重新登录' }, 401)
  }
}
如果项目用了 TypeScript 严格模式，c.set/c.get 的键值类型需要通过 Hono 的泛型 Variables 声明才有类型提示，这节课先用类型断言 as { userId: number } 跑通功能，类型声明可以作为课后自选项。
2给 src/db.ts 的 messages 表加 user_id 列 
// PG 分支
await pool!.query(`
  CREATE TABLE IF NOT EXISTS messages (
    id         SERIAL PRIMARY KEY,
    session_id TEXT NOT NULL,
    user_id    INTEGER NOT NULL,
    role       TEXT NOT NULL,
    content    TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  )
`)

// SQLite 分支
db.exec(`
  CREATE TABLE IF NOT EXISTS messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT    NOT NULL,
    user_id    INTEGER NOT NULL,
    role       TEXT    NOT NULL,
    content    TEXT    NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
  )
`)
这是破坏性表结构变更：已有的 chat.db 文件里 messages 表没有 user_id 列，CREATE TABLE IF NOT EXISTS 不会自动加列。本地开发可以直接删掉 chat.db 重建；生产环境要写显式的 ALTER TABLE messages ADD COLUMN user_id ... 迁移脚本，并给已有数据回填一个默认值，不能假装"删库重建"是普适方案。
3改造 insertMsg / getHistory / countSession，让 user_id 贯穿始终 
export async function insertMsg(sessionId: string | number, userId: number, role: string, content: string) {
  if (isPG) {
    await pool!.query(
      'INSERT INTO messages (session_id, user_id, role, content) VALUES ($1, $2, $3, $4)',
      [sessionId, userId, role, content]
    )
  } else {
    db.prepare('INSERT INTO messages (session_id, user_id, role, content) VALUES (?, ?, ?, ?)')
      .run(sessionId, userId, role, content)
  }
}

// 归属校验直接写进 WHERE 条件：session_id 和 user_id 必须同时匹配
export async function getHistory(sessionId: string | number, userId: number) {
  if (isPG) {
    const { rows } = await pool!.query(
      'SELECT role, content FROM messages WHERE session_id = $1 AND user_id = $2 ORDER BY id ASC',
      [sessionId, userId]
    )
    return rows
  }
  return db.prepare('SELECT role, content FROM messages WHERE session_id = ? AND user_id = ? ORDER BY id ASC')
    .all(sessionId, userId)
}

// countSession 同理加 user_id 条件
export async function countSession(sessionId: string | number, userId: number): Promise<number> {
  if (isPG) {
    const { rows } = await pool!.query(
      'SELECT COUNT(*) AS cnt FROM messages WHERE session_id = $1 AND user_id = $2',
      [sessionId, userId]
    )
    return Number(rows[0].cnt)
  }
  const { cnt } = db.prepare('SELECT COUNT(*) AS cnt FROM messages WHERE session_id = ? AND user_id = ?')
    .get(sessionId, userId) as any
  return cnt
}
4改造 src/business/chat.ts，把 userId 从 Context 传进每次数据库调用 
const userId = c.get('userId') as number

// 新 session → 先插入 system prompt
const cnt = await countSession(sessionId, userId)
if (cnt === 0) await insertMsg(sessionId, userId, 'system', SYSTEM_PROMPT)

// 写入 user 消息
await insertMsg(sessionId, userId, 'user', message)

// 读取完整历史（只会读到属于当前用户的记录）
const history = await getHistory(sessionId, userId) as ChatMessage[]
const trimmedHistory = trimHistory(history, MAX_CONTEXT_TOKENS)
注意 cnt === 0 这个判断现在变得更严格了：即使这个 sessionId 之前被别人用过（cnt 在全局意义上不为 0），只要当前用户从没在这个 sessionId 下写过消息，countSession(sessionId, userId) 对他来说就是 0，会重新插入一次 system prompt。这其实是一个天然的副作用：两个用户即使凑巧用了同一个 sessionId 字符串，数据也不会互相污染，因为查询永远带着 user_id 过滤。

五、本课总结

  • requireAuth 验证 token 后，要用 c.set('userId', ...) 把身份传给后续的业务代码，不能验证完就扔掉
  • messages 表加 user_id 列，PG 和 SQLite 两个分支的建表语句都要同步改
  • 归属校验要写进 SQL 的 WHERE 条件（session_id = ? AND user_id = ?），不能查出来再用 JS 判断
  • insertMsg / getHistory / countSession 全部要带上 userId 参数，一个不落
  • 表结构变更是破坏性迁移，本地可以删库重建，生产环境必须写 ALTER TABLE 脚本并处理存量数据

思考题

Q1：如果 getHistory 里的归属校验写成"先按 session_id 查出全部记录，再在 JS 里用 filter 过滤 user_id"，而不是写进 SQL 的 WHERE 条件，会有什么隐患？

Q2：requireAuth 里为什么要用 c.set 传递 userId，而不是让每个路由处理函数自己重新调用一次 jwt.verify？

Q3：给 messages 表新增 user_id NOT NULL 列后，如果生产环境的表里已经有旧数据，直接执行 ALTER TABLE messages ADD COLUMN user_id INTEGER NOT NULL 会发生什么？更稳妥的迁移步骤是什么？
