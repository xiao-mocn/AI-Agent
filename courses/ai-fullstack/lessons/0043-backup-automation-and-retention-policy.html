第四十三课：备份自动化与保留策略

目标时长 1 小时 · 难度 ★★☆ · 数据可靠性 · 可重复演练

本课你会学到：
  • 区分备份脚本、调度器、保留策略与恢复验证各自解决的问题。
  • 使用可排序的时间戳命名，明确保留最新备份的选择规则。
  • 把“只保留两份”和可接受的数据丢失窗口 RPO 联系起来。
  • 在临时目录中验证：保留后的备份仍然可以恢复虚构数据。

一、自动化不等于“写了一条复制命令”

备份流程至少有四个角色：备份动作创建副本，调度器按频率触发动作，保留策略决定哪些历史副本留下，恢复验证证明留下的副本真的能用。它们彼此相关，但不能互相替代。

例如，文件名中有时间戳并不会让任务每天自动运行；一个计划任务持续运行也不代表旧副本会按规则清理；只留下两份文件更不能证明它们可被数据库打开。把这些概念分开，才能在出现故障时准确知道缺少的是哪一环证据。

主阅读资源：SQLite 官方文档。本课用 SQLite 的单文件特性构造最小演练，但真实托管数据库必须按平台提供的备份、导出、保留与恢复能力单独核对。

二、命名、保留数量与 RPO

概念本课的最小做法不能证明什么
命名规则backup-YYYY-MM-DDTHHmmssZ.db，按文件名即可排序。不能证明备份任务会准时运行。
保留策略对排序后的四份副本，仅保留最新两份。不能证明两份副本都能恢复。
RPO用“最多可丢失多久的数据”反推备份间隔。不能凭“保留两份”直接得出丢失窗口。
恢复验证从保留副本复制出恢复副本，再以只读查询断言虚构记录。不能证明 Render 托管数据库的恢复能力。

如果业务最多允许丢失 1 小时数据，备份间隔通常不能大于 1 小时；若备份失败，还需要能发现失败并采取行动。保留数量还要结合间隔理解：每小时一份、保留两份只覆盖约两小时的历史窗口，而不是“永久安全”。

本课不是生产备份方案。严禁读取、复制、修改或删除 ai-backend/chat.db；严禁连接 Render、线上服务或任何托管数据库；不要读取环境变量、凭据或真实业务数据。所有练习仅使用本次命令创建的临时目录和虚构记录。

三、动手实践

1先锁定演练边界

命令使用 fs.mkdtempSync 在系统临时目录创建唯一根目录。源库、四份备份、恢复副本都在这个根目录内；清理动作只调用 fs.rmSync 删除这个函数刚刚返回的根目录。它不接受用户路径，也不扫描项目目录。

2创建确定性的虚构源库

演练创建表 drill_records，只写入 id=1、label=backup-retention-drill。这不是业务数据，而是恢复成功时必须查询到的断言。四个固定时间戳使排序和保留结果可重复，不依赖执行时钟。

3生成四份备份，保留最新两份并恢复验证

从 ai-backend 目录运行以下命令。它先创建四份副本，按名称排序后只保留最后两份，再从最新保留副本创建独立恢复副本并以只读方式查询。无论成功还是失败，finally 都只清理本次创建的临时根目录。

node -e "const fs=require('fs'),os=require('os'),path=require('path'),Database=require('better-sqlite3'); const dir=fs.mkdtempSync(path.join(os.tmpdir(),'ai-agent-backup-')); try { const source=path.join(dir,'source.db'); const db=new Database(source); db.exec('CREATE TABLE drill_records (id INTEGER PRIMARY KEY, label TEXT NOT NULL)'); db.prepare('INSERT INTO drill_records (label) VALUES (?)').run('backup-retention-drill'); db.close(); const names=['backup-2026-07-26T080000Z.db','backup-2026-07-26T090000Z.db','backup-2026-07-26T100000Z.db','backup-2026-07-26T110000Z.db']; for (const name of names) fs.copyFileSync(source,path.join(dir,name)); const backups=fs.readdirSync(dir).filter(name=>name.startsWith('backup-')&&name.endsWith('.db')).sort(); const kept=backups.slice(-2); for (const name of backups.slice(0,-2)) fs.unlinkSync(path.join(dir,name)); const remaining=fs.readdirSync(dir).filter(name=>name.startsWith('backup-')&&name.endsWith('.db')).sort(); if (remaining.length!==2 || remaining.join('|')!==kept.join('|')) throw new Error('retention verification failed'); const restored=path.join(dir,'restored.db'); fs.copyFileSync(path.join(dir,kept[1]),restored); const check=new Database(restored,{readonly:true}); const row=check.prepare('SELECT id, label FROM drill_records').get(); check.close(); if (!row || row.id!==1 || row.label!=='backup-retention-drill') throw new Error('restore verification failed'); console.log(JSON.stringify({result:'retained-and-restored',kept,record:row})); } finally { fs.rmSync(dir,{recursive:true,force:true}); }"

成功标准必须同时满足：保留的文件恰好是 backup-2026-07-26T100000Z.db 与 backup-2026-07-26T110000Z.db，且恢复副本查询到 id=1、label=backup-retention-drill。只看到两个文件仍不足以证明恢复有效。

4记录可复核的非敏感证据

将目标、保留结果、恢复查询结果、未触碰边界和限制记录到 本次备份保留演练记录。不要写入临时绝对路径、连接字符串、密码、令牌或真实数据。对 Render 而言，仍需在确认实际套餐能力后，以它支持的隔离恢复流程另行演练。

四、验收清单

  1. 演练只创建并清理系统临时目录中的虚构 SQLite 文件，没有触碰项目或线上数据库。
  2. 排序与清理后只保留两份指定的最新备份，而不是依赖肉眼判断文件数量。
  3. 恢复副本以只读方式查询到预期虚构记录，证明保留策略后的副本仍可打开。
  4. 演练记录写明了结果、边界和限制，且不含临时绝对路径或凭据。
  5. 能够说明：时间戳命名不是调度器，本地 SQLite 演练不是 Render 数据库的恢复验收。

五、本课总结

  • 备份频率由可接受的数据丢失窗口 RPO 驱动，而不是由文件名决定。
  • 保留策略限制历史副本数量和存储增长，必须明确排序规则与保留数量。
  • 恢复验证要打开保留后的副本并查询确定性数据，不能停留在文件存在。
  • 临时 SQLite 演练建立了可重复的方法，但不证明 Render 或其他托管数据库已有备份能力。
