第三十七课：配置变更管理与部署前检查

目标时长 1 小时 · 难度 ★★★ · 工程化 · 发布可靠性

本课你会学到：
  • 把配置 Schema 转化为团队可审查的运行时配置清单。
  • 区分可提交的示例文件和绝不能提交的真实密钥。
  • 在启动服务前执行独立配置检查，缩短部署失败的反馈时间。
  • 用固定的发布前顺序验证配置、类型与测试。

一、配置不仅是代码问题

第 36 课让应用能拒绝无效配置，但一次部署是否成功还取决于配置从哪里来、谁修改过、是否与代码版本一致。Schema 是机器可执行的契约；示例文件和发布检查则把这份契约交给开发、运维和 CI 使用。没有这些外围约束时，团队仍可能在部署页面漏填新变量，或把旧变量留在环境里却以为它仍有效。

产物是否提交 Git作用
configSchema.ts是定义程序接受的配置与类型。
.env.example是列出键名和非敏感示例，不含真实值。
.env / 平台密钥否保存实际凭据，只由本机或部署平台注入。
部署前检查命令是让 CI 或人工发布在监听端口前发现配置错误。
示例文件不是密钥备份。 即使是测试或过期的 API Key、数据库 URL、JWT 密钥也不要写进 .env.example。示例的价值在于键名、格式和说明，而不是可直接运行的凭据。

二、把配置变更当作接口变更

新增、删除或改变环境变量规则时，应同时更新 Schema、示例文件和部署平台的变量清单。这样代码审查能回答三个问题：新配置为什么需要、哪些环境必须提供、如何在发布前验证。变量名、默认值和是否敏感要在同一次变更中审查，避免应用代码与部署说明逐渐漂移。

本项目的 parseConfig 是纯函数，因此发布检查与单元测试可以复用完全相同的验证规则，而不是各写一套 if 判断。

三、动手实践

1创建无密钥的配置清单

在 ai-backend/.env.example 中列出当前 Schema 中的键。必填密钥保留空值；可安全默认的键给出示例。每新增一个 Schema 字段，都要同步审查这里。

NODE_ENV=production
PORT=3000
FRONTEND_URL=https://your-frontend.example.com
JWT_SECRET=
DEEPSEEK_API_KEY=
DATABASE_URL=
DB_PATH=chat.db
LOG_LEVEL=info
当前 DATABASE_URL 是可选项，因为项目可回退到 SQLite；不要在示例中制造一个假的生产数据库地址。生产环境若使用 PostgreSQL，部署平台必须显式提供它。
2增加独立配置检查命令

创建 scripts/check-config.ts。它只加载并验证配置，不启动 HTTP 服务、队列或 WebSocket。校验失败时进程应以非零状态结束；成功时只打印非敏感的环境名称与端口。

import 'dotenv/config'
import { config } from '../src/utils/config'

console.info(
  `[config-check] ${config.NODE_ENV} configuration is valid on port ${config.PORT}`,
)

然后在 package.json 的 scripts 中加入：

"check:config": "tsx scripts/check-config.ts"
3建立发布前固定顺序

本地发布或 CI 都按同一顺序执行。先验证外部输入，再验证代码质量，最后才部署；不要让部署成功与否依赖“启动后再看日志”。

Set-Location E:\project\AI-Agent\ai-backend
npm run check:config
npx tsc --noEmit
npm test

在部署平台中，用该平台的生产变量执行同一条 npm run check:config。若失败，读取键名和格式错误即可修复，绝不把平台变量完整打印到日志。

4用变更清单做一次审查

假设要新增 MAX_CONTEXT_TOKENS。在提交前依次确认：Schema 是否限定为合理正整数、.env.example 是否说明默认含义、测试是否覆盖非法值、部署平台是否需要显式设置。只有这四项都回答清楚，配置变更才算完成。

四、发布前检查清单

  1. Schema、.env.example 和部署平台变量名是否一致。
  2. 真实密钥是否仅存在于本机安全存储或部署平台，而不在 Git diff 中。
  3. npm run check:config 是否在服务启动前成功。
  4. 类型检查和测试是否在同一代码版本上通过。
  5. 配置失败日志是否仅给出键名与格式问题，不包含值。

五、本课总结

  • 配置 Schema 解决“程序接受什么”，示例文件解决“部署者需要准备什么”。
  • 示例文件可以提交，但只能包含键名、格式和非敏感示例。
  • 独立配置检查把部署失败提前到发布动作之前。
  • 配置变更应与接口变更一样被审查、测试和记录。
