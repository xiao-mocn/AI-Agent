第五十课：Repository 边界与内存数据源

预计 75–100 分钟 · 基于第 49 课已验证的 Service 与错误契约

第 49 课让 Service 不再关心 HTTP。现在还有一个问题：Service 要从哪里拿版本数据？若它自己保存 Map、读取配置、以后又直接写 SQL，它仍会变成难替换的“大杂烩”。这一课先建立 Repository 边界，再用内存实现模拟数据源。

本课胜利点

  • 能用一句话解释 Repository：它是业务层获取与保存数据的边界，不等于数据库。
  • 定义 ReleaseRepository 接口，并用内存 Map 实现它。
  • 让 VersionService 只依赖接口；找不到数据时仍表达为 ReleaseNotFoundException。
  • 写一个不启动 Spring 的 Service 单元测试，分别锁定“找到”和“找不到”的业务行为。

0. 先分清：Repository 不是数据库

Repository：数据边界

它向业务层提供“按什么条件取到什么数据”的能力。今天的数据在 Map，下一课可换成数据库；Service 的调用方式保持稳定。

数据库：一种实现细节

MySQL、PostgreSQL、H2 都可能成为 Repository 背后的存储方式。它们不是本课要学习的重点。

Service：业务解释者

Repository 返回空结果时，Service 决定这代表“发布标签不存在”，然后抛出业务异常。

Controller：HTTP 翻译员

它继续调用 Service；无论后面是内存 Map 还是 JPA，它的 URL、状态码和 JSON 契约都不需要改变。

前端类比：Repository 类似你在 Vue 项目中封装的 API client / 数据访问模块。页面或 composable 只调用 getRelease(label)，不应知道数据是本地 mock、HTTP 请求还是 IndexedDB。

1. 先画边界，而不是先写 Map

脱稿练习

2. 第一步：先声明业务需要的数据能力

1

新建 ReleaseRepository.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/ReleaseRepository.java

package com.example.ai.java_backend.version;

import java.util.Optional;

public interface ReleaseRepository {
  Optional<VersionResponse> findByReleaseLabel(String releaseLabel);
}
Optional 是什么？它明确告诉调用者：“这里可能没有结果。”比起返回 null，调用代码必须选择如何处理空结果，少一次忘记判空的机会。
为什么接口没有 @Repository？接口只描述能力；真正被 Spring 创建的是下一步的实现类。以后换成 JPA 实现时，接口和使用它的 Service 可以不变。

3. 第二步：用内存 Map 模拟一个数据源

2

新建 InMemoryReleaseRepository.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/InMemoryReleaseRepository.java

package com.example.ai.java_backend.version;

import java.util.Map;
import java.util.Optional;
import org.springframework.stereotype.Repository;

@Repository
public class InMemoryReleaseRepository implements ReleaseRepository {
  private final Map<String, VersionResponse> versions = Map.of(
      "local", new VersionResponse("1.0.1"));

  @Override
  public Optional<VersionResponse> findByReleaseLabel(String releaseLabel) {
    return Optional.ofNullable(versions.get(releaseLabel));
  }
}
@Repository 在这里做什么？它告诉 Spring 这是一个数据访问组件，启动时创建并管理这个对象。这里用 Map 只是最小可运行实现，不代表生产环境要把业务数据放在内存中。
Map.of 为什么合适？本课数据固定且只读。它能让你专注于边界，而不提前引入保存、删除、事务或数据库连接。

4. 第三步：让 Service 只解释业务结果

3

替换 VersionService.java

路径：java-backend/src/main/java/com/example/ai/java_backend/version/VersionService.java

package com.example.ai.java_backend.version;

import org.springframework.stereotype.Service;

@Service
public class VersionService {
  private final ReleaseRepository releaseRepository;

  public VersionService(ReleaseRepository releaseRepository) {
    this.releaseRepository = releaseRepository;
  }

  public VersionResponse currentVersion() {
    return findForReleaseLabel("local");
  }

  public VersionResponse findForReleaseLabel(String releaseLabel) {
    return releaseRepository.findByReleaseLabel(releaseLabel)
        .orElseThrow(() -> new ReleaseNotFoundException(releaseLabel));
  }
}
这一层做什么不在这里做什么
把空查询结果翻译为“发布标签不存在”的业务异常。不读 Map，不写 SQL，不返回 HTTP 404。
依赖 ReleaseRepository 接口。不依赖 InMemoryReleaseRepository 这个具体类。

5. 第四步：单独测试 Service 的业务解释

4

新建 VersionServiceTest.java

路径：java-backend/src/test/java/com/example/ai/java_backend/version/VersionServiceTest.java

package com.example.ai.java_backend.version;

import java.util.Optional;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.BDDMockito.given;

@ExtendWith(MockitoExtension.class)
class VersionServiceTest {
  @Mock
  ReleaseRepository releaseRepository;

  VersionService versionService;

  @BeforeEach
  void setUp() {
    versionService = new VersionService(releaseRepository);
  }

  @Test
  void returnsVersionProvidedByRepository() {
    given(releaseRepository.findByReleaseLabel("local"))
        .willReturn(Optional.of(new VersionResponse("1.0.1")));

    assertThat(versionService.findForReleaseLabel("local").version())
        .isEqualTo("1.0.1");
  }

  @Test
  void throwsBusinessExceptionWhenRepositoryHasNoRelease() {
    given(releaseRepository.findByReleaseLabel("missing"))
        .willReturn(Optional.empty());

    assertThatThrownBy(() -> versionService.findForReleaseLabel("missing"))
        .isInstanceOf(ReleaseNotFoundException.class)
        .hasMessage("找不到发布标签：missing");
  }
}
为什么这里不启动 Spring？这个测试只验证 Service 的业务规则。我们手动把假 Repository 传给构造方法，运行更快，也能准确定位失败是在业务解释而不是 Web 或配置层。

7. 易错点与变式练习

现象优先检查原因
Spring 启动时找不到 ReleaseRepository实现类是否有 @Repository，且在启动类根包下接口本身不能被实例化，Spring 需要一个可管理的实现类。
找不到标签变成 500orElseThrow 是否抛出 ReleaseNotFoundException异常类型必须与第 49 课的全局处理器匹配。
Service 里出现 MapMap 是否移动到内存 RepositoryService 会重新同时承担业务和数据访问两种职责。
变式练习：在 versions 中增加 "staging", new VersionResponse("1.1.0-rc1")。不改 Controller、不改 Service，预测 GET /versions/staging 的状态码与 JSON。完成后问我“为什么这次只改一个类？”

完成标准

  • 能说出 Repository 是“数据边界”，而不是“数据库同义词”。
  • ReleaseRepository 只声明查询能力，内存实现负责 Map 查询。
  • VersionService 通过接口查询并把空结果转成业务异常。
  • 新增的 Service 测试覆盖找到与找不到两种结果。
  • .\mvnw.cmd test 通过，三个 HTTP 请求的外部契约保持稳定。
