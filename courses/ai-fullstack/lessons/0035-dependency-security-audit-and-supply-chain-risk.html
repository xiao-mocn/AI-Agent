第三十五课：依赖安全审计与供应链风险

目标时长 1 小时 · 难度 ★★★ · 工程化 · 依赖安全

本节课你会学到：
  • 如何用 npm audit 识别直接与间接依赖中的已知漏洞
  • 如何判断升级、替换、暂缓修复三种处置方式
  • 如何在 CI 中增加依赖审计而不让低价值告警阻塞开发
  • 为什么锁文件是供应链可复现性的一部分

一、你的代码安全，不等于应用安全

应用依赖的 Web 框架、数据库驱动、测试工具都会带来供应链风险。npm audit 把安装树中的包版本与已知漏洞公告匹配，告诉你风险位于哪个依赖路径；它是排查入口，不是自动升级按钮。

结果含义首选动作
直接依赖可升级项目明确声明了受影响包阅读变更并升级后测试
间接依赖可升级由上游包引入升级上游包或等待其发布
无修复版本漏洞仍未解决或路径不受影响评估可达性并记录风险
不要直接执行 npm audit fix --force。 它可能跨主版本升级核心依赖，造成 API 变化或锁文件大范围漂移。先理解依赖路径和兼容性，再进行最小升级。

二、审计结果需要上下文

严重等级不是唯一决策依据。还要问：漏洞代码在本项目是否可达？是否暴露给外部请求？补丁是否包含破坏性变更？对于 AI 后端，HTTP 解析、认证、数据库驱动和生产依赖比纯开发期工具更值得优先处理。

审计没有发现漏洞，不代表依赖绝对安全；它只覆盖已有公开公告。固定锁文件、少装依赖、定期更新和代码审查共同降低供应链风险。

三、动手实践

1查看当前审计报告

在后端目录执行审计，先保存终端摘要。不要立即改动依赖；先区分生产依赖和开发依赖，并记录每条高危路径由谁引入。

Set-Location E:\project\AI-Agent\ai-backend
npm audit
2用依赖树验证一条风险路径

选择报告中的一个包，用 npm ls 确认它来自哪个直接依赖。若上游升级可解决问题，先阅读 release notes，并在单独提交中更新 package.json 与 package-lock.json。

npm ls <package-name>
npm outdated
锁文件必须和 package.json 一起提交。CI 使用 npm ci，它依赖这两份文件来重现你本地验证过的安装树。
3把审计加入 CI

在依赖安装后增加审计步骤。起步阶段先使用 --omit=dev 聚焦生产依赖，并以 --audit-level=high 阻止高危与严重漏洞；不要把所有低危告警都变成发布阻塞器。

- name: 审计生产依赖
  run: npm audit --omit=dev --audit-level=high
4处理失败而不是绕过失败

CI 审计失败后，先定位依赖路径并评估实际可达性。能安全升级就更新并运行类型检查、测试和 Docker 构建；不能立即修复时，记录原因、影响范围和复查日期。不要把 npm audit 静默替换成 || true。

四、提交前检查

  1. 依赖升级是否只包含必要包，而非整棵树的无关刷新？
  2. package.json 和 package-lock.json 是否同步？
  3. 普通测试、覆盖率测试和类型检查是否都通过？
  4. CI 是否只对高危生产依赖设置阻断，并保留可解释的处理记录？

五、本课总结

  • 审计报告指出已知漏洞路径，风险判断仍需要项目上下文。
  • 最小依赖升级与完整验证，比强制自动修复更可靠。
  • 锁文件让本地、CI 与生产获得同一份依赖树。
  • CI 安全门槛应优先阻止高危生产依赖风险。
