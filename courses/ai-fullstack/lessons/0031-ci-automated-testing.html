第三十一课：让 CI 自动跑 API 测试

目标时长 1 小时 · 难度 ⭐⭐ · 工程化 · CI

本节课你会学到：
  • 为什么本地跑过测试还不够，测试要成为每次提交都经过的门禁
  • 读懂现有 GitHub Actions 的触发条件、工作目录和执行顺序
  • 把 npm test 接入现有 CI，并理解为什么它不需要 DeepSeek 密钥
  • 从 Actions 日志判断安装、类型检查、测试或 Docker 构建在哪一步失败

一、CI 解决的是“会不会忘记跑”

第 30 课的 npm test 已经能在本地拦住会话越权回归，但它仍依赖你每次改代码都记得执行。持续集成会在每次 push 和 Pull Request 时，使用一台干净的 Linux 机器重新安装依赖、检查类型、运行测试。

只留在本地的测试：最容易在“这次只是改一行”的时候被跳过。权限校验这类低频分支，恰恰需要每次都被重复验证。

二、现有工作流已经准备好了

根目录的 .github/workflows/ci.yml 已在向 main push 或创建 PR 时运行。它进入 ai-backend 目录，依次执行 npm ci、TypeScript 类型检查和 Docker 构建。

步骤回答的问题失败时先看哪里
npm ci锁定版本能否在干净环境安装？package-lock 与 package.json
类型检查TypeScript 能理解所有调用吗？日志中的文件、行号、类型
npm test行为和权限边界仍成立吗？失败用例的期望值和实际值
Docker 构建生产镜像能构建吗？Dockerfile 与构建日志
npm ci 严格按照 lock 文件安装。它能让 CI 复现本地验证过的依赖树；lock 文件和 package.json 不一致时会直接失败，而不是悄悄替你换版本。

三、为什么 CI 不需要 DeepSeek Key

第 30 课的测试用 Vitest Mock 替换了外部 AI Client。/api/chat 仍走真实路由、鉴权和 SQLite 数据库，但不会请求 DeepSeek，因此 CI 不依赖网络、额度或第三方服务状态。

不要把真实 DEEPSEEK_API_KEY 写进 workflow 或仓库。即使使用 GitHub Secrets，真实 API 调用也会让普通回归测试变慢、付费且不稳定。真实模型验证应是单独、受控的集成测试。

四、动手实践

1确认本地基线

先在后端目录运行与 CI 完全相同的测试命令：

Set-Location E:\project\AI-Agent\ai-backend
npm test

预期看到 Test Files 1 passed 和 Tests 2 passed。本地失败时先在本地修复，不要等推到 GitHub 才开始猜。

2加入测试步骤

在 .github/workflows/ci.yml 的“类型检查”后、Docker 构建前加入：

- name: 运行 API 自动化测试
  run: npm test

工作流已有 working-directory: ai-backend，不需要额外 cd。测试先于 Docker 构建执行，能在更快、更便宜的阶段尽早失败。

3提交并观察 Actions

本地测试通过后，提交 workflow 改动并推送。到 GitHub 仓库的 Actions 标签展开“运行 API 自动化测试”，确认 Vitest 的通过摘要。功能分支创建 PR 也会触发这条检查，这就是合并前门禁。

4练习读失败日志

可以暂时把一个 toBe(404) 改成 toBe(200)，在本地运行 npm test 观察失败用例、期望值和实际状态码。练习结束后立即恢复正确断言并确认重新通过；不要提交故意失败的测试。

五、CI 失败时的排查顺序

  1. 先找失败的步骤名称，不要只看整个 job 的红色图标。
  2. npm ci 失败时，检查依赖改动是否连同 lock 文件提交。
  3. 类型检查失败时，在本地运行 npx tsc --noEmit，按日志文件和行号复现。
  4. 测试失败时，运行同一条 npm test，比较断言的预期与实际值。
  5. 前三步都通过而 Docker 失败时，才集中查看镜像构建环境。
不要用“删掉 CI 中的测试步骤”来处理红灯。红灯说明干净环境与代码契约出现差异；正确动作是定位失败层级、在本地复现、修复后让 CI 重新变绿。

六、本课总结

  • CI 把“记得跑测试”变成每次提交都会执行的自动规则
  • npm ci 保证依赖安装可复现，npm test 验证行为没有回归
  • Mock 外部 AI 调用让测试无需密钥，适合在 GitHub Actions 中稳定运行
  • 从失败步骤开始，按安装、类型、测试、Docker 的顺序缩小范围

思考题

Q1：为什么建议把 npm test 放在 Docker 构建前？如果 Docker 构建先跑，会造成什么实际成本？

Q2：本地 npm test 通过、GitHub Actions 却在 npm ci 失败时，你会先检查哪些文件和差异？为什么不应该直接改 CI 的安装命令？

Q3：当前测试 Mock 了 DeepSeek。如果以后要确认真实 DeepSeek API 仍可用，为什么不应把这类检查直接加入每次 push 的 CI？你会怎样设计它？
