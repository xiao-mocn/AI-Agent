第二十八课：对话列表与会话生命周期管理

目标时长 1.5 小时 · 难度 ⭐⭐⭐ · 后端 · 数据建模

本节课你会学到：
  • 为什么光靠 messages.session_id 分组，撑不起"查看我的所有会话"这个功能
  • 怎么设计一张独立的 sessions 表，把"会话"本身变成一等公民
  • 怎么在用户第一次发消息时自动创建一条 sessions 记录，并生成默认标题
  • 怎么实现 GET /api/sessions（列表）、PATCH /api/sessions/:id（改名）、DELETE /api/sessions/:id（删除）三个接口
  • 为什么"删除会话"必须同时清理 messages 表，而不是留下一堆孤儿数据

一、现在的 session_id 撑不起"会话列表"

第二十七课解决了"同一个 session_id 不会被两个用户混用"的问题，但 session_id 本身还只是前端随手生成的一个字符串（比如一个 UUID），后端从来没有为它单独建过档：不知道这个会话叫什么名字、 是什么时候创建的、当前用户名下一共有几个会话。

这意味着如果产品要做一个类似 ChatGPT 左侧边栏的"历史会话列表"，现在的表结构完全给不出答案—— SELECT DISTINCT session_id FROM messages WHERE user_id = ? 勉强能凑出一个 ID 列表， 但凑不出标题、也没法优雅地处理"删除会话"（删除后 DISTINCT 查询会不会重新捡回残留数据，取决于你有没有把 messages 也一起清干净）。

  • 没有标题：会话列表只能显示一串 session_id，用户体验很差
  • 没有创建/更新时间：列表没法按"最近使用"排序
  • 删除语义不清晰：到底是"这个 session_id 以后不能再用"，还是"把这些消息删了但 session_id 还能复用"，没有一个表能给出权威答案

二、拆出 sessions 表

第二十七课的表格里提过"拆出独立 sessions 表"这个选项，当时因为只需要解决越权问题，选了改动更小的方案。 现在需求变了——"会话列表"、"重命名"、"删除"都是围绕"会话"这个实体的操作，而不是围绕单条消息， 所以这节课把 sessions 表补上，让它成为会话的唯一权威来源，messages 通过 session_id 关联它。 

// PG 分支
await pool!.query(`
  CREATE TABLE IF NOT EXISTS sessions (
    id         TEXT PRIMARY KEY,
    user_id    INTEGER NOT NULL,
    title      TEXT NOT NULL DEFAULT '新会话',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  )
`)

// SQLite 分支
db.exec(`
  CREATE TABLE IF NOT EXISTS sessions (
    id         TEXT PRIMARY KEY,
    user_id    INTEGER NOT NULL,
    title      TEXT    NOT NULL DEFAULT '新会话',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
  )
`)
id 直接复用前端生成的 session_id 字符串做主键，不额外引入自增 ID——这样 messages.session_id 不用改类型，两张表靠同一个值天然对齐。
方案做法取舍
加外键约束messages.session_id 显式 REFERENCES sessions(id)数据库帮你保证一致性，删除 sessions 时可以用 ON DELETE CASCADE 自动清消息；但要求 sessions 记录必须先于 messages 存在，插入顺序不能乱
不加外键，应用层保证两张表各自独立，靠业务代码保证先建 session 再写消息灵活，但一致性完全靠代码纪律，容易出现孤儿消息

这节课选加外键 + ON DELETE CASCADE：这是数据库最擅长的事情——"父记录没了，子记录自动清理"这种一致性规则，交给数据库比交给业务代码更可靠。

ON DELETE CASCADE 意味着一旦执行 DELETE FROM sessions WHERE id = ?，这个会话下的所有消息会被无提示、不可逆地一起删掉。接口层必须在删除前做好归属校验（WHERE id = ? AND user_id = ?），确保用户只能删自己的会话——级联删除会把"权限校验疏漏"的后果放得更大，因为一次误删清空的是一整条对话历史，而不是一条消息。

三、动手实践

1在 src/db.ts 里建 sessions 表，并给 messages 补外键 
// messages 表的 session_id 列，改成带外键约束
// PG：
session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,

// SQLite：建表时加，并且需要 PRAGMA foreign_keys = ON 才会生效
db.pragma('foreign_keys = ON')
和第二十七课一样，这也是破坏性表结构变更：本地直接删 chat.db 重建；sessions 表要先于 messages 建出来，建表顺序不能颠倒（外键引用的表必须已存在）。
2新增 createSessionIfNotExists / listSessions / renameSession / deleteSession 
// 首次发消息时自动建档，标题取消息内容前 20 个字符
export async function createSessionIfNotExists(sessionId: string, userId: number, firstMessage: string) {
  const title = firstMessage.slice(0, 20) || '新会话'
  if (isPG) {
    await pool!.query(
      'INSERT INTO sessions (id, user_id, title) VALUES ($1, $2, $3) ON CONFLICT (id) DO NOTHING',
      [sessionId, userId, title]
    )
  } else {
    db.prepare('INSERT OR IGNORE INTO sessions (id, user_id, title) VALUES (?, ?, ?)')
      .run(sessionId, userId, title)
  }
}

// 归属校验同样写进 WHERE：只能列出自己的会话
export async function listSessions(userId: number) {
  if (isPG) {
    const { rows } = await pool!.query(
      'SELECT id, title, updated_at FROM sessions WHERE user_id = $1 ORDER BY updated_at DESC',
      [userId]
    )
    return rows
  }
  return db.prepare('SELECT id, title, updated_at FROM sessions WHERE user_id = ? ORDER BY updated_at DESC')
    .all(userId)
}

// 改名：WHERE 里同时带 id 和 user_id，查不到就是"不存在或不是你的"
export async function renameSession(sessionId: string, userId: number, title: string): Promise<boolean> {
  if (isPG) {
    const res = await pool!.query(
      'UPDATE sessions SET title = $1, updated_at = CURRENT_TIMESTAMP WHERE id = $2 AND user_id = $3',
      [title, sessionId, userId]
    )
    return (res.rowCount ?? 0) > 0
  }
  const info = db.prepare('UPDATE sessions SET title = ?, updated_at = CURRENT_TIMESTAMP WHERE id = ? AND user_id = ?')
    .run(title, sessionId, userId)
  return info.changes > 0
}

// 删除：只删 sessions，messages 靠 ON DELETE CASCADE 自动清理
export async function deleteSession(sessionId: string, userId: number): Promise<boolean> {
  if (isPG) {
    const res = await pool!.query('DELETE FROM sessions WHERE id = $1 AND user_id = $2', [sessionId, userId])
    return (res.rowCount ?? 0) > 0
  }
  const info = db.prepare('DELETE FROM sessions WHERE id = ? AND user_id = ?').run(sessionId, userId)
  return info.changes > 0
}
renameSession/deleteSession 都返回一个 boolean：受影响行数为 0， 路由层就能区分"这个会话本来就不存在或不是你的"，回一个 404，而不是含糊地回 200。
3在 chat.ts 里，写第一条消息前先调用 createSessionIfNotExists 
const userId = c.get('userId') as number

// 会话不存在则建档（幂等，重复调用不会报错也不会覆盖已有标题）
await createSessionIfNotExists(sessionId, userId, message)

const cnt = await countSession(sessionId, userId)
if (cnt === 0) await insertMsg(sessionId, userId, 'system', SYSTEM_PROMPT)
await insertMsg(sessionId, userId, 'user', message)
4新增 src/business/sessions.ts，暴露三个路由 
import { Hono } from 'hono'
import type { AppEnv } from '../types'
import { listSessions, renameSession, deleteSession } from '../db'

export default function SessionRoutes(app: Hono<AppEnv>) {
  app.get('/api/sessions', async (c) => {
    const userId = c.get('userId') as number
    const sessions = await listSessions(userId)
    return c.json({ sessions })
  })

  app.patch('/api/sessions/:id', async (c) => {
    const userId = c.get('userId') as number
    const sessionId = c.req.param('id')
    const { title } = await c.req.json()
    if (!title || typeof title !== 'string') return c.json({ error: 'title 不能为空' }, 400)

    const ok = await renameSession(sessionId, userId, title)
    if (!ok) return c.json({ error: '会话不存在' }, 404)
    return c.json({ ok: true })
  })

  app.delete('/api/sessions/:id', async (c) => {
    const userId = c.get('userId') as number
    const sessionId = c.req.param('id')

    const ok = await deleteSession(sessionId, userId)
    if (!ok) return c.json({ error: '会话不存在' }, 404)
    return c.json({ ok: true })
  })
}
别忘了在 index.ts 里 app.use('/api/*', requireAuth) 之后注册 SessionRoutes(app)——三个接口都依赖 c.get('userId')，必须先经过鉴权中间件。

四、本课总结

  • 新增 sessions 表作为会话的唯一权威来源，messages.session_id 用外键 ON DELETE CASCADE 关联它
  • 用户第一次发消息时，createSessionIfNotExists 自动建档并生成默认标题
  • listSessions/renameSession/deleteSession 全部要求 userId 参数，归属校验写进 SQL 的 WHERE 条件
  • renameSession/deleteSession 返回受影响行数而不是"成功就完事"，路由层据此区分 404 和 200
  • 级联删除是把双刃剑：效率高，但一旦权限校验疏漏，误删的后果会被放大成整条对话历史

思考题

Q1：如果没有 ON DELETE CASCADE，直接执行 DELETE FROM sessions WHERE id = ? AND user_id = ?，会遗留什么问题？如果反过来"先手动删 messages，再删 sessions"，又要注意什么顺序问题？

Q2：renameSession 的 SQL 是 WHERE id = ? AND user_id = ?，如果只写 WHERE id = ?（不校验 user_id），会造成什么后果？只在路由层用 if (session.userId !== userId) 判断、不写进 SQL，是否能达到同样的安全效果？

Q3：用"消息内容前 20 个字符"当默认会话标题，在实际使用中会遇到什么局限（比如用户第一句话很短、或者是一段代码）？如果想用 AI 自动生成更有意义的标题，这个调用应该放在请求的同步路径里，还是异步做？为什么？
