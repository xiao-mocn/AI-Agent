第四十四课：备份失败可见性与恢复运行手册

目标时长 1 小时 · 难度 ★★☆ · 故障响应 · 可复核证据

本课你会学到：
  • 让备份任务同时产生进程退出码与结构化结果事件。
  • 用“最后一次成功备份距今多久”判断数据保护是否逼近 RPO。
  • 区分日志、告警和恢复运行手册各自承担的责任。
  • 编写一份要求隔离恢复、只读验证和证据留存的最小运行手册。

一、无人知道的失败，等于没有备份保障

定时任务按时启动，只能证明调度器发起过执行。要让自动化结果可见，任务至少要给出机器可判断的退出码，并记录包含状态、备份标识、开始时间、结束时间、耗时和稳定错误码的结构化事件。退出码便于调度器判定成功或失败，结构化事件则让人和监控系统知道失败发生在哪一环。

错误信息应帮助定位类别，例如 DESTINATION_UNAVAILABLE，但不应包含数据库连接字符串、令牌、密码或原始业务数据。成功事件同样重要：只有连续记录最近一次真正成功的时间，才能判断保护窗口是否正在变旧。

主阅读资源：Node.js process.exitCode 文档。生产任务还要核对实际调度平台如何保存日志、识别非零退出码和发送通知。

二、单次失败与“备份已经过旧”不是同一个信号

信号回答的问题典型动作
本次退出码非零刚才这次执行是否失败？记录失败，按重试策略处理。
结构化失败事件失败属于哪一类、发生在何时？聚合日志，定位责任边界。
最后成功时间过旧当前数据丢失窗口是否可能超过 RPO？触发告警并进入人工响应。
恢复运行手册收到告警后应该按什么顺序行动？隔离恢复、验证、决策和留证。

一次任务失败后，下一次重试可能很快成功；反过来，即使没有收到失败事件，调度器停止运行也会让备份持续变旧。因此告警不能只盯着失败次数，还要比较当前时间与最后一次成功时间。若 RPO 是 60 分钟，而最后成功备份已经过去 95 分钟，就必须把它视为数据保护风险。

三、运行手册把告警变成可执行顺序

运行手册不是一段笼统的“恢复数据库”说明。它应写明触发条件、责任人、证据入口、停止条件、隔离恢复步骤、验证标准、升级路径和事后记录。每一步都应让临时接手的人知道做什么、根据什么判断，以及何时不能继续。

恢复演练不得直接覆盖生产数据库。先确认影响范围和最近成功备份，在隔离环境恢复，再以只读查询验证结构与确定性数据；涉及生产切换、删除或覆盖时必须单独审批。本课不读取环境变量、凭据、真实数据库或线上日志。

四、动手实践

1模拟成功与失败结果

在 ai-backend 目录依次执行下面两条命令。它们只输出固定的虚构事件，不访问文件、数据库、网络或环境变量。第一条应输出成功 JSON 且退出码为 0；第二条应把失败 JSON 写到标准错误且退出码为 1。

node -e "const mode=process.argv[1]; const event={event:mode==='failure'?'backup.failed':'backup.completed',status:mode==='failure'?'failed':'succeeded',backupId:'backup-drill-2026-07-27T080000Z',startedAt:'2026-07-27T08:00:00Z',finishedAt:'2026-07-27T08:00:03Z',durationMs:3000}; if(mode==='failure'){event.errorCode='DESTINATION_UNAVAILABLE'; console.error(JSON.stringify(event)); process.exitCode=1}else{console.log(JSON.stringify(event))}" success
Write-Output "exit=$LASTEXITCODE"

node -e "const mode=process.argv[1]; const event={event:mode==='failure'?'backup.failed':'backup.completed',status:mode==='failure'?'failed':'succeeded',backupId:'backup-drill-2026-07-27T080000Z',startedAt:'2026-07-27T08:00:00Z',finishedAt:'2026-07-27T08:00:03Z',durationMs:3000}; if(mode==='failure'){event.errorCode='DESTINATION_UNAVAILABLE'; console.error(JSON.stringify(event)); process.exitCode=1}else{console.log(JSON.stringify(event))}" failure
Write-Output "exit=$LASTEXITCODE"
2验证基于 RPO 的过旧告警

下面的固定输入表示最后成功备份距当前时间 95 分钟，而 RPO 为 60 分钟。命令必须输出 backup.stale 事件并返回退出码 1；这证明告警依据是成功备份的新鲜度，而不是是否碰巧收到了某一条失败日志。

node -e "const lastSuccessAt=new Date('2026-07-27T08:00:00Z'),now=new Date('2026-07-27T09:35:00Z'),rpoMinutes=60; const ageMinutes=(now-lastSuccessAt)/60000; const stale=ageMinutes>rpoMinutes; console.log(JSON.stringify({event:stale?'backup.stale':'backup.fresh',lastSuccessAt:lastSuccessAt.toISOString(),ageMinutes,rpoMinutes})); if(stale) process.exitCode=1"
Write-Output "exit=$LASTEXITCODE"

4做一次桌面演练并记录证据

把第二步的固定过旧事件当作告警输入，按运行手册逐项走读：谁先响应、去哪里找最后成功备份、怎样选择隔离目标、用什么只读断言判断恢复有效、什么条件下升级。将本次桌面演练的输入、关键决策、预期证据和未执行的生产动作写入 docs/recovery/2026-07-27-backup-failure-tabletop.md。

五、验收清单

  1. 成功模拟返回退出码 0，失败模拟返回退出码 1，且两者都有可解析的结构化事件。
  2. 过旧检测以最后成功时间和 RPO 为输入，固定样例得到 95 分钟大于 60 分钟的告警。
  3. 失败事件与运行手册不含连接字符串、密码、令牌、真实数据或临时绝对路径。
  4. 运行手册明确要求先隔离恢复和只读验证，生产覆盖或切换必须单独审批。
  5. 桌面演练记录能够让另一位工程师复核触发条件、决策顺序、验证标准和限制。

六、本课总结

  • 退出码让调度器判断结果，结构化事件让监控和工程师理解结果。
  • 最后成功备份的新鲜度比单次失败次数更直接地反映 RPO 风险。
  • 告警只负责叫醒人，运行手册负责约束收到告警后的安全行动顺序。
  • 恢复必须先在隔离环境验证；生产切换是独立的高风险决策。
