第三十课：给后端 API 写自动化测试（Vitest + Supertest）

目标时长 1.5 小时 · 难度 ⭐⭐⭐ · 后端 · 测试

本节课你会学到：
  • 为什么"删别人的会话该 404"这类权限边界，光靠手动点前端几乎测不到，需要自动化测试兜底
  • Vitest 是什么、为什么这个项目选它而不是 Jest，怎么装、怎么跑
  • 用 Supertest 对 Hono 应用发真实 HTTP 请求，链式断言状态码和响应体
  • 为什么要把"构建 app"和"启动服务器"拆成两个文件，测试才能安全地 import app
  • 测试用的数据库要怎么和本地开发用的 chat.db 隔离开

一、手动点前端，为什么撑不住了

这几周攒下来的接口已经不少了：注册、登录、发消息（流式）、拉会话列表、按需拉历史消息、重命名、删除…… 而且第27课之后每个接口都带着 userId 归属校验。上一课改完前端顺手发现 ChatSchema.sessionId 还是四课以前的类型定义，跟实际用的 UUID 对不上——这种"改了 A 处，没注意到 B 处早就假设了别的东西"的回归， 光靠自己手动点一遍界面是很难兜住的。

更麻烦的是权限边界这一类分支：要测出"用户 A 删不掉用户 B 的会话"，你得手动开两个浏览器（或者两个隐私窗口）， 分别注册、登录、拿到两个不同的 sessionId，再故意拿 A 的 token 去删 B 的会话——这种操作成本高、 容易嫌麻烦而跳过，恰恰是最需要被测试覆盖的场景，因为它是安全边界，出问题就是真实的越权漏洞。

如果没有自动化测试网：每次改动都要祈祷"没改坏别的地方"，权限边界这种低频但高危的分支基本没人会每次都手动验证一遍，出问题往往是等用户投诉才发现。

二、为什么选 Vitest

Node.js 生态最常见的测试框架是 Jest，但这个项目从第一课开始就用 tsx 直接跑 TypeScript， 没有走 Babel/webpack 那套编译链路。Vitest 底层用 esbuild/Vite 做转译，天然支持 TypeScript 和 ESM， 配置成本几乎为零；而且它的 API（describe/it/expect）和 Jest 高度兼容， 以后如果换公司用 Jest，学习成本也不会归零。

三、Supertest 怎么对 Hono 应用发请求

Hono 官方推荐的测试方式是直接调用 app.request(path, init)，拿到一个标准的 Response 对象自己解析。 这节课选 Supertest 的原因是它的链式断言 API（.expect(200)、.expect(res => ...)）更贴近 Express/Koa 生态里最常见的写法，换到别的 Node 后端项目也能直接复用这套思路。技术上能接得上，是因为 @hono/node-server 的 serve() 返回的就是一个真正的 node:http Server 实例， Supertest 本来就是包这种对象设计的。

四、要让 app 可测试，得先做一次小拆分

现在 src/index.ts 把"构建 Hono 应用"和"启动服务器"焊在了一起——文件顶层直接 initDB().then(() => serve({ fetch: app.fetch, port: PORT }, ...))，还顺带启动了 scheduler、worker、websocket，注册了优雅关闭的信号监听。 如果测试文件直接 import 这个文件，就会真的连数据库、真的监听端口、真的启动定时任务——这些副作用测试根本不需要， 还会导致测试跑不完（进程被 serve() 挂起）或者端口冲突。

拆分方案：新建 src/app.ts，只做"new Hono() + 注册中间件 + 注册路由 + onError/notFound"， 然后 export default app。src/index.ts 瘦身成启动入口：import app from './app'， 剩下的 initDB()/serve()/优雅关闭逻辑原样留在这里不动。测试文件只 import app.ts， 拿到的是一个"配置好了但没有监听端口"的纯 Hono 实例，交给 Supertest 自己接管监听。

五、测试数据库怎么和开发库隔离

方案做法取舍
SQLite 内存库 :memory:每次 new Database(':memory:') 给一个全新的库速度最快、天然不留文件；但 db.ts 现在是模块级单例（export const db = new Database(...)），每个测试文件各自 import 时如果没控制好加载时机，容易出现"用的不是同一个连接"的问题
每个测试文件一个临时文件路径测试启动前通过 process.env.DB_PATH 指向一个临时 .db 文件，测试结束后删除能直接复用 db.ts 现成的"读 DB_PATH 环境变量"逻辑，不用改一行生产代码；行为也更接近生产环境用的落盘数据库

这节课选临时文件方案：不用改 db.ts 一行代码，只要保证测试文件在 import 应用代码之前把 DB_PATH 环境变量设置好——因为 db.ts 顶层的 new Database(process.env.DB_PATH || 'chat.db') 只在模块第一次被加载时执行一次。

这里有个容易踩的坑：Vitest 默认每个测试文件跑在独立的 worker 里，模块也是独立加载的，所以"在 beforeAll 里设置 process.env.DB_PATH，再动态 import 应用代码"这个顺序不能反——如果测试文件顶部用静态 import 提前加载了 app.ts（从而提前加载了 db.ts），DB_PATH 这时候还没设置，模块已经连上默认的 chat.db 了，之后再改环境变量也没用。

六、动手实践

1安装依赖，加测试脚本 
npm install -D vitest supertest @types/supertest

package.json 里把占位的 test 脚本换掉：

"scripts": {
  "start": "tsx src/index.ts",
  "test": "vitest run"
}
2拆分 src/app.ts / src/index.ts 
// src/app.ts —— 只负责"搭好这个 Hono 应用长什么样"，不做任何启动动作
import { Hono } from 'hono'
import { secureHeaders } from 'hono/secure-headers'
import { cors } from 'hono/cors'
import { requestId } from 'hono/request-id'
// ……原来 index.ts 里 app.use / 路由注册 / onError / notFound 那部分整体搬过来
import type { AppEnv } from './types'

const app = new Hono<AppEnv>()
// app.use(...) / user(app) / ChatMessageRoutes(app) / SessionRoutes(app) / app.onError(...) / app.notFound(...)

export default app
// src/index.ts —— 瘦身后的启动入口
import app from './app'
import { serve } from '@hono/node-server'
// initDB / attachWebSocket / startScheduler / startWorker / 优雅关闭那一整套原样保留

initDB().then(() => {
  const server = serve({ fetch: app.fetch, port: PORT }, (info) => { ... })
  ...
})
这次拆分只是"剪切粘贴 + 改 import"，不改变任何运行时行为——npm start 跑起来应该和拆分前完全一样。
3测试专用的数据库隔离 + 登录辅助函数 
// tests/helpers.ts
import { randomUUID } from 'crypto'
import path from 'path'

// 每个测试文件调用一次，必须在 import app.ts 之前调用
export function useTestDB() {
  process.env.DB_PATH = path.join(__dirname, `test-${randomUUID()}.db`)
}

// 注册 + 登录，返回可以直接拼进 Authorization 头的 token
export async function registerAndLogin(request: any, app: any, username: string) {
  const password = 'Test1234!'
  await request(app).post('/register').send({ username, password })
  const res = await request(app).post('/login').send({ username, password })
  return res.body.token as string
}
useTestDB() 只是设置了环境变量，真正"生效"是在 db.ts 第一次被 import 的时候。所以测试文件里必须先调用它，再用动态 import() 加载 app.ts 和 initDB，不能在文件顶部用静态 import（那样会在 useTestDB() 跑之前就把模块加载完了）。
4正常流程测试：注册 → 登录 → 发消息 → 能在会话列表里看到 
// tests/sessions.test.ts
import { describe, it, expect, beforeAll } from 'vitest'
import request from 'supertest'
import { useTestDB, registerAndLogin } from './helpers'

useTestDB()
let app: any

beforeAll(async () => {
  const { initDB } = await import('../src/db')
  await initDB()
  app = (await import('../src/app')).default
})

describe('会话列表', () => {
  it('发一条消息后，会话应该出现在 GET /api/sessions 里', async () => {
    const token = await registerAndLogin(request, app, 'alice')
    const sessionId = crypto.randomUUID()

    await request(app)
      .post('/api/chat')
      .set('Authorization', `Bearer ${token}`)
      .send({ message: '你好', sessionId })

    const res = await request(app)
      .get('/api/sessions')
      .set('Authorization', `Bearer ${token}`)

    expect(res.status).toBe(200)
    expect(res.body.sessions.some((s: any) => s.id === sessionId)).toBe(true)
  })
})
POST /api/chat 是流式接口，测试里不用管流式细节——只要请求发出去、状态码不是错误，后端就已经把 user 消息和会话记录落库了，紧接着查 GET /api/sessions 能验证到这一点就够了。
5权限边界测试：这才是这节课真正要补的网 
describe('跨用户越权', () => {
  it('用户 B 不能删除用户 A 的会话', async () => {
    const tokenA = await registerAndLogin(request, app, 'sessionOwnerA')
    const tokenB = await registerAndLogin(request, app, 'attackerB')
    const sessionId = crypto.randomUUID()

    await request(app)
      .post('/api/chat')
      .set('Authorization', `Bearer ${tokenA}`)
      .send({ message: '这是 A 的会话', sessionId })

    // B 拿着自己的 token，去删 A 的 sessionId
    const delRes = await request(app)
      .delete(`/api/sessions/${sessionId}`)
      .set('Authorization', `Bearer ${tokenB}`)

    expect(delRes.status).toBe(404) // 而不是 200

    // 确认 A 的会话真的还在
    const listRes = await request(app)
      .get('/api/sessions')
      .set('Authorization', `Bearer ${tokenA}`)
    expect(listRes.body.sessions.some((s: any) => s.id === sessionId)).toBe(true)
  })
})
如果这个测试写完之后跑起来是失败的（delRes.status 实际是 200）， 说明第28课 deleteSession 里 WHERE id = ? AND user_id = ? 这个归属校验被后续某次改动破坏了—— 这正是自动化测试要在这种时候把你拦下来，而不是等上线后被用户发现。

七、本课总结

  • 安装 vitest + supertest，package.json 的 test 脚本改成 vitest run
  • 把 src/index.ts 拆成 src/app.ts（只搭应用）和瘦身后的 src/index.ts（负责 initDB/serve/优雅关闭），测试才能安全 import
  • 测试用 DB_PATH 环境变量指向临时文件，跟本地开发用的 chat.db 完全隔离，必须在 import 应用代码之前设置好
  • Supertest 直接包 Hono 应用（本质是 node:http Server），用链式 .expect() 断言状态码和响应体
  • 正常流程测试之外，权限边界测试（"删别人的会话该 404"）是这节课真正要补上的网——这类分支平时手动点前端几乎不会触发

思考题

Q1：为什么测试要用独立的临时数据库文件，而不是直接复用本地开发用的 chat.db？如果图省事直接跑在 chat.db 上，会出现什么问题？

Q2：这节课把 src/index.ts 拆成了 app.ts + index.ts 两个文件。如果不做这次拆分，直接在测试文件里 import '../src/index' 会发生什么？（提示：想想 initDB().then(() => serve(...)) 和进程生命周期）

Q3：第29课 GET /api/sessions/:id/messages 的设计是"查不到就返回 200 + 空数组"，而不是 404。如果要给这个接口写一个"用户 B 读不到用户 A 的会话消息"的越权测试，断言该写成"状态码是 404"还是"状态码是 200 但 messages 是空数组"？这种设计对写自动化测试的人来说，是更容易还是更容易漏掉这个边界？
