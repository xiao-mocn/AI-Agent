第二十四课：定时任务与后台队列

目标时长 1.5 小时 · 难度 ⭐⭐⭐ · 后端 · 部署

本节课你会学到：
  • 为什么 Node.js 服务里需要定时任务，以及直接写 setInterval 会踩哪些坑
  • 什么是后台队列，以及它怎么避免"慢操作"阻塞主请求
  • 用 node-cron 实现一个每天清理过期消息的定时任务
  • 用内存队列把 AI 调用改成"先接收请求、后台慢慢处理、做完再通知"的模式
  • 定时任务和队列在优雅关闭时要怎么处理

一、为什么需要定时任务和后台队列

你的 AI 聊天应用运行一段时间后，数据库里的消息会越来越多。这些数据里有很多是临时对话，保留太久既浪费存储，也可能带来隐私风险。如果靠人手动清理，迟早会忘。定时任务就是让这类"周期性维护工作"自动化的机制。

后台队列解决的是另一个问题。现在用户发一条消息，后端要立刻调用 DeepSeek API、等它返回、再把结果写回数据库，整个过程中 HTTP 请求一直卡着。如果 AI 响应慢，用户看到的就会是"转圈圈"，严重时还会超时。后台队列的思路是：请求进来后只做两件事——把任务放进队列、立刻返回"已收到"；另一个 worker 在后台慢慢处理任务，做完再通过 WebSocket 或轮询接口把结果推给用户。

这一课我们先在单进程、内存队列的层面理解原理，不引入 Redis、RabbitMQ 这类外部消息队列。等以后服务需要多实例部署时，再把内存队列替换成持久化队列。

二、定时任务的常见陷阱

很多同学第一次写定时任务会用 setInterval：

setInterval(() => {
  cleanupOldMessages()
}, 24 * 60 * 60 * 1000)

这样写有几个隐患：

  • 任务执行时间超过间隔：如果某次清理很慢，下一次会重叠执行，导致资源竞争或重复清理
  • 进程崩溃后没有补偿：服务重启了，就再也不会执行，直到下一次触发点
  • 多实例部署时会重复执行：如果未来水平扩展成两个容器，两个进程都会跑同一份定时任务，容易冲突
  • 优雅关闭时不等待：第二十一课讲过优雅关闭，如果关闭时定时任务正在跑，可能中途被中断，留下半清理状态

node-cron 这类库能帮你解决"重叠执行"的问题（通过锁或下次触发时跳过正在跑的任务），但"多实例重复执行"和"进程补偿"需要依赖外部锁或数据库级调度。这节课我们先聚焦单实例场景，把基础模式做对。

三、后台队列的基本模式

模式说明适用场景
同步处理请求进来直接调用 AI，等返回再响应简单、快速、可容忍延迟的操作
异步队列请求只入队，立刻返回任务 ID；worker 后台处理耗时长、可能失败、需要重试的操作
发布/订阅一个事件被多个消费者并行处理通知、日志、数据同步

我们这节课实现的是第二种：内存异步队列。它的核心结构是三部分：

  1. 队列：保存等待处理的任务
  2. 生产者：HTTP handler 收到请求后把任务塞进去
  3. 消费者 / worker：循环从队列取任务并执行

四、动手实践

1安装 node-cron 和类型定义 
npm install node-cron
npm install --save-dev @types/node-cron
2新增 src/scheduler.ts：每天清理 30 天前的消息 
import cron from 'node-cron'
import { db, isPG } from './db'
import logger from './logger'

let task: cron.ScheduledTask | null = null

export function startScheduler() {
  // 每天凌晨 3 点执行
  task = cron.schedule('0 3 * * *', async () => {
    try {
      const cutoff = new Date()
      cutoff.setDate(cutoff.getDate() - 30)
      const iso = cutoff.toISOString()

      if (isPG) {
        // PG 版本待实现
      } else {
        const result = db.prepare('DELETE FROM messages WHERE created_at < ?').run(iso)
        logger.info({ deleted: result.changes }, '定时清理过期消息完成')
      }
    } catch (err) {
      logger.error(err, '定时清理失败')
    }
  }, {
    scheduled: true,
    timezone: 'Asia/Shanghai',
    // node-cron 默认不会重叠执行，但如果任务执行超过 24 小时仍需额外保护
  })
}

export function stopScheduler() {
  if (task) {
    task.stop()
    task = null
  }
}
这里用了 DELETE 直接删数据。真实生产环境中，通常会先把数据归档或软删除，确认没问题再做物理清理。这节课为了演示核心机制，简化了这一步。
3新增 src/queue.ts：简单的内存任务队列 
import logger from './logger'

type Task = {
  id: string
  type: 'ai-reply'
  sessionId: string | number
  content: string
}

const queue: Task[] = []
let running = false
let activePromise: Promise<void> | null = null

async function processTask(task: Task) {
  // 这里调用 AI 并保存结果
  logger.info({ taskId: task.id }, '开始处理任务')
  // await callAIAndSave(task.sessionId, task.content)
}

async function loop() {
  while (running || queue.length > 0) {
    const task = queue.shift()
    if (!task) {
      await new Promise(resolve => setTimeout(resolve, 100))
      continue
    }
    try {
      await processTask(task)
    } catch (err) {
      logger.error(err, { taskId: task.id }, '任务处理失败')
    }
  }
}

export function startWorker() {
  running = true
  activePromise = loop()
}

export function stopWorker() {
  running = false
}

export function waitForWorker() {
  return activePromise ?? Promise.resolve()
}

export function enqueue(task: Task) {
  queue.push(task)
}
这里的 loop 用 running 标志控制退出，优雅关闭时把 running 设成 false，worker 会把手头任务跑完再退出。
4在 src/index.ts 启动和关闭时接入调度器与队列 
// 启动时
startScheduler()
startWorker()

// 优雅关闭时（在 SIGTERM/SIGINT handler 里）
await waitForWorker()
stopScheduler()

五、本课总结

  • 定时任务把"周期性维护"自动化，但直接写 setInterval 容易出现重叠执行、崩溃丢失、多实例冲突等问题
  • node-cron 能避免重叠执行，配合时区配置更适合真实业务场景
  • 后台队列把"耗时操作"从请求路径上剥离，避免用户请求阻塞或超时
  • 内存队列适合单实例学习和小规模服务，生产多实例场景需要换成 Redis 等持久化队列
  • 定时任务和队列都要接入优雅关闭流程，避免中途被 SIGTERM 打断
