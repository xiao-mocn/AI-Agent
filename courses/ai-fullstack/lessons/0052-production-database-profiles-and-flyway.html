第五十二课：生产数据库配置与 Flyway 迁移边界

预计 90–120 分钟 · 基于第 51 课的 H2 与 JPA Repository

H2 让你验证了“对象能写进表”。但生产环境不能靠应用启动时临时建表和插入数据。本课把“连接哪个数据库”与“数据库结构如何演进”分开：Profile 选择环境，Flyway 记录并执行迁移。

本课胜利点

  • 能区分开发环境的 H2 与生产 PostgreSQL 的职责。
  • 能用 application-dev.properties 与 application-prod.properties 隔离连接信息。
  • 能解释为什么生产环境使用 ddl-auto=validate，而不是 create-drop。
  • 能把建表和种子数据迁入版本化的 Flyway SQL 文件。
  • 能说清迁移文件为什么只能新增、不能改历史。

0. 先明确两条边界

问题负责者例子
本次应用连接哪一个数据库？Spring Profile + 环境变量本机 H2；线上 PostgreSQL
数据库应有哪些表和列？Flyway 迁移文件V1__create_releases.sql
Java 实体是否与已存在的表一致？Hibernate 校验ddl-auto=validate
前端类比：Profile 像 Vite 的不同 .env 文件，决定请求打到本地还是线上；Flyway 迁移则像被 Git 管理的数据库变更记录。两者都不能写进前端页面代码里。

1. 脱稿：先判断风险

不看后文，回答一句话

如果生产应用保留 spring.jpa.hibernate.ddl-auto=create-drop，重启时可能发生什么？

先记住：create-drop 适合临时学习数据库；它能在启动创建、关闭删除表。生产数据不能交给这个行为决定命运。

2. 第一步：把环境差异放进 Profile

1

拆分配置文件

修改 java-backend/src/main/resources/application.properties，并新建同目录下的两个 Profile 文件。

# application.properties：所有环境共同遵守的规则
spring.application.name=java-backend
spring.profiles.default=dev
spring.jpa.hibernate.ddl-auto=validate
spring.sql.init.mode=never

# application-dev.properties：仅本机开发使用
spring.datasource.url=jdbc:h2:mem:versiondb;DB_CLOSE_DELAY=-1
spring.datasource.username=sa
spring.datasource.password=

# application-prod.properties：值来自部署平台的环境变量
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}
为什么密码不写死？配置文件会进入 Git；环境变量由部署平台在运行时注入。这样仓库、日志和课程截图里都不会出现生产密码。

本机使用默认的 dev；模拟生产配置时执行：.mvnw.cmd spring-boot:run -Dspring-boot.run.profiles=prod。没有设置 DB_URL 时失败是安全且正确的，不要用真实密码补到文件里。

3. 第二步：让 Flyway 成为唯一建表来源

2

加入 Flyway 与 PostgreSQL 驱动

在 java-backend/pom.xml 的 <dependencies> 中加入。保持 H2，供 dev Profile 和测试使用。

<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-database-postgresql</artifactId>
</dependency>
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <scope>runtime</scope>
</dependency>
为什么需要数据库专用模块？Flyway 核心负责迁移流程；PostgreSQL 模块提供该数据库的支持。Spring Boot 在类路径发现 Flyway 后，会在应用使用数据库前执行迁移。

迁移旧的初始化 SQL

删除 data.sql，新建目录 src/main/resources/db/migration/，然后新建：

-- V1__create_releases.sql
CREATE TABLE releases (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  release_label VARCHAR(255) NOT NULL UNIQUE,
  version VARCHAR(255) NOT NULL
);

INSERT INTO releases (release_label, version) VALUES ('local', '1.0.1');
INSERT INTO releases (release_label, version) VALUES ('staging', '1.1.0-rc1');
命名规则：V1__ 是版本 1；双下划线后是人类可读说明。Flyway 默认读取 classpath:db/migration，并把已执行版本记录在自己的历史表中。

4. 第三步：验证而不是让 Hibernate 改库

3

保留实体，改变 Hibernate 的职责

不改 ReleaseEntity、ReleaseJpaRepository 或业务适配器。公共配置里的 ddl-auto=validate 会让 Hibernate 在启动时检查实体与 Flyway 创建的表是否匹配。

模式适用场景本课选择
create-drop短暂学习、一次性实验不再用于默认应用启动
update看似方便，但变更不可审计不要用于生产
validate只检查，不擅自改表与 Flyway 配合使用

运行 .mvnw.cmd clean test。预期：Flyway 建表和插入数据，JPA 查询测试与既有接口测试都通过。

5. 迁移文件是不可变的历史

4

做一个不会破坏历史的变更

假设需要增加发布时间，不要回去改 V1__create_releases.sql。新建 V2__add_released_at.sql：

ALTER TABLE releases ADD COLUMN released_at TIMESTAMP NULL;

然后才在 Java 实体中增加对应字段，并为它写测试。线上数据库已经执行过 V1；改 V1 会让已记录的校验和与 Git 中的文件不一致，部署应当失败。

胜利点：你现在可以把“代码需要的新结构”表达为一个可审查、可回放、可排序的 SQL 文件，而不是依赖某次手工连库操作。

6. 验收清单

  • 默认 dev Profile 能使用 H2，prod Profile 只从环境变量获取 PostgreSQL 连接。
  • data.sql 已被迁移文件替代，且 spring.sql.init.mode=never 防止两套初始化机制混用。
  • Flyway 的 V1__create_releases.sql 建表并插入课程数据。
  • Hibernate 使用 validate，只核对实体与表，不直接修改生产结构。
  • 新增结构通过新版本迁移文件表达，不改已执行的历史文件。
