第三十八课：配置审计与密钥轮换

目标时长 1 小时 · 难度 ★★★ · 工程化 · 凭据安全

本课你会学到：
  • 区分配置变更的审计证据与敏感配置值。
  • 设计不中断服务的密钥轮换顺序。
  • 记录轮换动作而不记录凭据。

一、审计记录的是决定，不是秘密

配置变更需要能回答谁、何时、为什么修改了哪个键，但审计记录绝不能保存 API Key、JWT 密钥或完整连接串。Git 提交、部署平台历史和发布记录共同构成证据链，帮助定位事故受哪个变更影响。

不要把旧密钥、完整哈希、截图或新密钥写进 Issue、提交信息和日志。 泄露发生后，扩大传播范围会比原始泄露更难收回。

二、轮换是一个有顺序的发布

先准备新值，再更新运行环境并验证，最后撤销旧值。JWT 密钥轮换还要决定已有令牌是立即失效，还是在有限窗口内用双密钥验证；后一种方案必须有明确截止时间。

轮换成功的标准是新密钥已生效、旧密钥已撤销、审计记录完整，而不是代码没有报错。

三、动手实践

1建立无密钥轮换记录

在发布记录中写：配置键、轮换原因、新值是否已设置、npm run check:config 结果、旧值撤销时间和验证人。不要写任何凭据值。

2演练第三方 API Key 轮换
  1. 在供应商控制台创建新 Key，只保存到部署平台密钥管理界面。
  2. 更新平台变量后运行 npm run check:config，再做一次受控业务请求。
  3. 确认新 Key 生效后撤销旧 Key，并记录撤销时间与验证结果。
不要在终端回显完整变量，也不要把新 Key 临时写入可提交文件。
3为 JWT 轮换做决策

确定可接受的会话影响：立即失效，或在受限窗口内兼容旧签名。若兼容，必须有双密钥验证、截止时间和可观测指标；窗口结束后删除旧密钥支持。

四、轮换检查清单

  1. 新凭据仅注入安全存储，未进入 Git、日志或聊天记录。
  2. 已用配置检查和最小业务请求验证新凭据。
  3. 旧凭据已撤销，或存在明确的兼容截止时间。
  4. 记录了配置键、原因、时间、验证结果和负责人。

五、本课总结

  • 审计记录变更元数据，不记录配置值。
  • 轮换先建立新值并验证，再撤销旧值。
  • JWT 轮换必须显式处理已有登录会话。
