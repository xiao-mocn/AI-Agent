第三十二课：测试数据清理与覆盖率

目标时长 1 小时 · 难度 ★★☆ · 工程化 · 测试维护

本节课你会学到：
  • 为什么 SQLite 测试库会留下 .db、-wal、-shm 文件
  • 如何让测试在服务关闭后自动删除自己的临时数据
  • 如何运行 Vitest V8 覆盖率报告并阅读行、函数与分支覆盖率
  • 如何用覆盖率发现值得补测的安全和错误处理分支

一、测试必须自己收拾现场

第 30 课为每个测试文件生成了随机的 test-UUID.db，避免不同测试互相污染。这保证了隔离性，却也会在 test/ 留下数据库文件；SQLite 启用 WAL 模式时，还可能同时出现 -wal 和 -shm 旁车文件。

不要用通配符删除整个 test 目录。 清理逻辑只能删除本次测试自己创建并记录下来的精确路径，以及对应的 -wal、-shm 文件。测试辅助文件和源代码绝不能成为清理目标。

二、覆盖率回答“跑过了吗”，不是“写过了吗”

测试通过说明现有断言成立；覆盖率报告则显示哪些代码路径真正被执行过。对于鉴权、找不到资源、数据库异常等分支，分支覆盖率比单纯的行覆盖率更有参考价值。

指标回答的问题本项目优先关注
Statements语句是否执行过？路由主流程
Functions函数是否被调用？控制器与数据库辅助函数
Branches每个条件的两侧是否都走过？鉴权失败、404 与错误处理
Lines哪些源码行仍未覆盖？报告中的具体文件和行号
覆盖率不是 KPI 游戏。不要为了数字给每一行写机械测试；优先补会影响用户隔离、权限边界和失败恢复的分支。

三、动手实践

1确认遗留文件

先运行一次测试，再查看测试目录。你应能看到随机命名的测试数据库或它的 WAL/SHM 旁车文件：

Set-Location E:\project\AI-Agent\ai-backend
npm test
Get-ChildItem .\test\test-*.db*
2让 helper 暴露精确的清理函数

在 test/helpers.ts 中保存随机生成的数据库路径，并增加 cleanupTestDB()。它只针对该路径依次尝试删除数据库主文件、-wal 和 -shm；文件不存在时不应失败。

import fs from 'fs'

let testDBPath = ''

export function useTestDB() {
  testDBPath = path.join(__dirname, `test-${randomUUID()}.db`)
  process.env.DB_PATH = testDBPath
}

export function cleanupTestDB() {
  for (const suffix of ['', '-wal', '-shm']) {
    fs.rmSync(`${testDBPath}${suffix}`, { force: true })
  }
}

保留现有的 registerAndLogin，不要把业务断言、HTTP 请求或全局删除操作混进 helper。

3在关闭服务器后清理

在 test/sessions.test.ts 引入 cleanupTestDB，并在已有的 afterAll 中先等待 server.close 完成、再调用它。这样 SQLite 不再被服务连接占用，Windows 也能稳定删除文件。

afterAll(async () => {
  await new Promise<void>((resolve, reject) => {
    server.close((error) => error ? reject(error) : resolve())
  })
  cleanupTestDB()
})

运行 npm test 后再次执行 Get-ChildItem .\test\test-*.db*，预期没有任何输出。

4生成第一份覆盖率报告

安装与当前 Vitest 版本匹配的 V8 provider，并在 package.json 增加覆盖率脚本：

npm install -D @vitest/coverage-v8

// package.json 的 scripts
"test:coverage": "vitest run --coverage"

随后运行：

npm run test:coverage

查看终端表格，重点记录 src/app.ts 与会话相关路由的分支覆盖情况。不要在未理解缺口前追求百分比阈值。

四、排查顺序

  1. 删除失败时，先确认服务已关闭，再检查清理是否在同一个 afterAll 中执行。
  2. 确认清理函数使用的是本次随机生成的精确路径，而不是目录或宽泛通配符。
  3. 覆盖率命令找不到 provider 时，确认 @vitest/coverage-v8 已写入 devDependencies 和 lock 文件。
  4. 覆盖率很低时，先读未覆盖分支的业务意义，再决定是否增加 API 测试。

五、本课总结

  • 临时测试数据需要隔离，也需要在测试结束时精确清理
  • SQLite 的 -wal 与 -shm 是数据库状态的一部分，不能只删除主文件
  • 先关闭 HTTP 服务再删除数据库，可避免 Windows 上的文件占用问题
  • 覆盖率报告用来指引风险分支的测试补强，不替代有意义的断言
