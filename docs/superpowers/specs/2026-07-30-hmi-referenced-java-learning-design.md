# 公司项目参考的 Java 学习设计

## 目标

让学习者在自有 Java Demo 中，以 Java 21 和 Spring Boot 3.5 建立现代后端能力；随后能够把这些能力映射到公司 `hmi-backend` 的 Java 8 / Spring Boot 2.7.18 多模块代码，并安全地承接低风险真实需求。

## 范围与边界

- 动手代码只写入 `E:\project\AI-Agent` 中的学习 Demo，不修改 `E:\project\hmi-backend`。
- `hmi-backend` 是架构和代码阅读样本，不是早期练习场。
- 不为匹配公司旧版本而将 Demo 降级为 Java 8 或 Spring Boot 2.7。
- Agent、MCP 和复杂 RAG 不进入 Java 基础阶段；它们只在常规后端边界已建立后引入。
- 第一轮基础学习限定为 8 周核心版或 10 周扩展版，每天投入 1-2 小时；结束后才开始正式阅读和修改真实业务代码。

## 已确认的公司项目参考

`hmi-backend` 的 `develop` 分支是 Maven 多模块工程：根项目聚合 `server`、`framework`、`module-system`、`module-infra` 与 `module-model`。当前技术基线为 Java 8、Spring Boot 2.7.18、Spring Security 5.8、MyBatis-Plus、动态数据源、Redis、任务、消息、WebSocket 和多租户能力。

站点管理链路可作为后续阅读样本：`StationController` 负责 HTTP、权限声明和租户上下文；`StationServiceImpl` 协调草稿状态、校验、事务与跨库步骤；`StationInfoMapper` 通过 MyBatis-Plus 和 `@DS` 访问模型库。它说明真实项目的难点不止 CRUD，而包括权限、数据边界和事务一致性。

## 教学架构

```text
自有 Demo（实现与试错）
  -> 现代 Java / Spring Boot 基础
  -> 常规业务闭环与自动化测试
  -> 企业能力的渐进模拟
  -> Java 中的 AI 集成

hmi-backend（只读对照）
  -> 模块边界
  -> 同类能力的生产实现
  -> Java 8 / Spring Boot 2.7 兼容差异
  -> 未来真实需求的定位入口
```

每节实践课均包含四部分：Demo 中的最小实现、对应的 `hmi-backend` 阅读入口、版本或架构差异、可重复的验收命令。课程不复制公司业务数据、配置或凭据。

## 独立构建的教学规则

用户已经完成 Node.js 课程主线，但自评仍无法脱离课程从零实现同类功能。这不是继续堆叠新框架的信号，而是需要把课程从“引导完成”改为“检索、构建、迁移”的反馈循环。

每节课固定执行以下顺序：

1. **无提示设计**：在阅读实现前，用 10-15 分钟写出接口契约、涉及文件、关键数据流和至少一个失败分支。
2. **有限提示实现**：先只给出验收条件和分层提示；用户尝试后才按阻塞点给出局部代码，不直接提供整段可复制答案。
3. **变式迁移**：完成基本需求后，立即加入一个参数、状态规则、权限规则或失败条件的变化，由用户独立修改。
4. **延迟复现**：24-72 小时后，不看上次实现，从空白文件或新接口重新构建关键切片，并解释设计取舍。

第 2、4、8 周分别进行脱稿检查。未达到“能定位文件、写出最小实现、运行验证、解释失败边界”的标准时，暂停引入下一层技术，回到对应切片做缩小练习。课程完成记录必须保留用户独立实现、命令输出和复盘结论，而不能只记录跟随步骤后的结果。

## 时间安排与项目准入

### 开始前：Node.js 脱稿诊断（一次，45-60 分钟）

在开始 Java 前，不查看既有课程或 `ai-backend` 代码，根据一个简化的聊天接口需求写出：路由契约、文件职责、请求处理伪代码、需要保存的数据、至少两个失败分支和验证步骤。该诊断不按“写出完整可运行代码”评分，而用于识别独立构建障碍是在需求拆分、后端分层、异步 API、持久化、鉴权还是测试。

诊断结果决定 Java 第一周的练习难度：概念正确但写不出语法时提供小型语法卡片；不知道文件和职责时先练 API 切片设计；能写主路径但漏掉失败边界时先练测试驱动的异常路径。诊断产物与复盘进入学习记录，作为后续脱稿检查的对比基线。

### 8 周核心版

| 周次 | Demo 学习主题 | 公司项目只读对照 | 本周可验证产物 |
| --- | --- | --- | --- |
| 1 | Java 21 基础、Maven、单元测试、异常与集合 | 根 `pom.xml` 的聚合与依赖管理 | 可编译、可测试的 Java 项目，以及无提示解释构建与测试入口 |
| 2 | Spring Boot 3.5 启动、配置、健康检查、HTTP 基础 | `server/ServerApplication.java` | 可运行的健康与就绪接口，以及首个脱稿复现 |
| 3 | Controller/Service/Mapper、VO/DO、统一响应、参数校验与异常处理 | `StationController` | 带校验和错误响应的 Demo API，以及一个变式接口 |
| 4 | MyBatis-Plus、单库 CRUD、分页与唯一性校验 | `StationInfoMapper` | 可查询、分页、创建和更新的业务实体，以及脱稿 CRUD 切片 |
| 5 | 事务、状态变化、测试替身与数据隔离 | `StationServiceImpl` 的草稿与提交流程 | 被自动化测试保护的状态变更，含失败分支 |
| 6 | 登录、认证与权限边界 | `module-system` 的认证和权限职责 | 受授权规则保护的 Demo API，以及权限规则变式 |
| 7 | 日志、配置边界、数据库迁移、Maven 构建与发布前检查 | `module-infra` 的日志职责 | 可重复的测试、构建和本地验证记录 |
| 8 | 完整复盘：从接口到数据库的调用链、影响分析和回滚判断 | 站点管理完整链路与模块边界 | 一份不改公司代码的需求影响分析，以及最终脱稿功能切片 |

### 第 9-10 周扩展版

时间允许时，加入 Redis 缓存、模块化演进，以及 Java 21 / Boot 3.5 与 Java 8 / Boot 2.7 的兼容适配阅读。动态数据源、租户隔离、跨库一致性、任务、WebSocket 与消息只做概念和公司代码定位，不在这一轮的 Demo 中完整实现。

### 进入真实业务代码的准入门槛

开始修改 `hmi-backend` 前，学习者必须能够：

- 在 Demo 中独立交付一个包含校验、权限、持久化、事务与测试的单库功能。
- 从一个公司接口定位 Controller、Service、Mapper、VO/DO、数据源、权限和配置入口。
- 写出一个真实需求的受影响模块、验证步骤、失败风险和回滚条件。
- 说明 `javax` / `jakarta`、Spring Security 5 / 6 与 Java 8 / 21 的相关边界，且不将新版依赖或 API 直接带入公司代码。

### 阶段 A：现代 Demo 基线

保留 Java 21 + Spring Boot 3.5。先完成项目启动、类型化配置、健康与就绪检查、Controller/Service/Mapper 分层、统一响应、请求校验和异常处理。

公司对照：根 `pom.xml`、`server/ServerApplication.java`、`module-model` 的 Controller 与 Service。重点识别 Maven 聚合、组件扫描和 VO/DO 分层，不引入公司模块结构。

### 阶段 B：可交付的单库业务

在 Demo 中实现一个完整但低复杂度的业务实体：创建、更新、分页、详情、删除、唯一性校验、MyBatis-Plus 持久化和单数据源事务。每个接口都有服务层测试或 Web 层测试。

公司对照：`StationController`、`StationServiceImpl`、`StationInfoMapper`。重点理解权限检查、草稿和提交状态，但 Demo 初期不模拟跨库提交。

### 阶段 C：安全与工程质量

在 Demo 中加入认证、基于角色或权限的授权、请求日志、错误边界、数据库迁移、测试数据隔离与 Maven 构建。将此前 Node.js 主线的测试和发布证据要求迁移到 Java。

公司对照：`module-system` 的认证与权限能力、`module-infra` 的访问日志和错误日志服务、`framework/spring-boot-starter-test` 的测试基类。

### 阶段 D：企业复杂度的按需引入

仅在单库业务稳定后，依次学习模块边界、Redis 缓存、租户隔离、动态数据源、跨库一致性、任务、WebSocket 和消息。每次只在 Demo 中引入一种新增复杂度，并先写出失败或边界测试。

公司对照：`module-system`、`module-infra`、`module-model` 与相应 `framework` starter。首个跨库案例需要明确补偿策略和失败处理，不能将多个本地事务误认为全局事务。

### 阶段 E：Java 中的 AI 应用

先将已有的 DeepSeek 对话、流式输出、会话存储和安全边界接入 Java Demo，再按业务需求学习 RAG、评估、工具调用与 MCP。AI 功能必须复用阶段 C 和 D 建立的认证、权限、审计、数据边界和成本观测能力。

## 版本兼容策略

- Demo 使用 `jakarta.*`、Spring Security 6 和 Java 21；公司代码中的 `javax.*`、Spring Security 5 与 Java 8 作为对照知识。
- 前两阶段的业务代码避免依赖 `record`、虚拟线程、模式匹配等 Java 21 特有能力，保证核心建模和服务逻辑易于迁移。
- 涉及校验、Servlet、Security、JPA 或依赖升级时，在课程中明确给出 Boot 3 与 Boot 2.7 的差异；不将新版代码直接复制到公司仓库。
- 进入真实需求前，单独进行一次 Java 8 / Boot 2.7 适配阅读和小改动演练。

## 初始课次调整

第 47 课继续使用 Java 21 + Spring Boot 3.5，但增加公司基线对照：公司为何仍使用 Java 8 / Boot 2.7、`javax` 与 `jakarta` 的对应关系，以及新版 Demo 不能直接作为公司模块引入的原因。

第 48 课保持运行时配置与就绪检查。后续优先顺序为：分层与统一错误处理、MyBatis-Plus 单库持久化、分页与事务、认证授权、Java 测试和 Maven 构建，然后才是 Redis、租户、多数据源与异步能力。

## 验收标准

- 学习者能从一个 Demo API 定位 Controller、Service、Mapper、VO/DO、配置和测试的位置。
- 学习者能完成并测试一个单库小功能，解释其事务、校验和授权边界。
- 学习者能从公司站点管理链路找到对应层，并说明与 Demo 的版本和企业复杂度差异。
- 在进入真实仓库修改前，学习者能写出受影响模块、验证步骤、风险点和回滚条件。
