# AI 全栈课程：eao-api 后端上岗桥接阶段设计

## 背景

用户已经完成 AI 全栈课程第 1～51 课，Node.js 主线已经覆盖从 API、数据库、测试到部署运维，Java 副线也已经进入 Spring Boot、Controller、Service、Repository 和 JPA/H2。

当前工作需求发生变化：用户将逐渐参与公司后端代码修改，但面对 `E:\project\eao-api` 时仍基本无法独立阅读代码。原课程继续深入 JPA、生产数据库和 AI 集成，不能优先解决近期工作压力，因此需要增加一个为期两周的后端上岗桥接阶段。

## 已确认约束

- 时间目标：两周内达到可以在同事或 AI 指导下完成简单后端改动。
- 每天可学习 1～2 小时，共安排 10 次核心训练。
- 当前不确定会先接触哪个业务模块，因此选择结构典型、迁移性强的品牌管理链路作为第一样本。
- 学习方式采用“真实代码导航 + 小型仿真实践”。
- `eao-api` 和 `eao-front` 只作为阅读素材，不在桥接课程中直接修改。
- 用户已完成的课程不删除、不回滚。
- 原 AI 全栈目标保留为长期目标，桥接阶段只是近期优先级调整。

## 现状分析

### 课程当前能力

用户已经接触：

- HTTP API、Controller、Service、Repository 的基本职责；
- Spring Boot 应用启动、配置和健康检查；
- 统一错误响应；
- JPA Entity、Repository 和 H2 持久化；
- 基础自动化测试。

目前的主要断层不是完全缺少概念，而是缺少把概念映射到大型现有项目的能力，包括：

- 从前端请求或需求描述定位后端入口；
- 在大量包和类中识别主调用链；
- 阅读 Java 接口、实现类、泛型、注解和依赖注入；
- 区分 VO、DO、Convert、Mapper 和 XML 的职责；
- 判断一个小需求会影响哪些文件；
- 对修改结果进行有针对性的验证。

### eao-api 的相关特征

`eao-api` 是一个 Maven 多模块 Spring Boot 项目，根项目包含：

- `app`：唯一可执行应用；
- `domains/eao-system`：用户、租户、组织、权限、字典和通知；
- `domains/eao-infra`：平台配置、文件、日志等基础设施；
- `domains/eao-model`：资产、设备、站点、拓扑、策略和告警写模型。

项目约有 820 个 Java 文件，包含大量 Controller、Service、DO 和 Mapper。数据访问主线是公司封装的 MyBatis/MyBatis-Plus 体系，而不是课程当前使用的 JPA。

品牌管理是一条适合入门的典型链路：

`eao-front BrandApi.getBrandPage`

→ `POST /model/brand/page`

→ `BrandController.getBrandPage`

→ `BrandServiceImpl.getBrandPage`

→ `BrandInfoMapper.selectPage`

→ MyBatis-Plus 查询与数据库

这条链路同时覆盖前端请求、Controller、请求/响应 VO、Service 接口与实现、MapStruct Convert、DO、Mapper 和 XML，且业务规则相对容易理解。

## 目标与验收标准

桥接阶段的短期使命是：

> 面对 eao-api 中一个普通业务需求，能够找到相关代码、说清调用链，在同事或 AI 指导下完成低风险修改，并知道如何验证。

两周后按以下五项能力验收。

### 1. 代码导航

看到一个前端 API 地址后，能够在 10 分钟内定位对应的：

`Controller → 请求/响应 VO → Service → ServiceImpl → Convert → DO → Mapper/XML`

### 2. 代码解释

能够用自己的话解释：

- 请求参数从哪里进入；
- 参数在哪里校验；
- 业务规则写在哪里；
- SQL 或查询条件在哪里；
- 数据为什么要在 VO 和 DO 之间转换；
- 最终响应从哪里返回。

### 3. 简单修改

能够在指导下完成以下三类练习：

- 增加一个请求或响应字段；
- 增加一个分页筛选条件；
- 增加一条简单业务校验及错误返回。

### 4. 安全修改

修改前检查调用方、数据结构和影响范围；修改后查看 Git diff，并执行相关测试或接口验证。不能再把“项目能启动”作为唯一完成标准。

### 5. 陌生链路迁移

离开已经反复练习的品牌模块后，能够对另一个简单模块完成入口定位、调用链梳理和改动点分析。

## 教学策略

### 真实代码与练习代码的分工

| 位置 | 用途 | 桥接阶段操作边界 |
| --- | --- | --- |
| `E:\project\eao-api` | 阅读真实后端目录、注解和调用链 | 只读 |
| `E:\project\eao-front` | 从熟悉的前端调用反查后端入口 | 只读 |
| `E:\project\AI-Agent\java-backend` | 编写简化代码、制造需求并完成修改 | 可修改 |

真实项目负责训练“认路”，课程项目负责训练“动手”。课程项目中的练习模块模仿 `eao-api` 的命名和分层，但不引入权限、多数据源、审计日志、MQ 等与当前目标无关的复杂度。

### 内容比例

- 约 40%：阅读和导航 `eao-api`、`eao-front` 的真实代码；
- 约 60%：在 `java-backend` 中复刻结构、完成变更和验证。

### 单课反馈循环

每节课均采用以下顺序：

1. 不看答案，先根据 URL、类名或业务词定位代码；
2. 写出对当前文件职责和数据流的初步判断；
3. 卡住时按“目录提示 → 类名提示 → 方法提示 → 代码解释”逐层获取帮助；
4. 在练习项目中完成一个小操作；
5. 用测试、HTTP 请求或 Git diff 验证；
6. 在 24～72 小时后进行一次短复现或需求变式。

课程完成标准由“跟随步骤运行成功”改为“能复述数据流、解释修改原因、完成验证并处理一个小变化”。

## 课程项目设计

在 `java-backend` 中新增一个简化的品牌管理纵向切片。它应具备：

- Controller；
- 保存、分页和响应对象；
- Service 接口与实现；
- 显式对象转换；
- 数据对象；
- 可替换的数据访问边界；
- H2 测试数据；
- Service 测试和 HTTP 层测试。

第一周以读取为主，只引入每节课所需的最少代码。第二周在这个纵向切片上实施字段、筛选条件和业务校验变更。

练习项目不复制公司内部 Starter，也不模拟与当前验收无关的权限、多租户、多数据源、审计日志、Redis、MQ、MQTT、TDengine 或 S3。真实代码中的这些元素统一标记为“暂时知道职责，不追踪内部实现”。

MyBatis-Plus 的公司封装类通过真实代码阅读理解；练习项目的具体持久化实现需要在实施计划阶段根据现有 Spring Boot 4 依赖兼容性确定。无论选用 MyBatis、MyBatis-Plus 或简化适配层，都必须保持 Controller、Service、Convert、DO、Mapper 的学习边界与 `eao-api` 对齐。

## 错误处理与卡点策略

学习过程中对卡点分为三类：

- **语言卡点**：不理解 Java 语法、泛型或注解时，使用 TypeScript/Vue 类比后立即回到当前调用链；
- **框架卡点**：不理解公司 Starter 或封装类时，先确定它在链路中的输入输出，不在第一轮追踪内部源码；
- **业务卡点**：不理解能源领域名词时，先记录术语和上下文，必要时查询前端页面及项目业务文档，不把业务未知误判为 Java 未学会。

如果一节课中出现三个以上全新核心概念，则拆课或把次要概念降级为“暂时识别即可”。如果用户无法完成前一课的脱稿定位，则优先补练，不继续增加框架内容。

## 验证策略

课程设计和练习代码采用分层验证：

- 导航题：根据本地文件路径核对调用链；
- 理解题：要求用户复述，不使用选择题替代；
- Service 行为：运行针对性单元测试；
- HTTP 契约：运行 Controller 测试或发送本地 HTTP 请求；
- 修改完整性：检查 Git diff 和受影响文件；
- 迁移能力：在未讲解的简单模块上进行限时定位。

由于 `eao-api` 依赖公司内部 Maven 组件，桥接阶段不以能够在课程环境完整构建该仓库为前提。真实仓库用于阅读，所有必须执行的验证在课程项目中完成。

## 暂不包含

两周桥接阶段不深入以下内容：

- JPA 进阶和数据库迁移工具；
- AI/LLM 接口开发；
- 部署、Kubernetes 和复杂运维；
- Spring Security、租户和权限框架内部实现；
- Redis、MQ、MQTT、WebSocket、TDengine、S3；
- 独立设计大型后端模块；
- 无指导处理高风险生产缺陷。

这些内容不从长期课程中删除，而是在用户具备基础代码阅读和低风险修改能力后重新排序。

## 风险与应对

### 真实项目复杂度过高

只选择一条纵向链路，第一周固定使用品牌模块；遇到公共框架只识别职责，不展开内部实现。

### 练习项目与公司项目不完全一致

每节练习都显式列出“课程简化点”和“公司真实写法”，避免把简化实现误认为生产规范。

### 两周后仍依赖指导

本阶段的目标本来就是“在指导下完成低风险修改”。结业任务重点验证定位、解释和验证能力，不虚构独立开发能力。

### 只会熟悉的品牌案例

第 62 课强制更换陌生 CRUD 模块，并限制提示层级，以检验方法迁移而非文件记忆。

## 后续方向

完成第 62 课后，根据结业表现选择后续路线：

- 定位和修改仍不稳定：增加一周不同模块的变式练习；
- 常规 CRUD 已稳定：学习事务、权限、多数据源和公司公共 Starter；
- 工作中已有明确需求：切换到真实任务陪练，先做影响分析和补丁预览，再决定是否修改公司仓库；
- 工作压力降低：回到长期 AI 全栈主线，继续数据库、AI 集成和部署内容。
