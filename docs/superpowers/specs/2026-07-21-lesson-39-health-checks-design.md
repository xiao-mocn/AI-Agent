# 第 39 课：健康检查与可观测性边界

## 目标

为现有 AI 后端的健康检查补齐自动化回归测试，锁定存活检查与就绪检查的职责边界，避免后续改动向公开探针响应中加入内部信息。

## 范围

- 保持 `GET /health` 为轻量存活检查：返回 `200` 和 `{ status: 'ok' }`，不访问数据库或第三方服务。
- 保持 `GET /ready` 为数据库就绪检查：数据库可查询时返回 `200` 和 `{ status: 'ready' }`。
- 两个端点均位于 `/api/*` 鉴权中间件之前，因此无需 JWT。
- 在现有测试服务启动后加入上述两条成功路径的精确响应断言。

## 非范围

- 不改动既有路由和 `checkDBHealth()` 的实现，因为它们已符合本课要求。
- 不为本课增加 DeepSeek API 探测、业务请求探测或公开诊断详情。
- 不在仓库中配置部署平台；部署时由人工分别配置 `/health` 和 `/ready`。

## 测试策略

在 `ai-backend/test/sessions.test.ts` 中复用已初始化的测试数据库和 HTTP 服务，新增“健康检查”测试组：

1. `GET /health` 不携带 JWT，精确断言状态码 `200` 和响应体 `{ status: 'ok' }`。
2. `GET /ready` 不携带 JWT，精确断言状态码 `200` 和响应体 `{ status: 'ready' }`。

先运行新增测试，确认当前测试基线缺少对应断言；随后不修改生产代码，重新运行测试以验证已有实现满足契约。最后执行完整 `npm test`。

## 风险与边界

本次不覆盖数据库故障时 `/ready` 的 `503` 分支，因为当前测试架构没有可控的数据库依赖替身。该分支仍由现有实现固定返回 `{ status: 'not ready' }`；未来如重构为可注入依赖，可增加独立失败路径测试。
