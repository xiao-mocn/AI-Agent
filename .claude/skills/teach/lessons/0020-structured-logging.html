第二十课：结构化日志与可观测性

目标时长 2 小时 · 难度 ⭐⭐⭐ · 后端 · 工程质量

本节课你会学到：
  • 为什么 console.log 在生产环境里几乎等于没有日志
  • pino：高性能、TypeScript 友好的结构化 JSON 日志库
  • 用 pino-http 给每个请求自动打日志（方法、路径、状态码、耗时）
  • 用 requestId 把一次请求里的所有日志串成一条线
  • 把上一课 onError 里的 console.error 升级成结构化错误日志
  • 敏感字段（密码、token）自动脱敏，避免日志本身变成泄露源

一、为什么 console.log 不够用

上一课我们在 app.onError 里写了 console.error('[未处理异常]', err)——这只是"先别让堆栈泄露给用户"的临时方案，作为生产环境的日志系统，它有几个致命问题：

  • 不可检索：日志是纯文本堆在终端或文件里，想找"过去一小时里所有 500 错误"只能肉眼翻
  • 不可分级：调试信息、警告、致命错误全部长一个样，生产环境想只看 error 级别做不到
  • 请求对不上号：并发请求下，A 请求和 B 请求的日志交错打印，出问题时分不清哪几行属于同一次请求
  • 没有结构：日志分析工具（如 ELK、Datadog、Grafana Loki）需要 JSON 这样的结构化数据才能做统计和告警，纯文本很难解析

这就是"可观测性"（Observability）要解决的问题：不用重现 bug，只看日志就能定位问题根因。

二、pino 是什么

pino 是 Node.js 生态里性能最好的日志库之一，核心特点：

  • 默认输出结构化 JSON：每条日志都是一个对象，天然适合被日志系统检索、过滤、聚合
  • 极致性能：通过异步序列化把日志开销降到最低，不会成为高并发下的瓶颈
  • 日志分级：trace/debug/info/warn/error/fatal 六个级别，生产环境只开 info 以上
  • 字段脱敏：内置 redact 选项，声明敏感字段路径就能自动打码
  • 开发体验：配合 pino-pretty，本地开发时把 JSON 转成人类可读的彩色输出
推荐阅读官方文档：pino API 文档，尤其是 redact 和 child logger 两节。

三、安装与基础用法

1安装 
cd ai-backend
npm install pino pino-http
npm install -D pino-pretty
2创建 logger 实例

新建 ai-backend/src/logger.ts，集中配置：

import pino from 'pino'

const isDev = process.env.NODE_ENV !== 'production'

export const logger = pino({
  level: process.env.LOG_LEVEL ?? (isDev ? 'debug' : 'info'),
  // 敏感字段自动脱敏，路径按 pino 的点号语法写
  redact: {
    paths: ['req.headers.authorization', '*.password', '*.token'],
    censor: '[REDACTED]',
  },
  // 开发环境用 pino-pretty 格式化，生产环境保持纯 JSON（方便日志系统采集）
  transport: isDev ? { target: 'pino-pretty', options: { colorize: true } } : undefined,
})
level 用环境变量 LOG_LEVEL 控制，本地开发默认 debug（看到所有细节），生产环境默认 info（只看关键事件），部署时不用改代码，改环境变量就行。

四、给每个请求自动打日志

1用 hono/request-id 生成 requestId

Hono 内置了请求 ID 中间件，给每个请求生成唯一 ID，方便把同一次请求的日志串起来：

// index.ts
import { requestId } from 'hono/request-id'
import { logger } from './logger'

app.use('*', requestId())

// 请求日志中间件：记录方法、路径、状态码、耗时
app.use('*', async (c, next) => {
  const start = Date.now()
  await next()
  logger.info({
    requestId: c.var.requestId,
    method: c.req.method,
    path: c.req.path,
    status: c.res.status,
    durationMs: Date.now() - start,
  }, '请求完成')
})
把这个中间件放在最前面（secureHeaders 之前或之后都行，但要在业务路由之前），这样无论请求最终成功还是被限流、鉴权拦截，都会留下一条日志。

五、把 onError 升级成结构化错误日志

上一课的 app.onError 只有 console.error，现在换成 pino，并带上 requestId 方便和请求日志对应：

// index.ts
app.onError((err, c) => {
  logger.error({
    requestId: c.var.requestId,
    err: { message: err.message, stack: err.stack },
    path: c.req.path,
  }, '未处理异常')
  return c.json({ error: '服务器内部错误，请稍后重试' }, 500)
})
为什么这样更好：
  • err.stack 只写进服务器日志，从来不会到达 c.json 返回给客户端——延续了第十九课"5xx 不暴露内部信息"的原则
  • requestId 让你能拿着用户报告的一次失败请求，在日志系统里精确搜出对应的错误堆栈
  • 结构化字段（path、err.message）可以直接用来做告警规则，比如"某个 path 的 500 次数超过阈值就报警"

六、敏感信息脱敏的边界

redact 只能屏蔽你显式声明的字段路径，无法自动识别"这个字符串看起来像密码"。所以：

  • 打印请求体前，永远检查里面有没有 password、token、Authorization 这类字段
  • 不要在日志里直接 logger.info(body) 打印整个未经筛选的请求体——写清楚要打印哪些字段
  • JWT token 即使脱敏了字段名，也要注意别把 token 整串拼进其他字段（比如拼进一条纯文本消息里）

七、日志级别怎么用

级别什么时候用
debug开发调试用的细节信息，生产环境通常关闭
info正常业务事件：请求完成、用户登录成功、任务执行完毕
warn不影响当前请求，但需要关注的异常情况：限流触发、token 即将过期
error请求失败、未捕获异常——需要有人去看
fatal进程即将崩溃退出前的最后记录

八、本课总结

  • console.log 只是"输出"，不是"可观测性"——生产环境需要结构化、可检索、可分级的日志
  • pino 提供高性能的 JSON 日志，配合 pino-pretty 兼顾开发体验
  • 用 hono/request-id 生成 requestId，串联同一次请求的所有日志
  • 请求日志 + 错误日志双管齐下：正常请求记 info，异常记 error 并带上 requestId
  • redact 只能防你想到的字段，打印请求体前始终要过一遍脑子
