第十九课：输入验证与错误处理规范

目标时长 2 小时 · 难度 ⭐⭐⭐ · 后端 · 工程质量

本节课你会学到：
  • 为什么后端必须独立做输入验证，不能依赖前端
  • Zod：TypeScript-first 的 Schema 验证库，一次声明同时获得类型 + 运行时校验
  • 用 safeParse 安全解析请求体，返回有意义的错误信息
  • 统一错误响应格式，区分客户端错误（4xx）和服务器错误（5xx）
  • 给 /login、/register、/api/chat 接口加上 Zod 校验

一、为什么后端必须独立做输入验证

没有后端验证时会发生什么？
  • 用户名传空字符串 "" → 数据库里存了一个空用户名，后续查询逻辑全乱
  • 密码传 null → bcrypt 比较 null 和哈希，可能抛异常，500 错误泄露堆栈信息
  • message 传 10 万字的字符串 → DeepSeek API 返回 400 或账单飙升
  • sessionId 传 "haha" → SQL 查询拿到 NaN，数据库查出意外结果

关键原则：前端校验是用户体验层，后端校验是安全层。任何人都能绕过前端直接发 HTTP 请求，后端必须假设所有输入都是不可信的。

二、Zod 是什么

Zod 是 TypeScript 生态最流行的 Schema 验证库。它的核心优势：

  • 一次声明，双重收益：写一个 Schema，既能运行时校验，又能自动推导出 TypeScript 类型，无需手写 interface
  • 链式 API：z.string().min(3).max(30).regex(...)，读起来就是规则说明
  • 类型安全的解析结果：safeParse 返回 { success: true, data: T } 或 { success: false, error }，强制你处理错误
  • 丰富的错误信息：每条错误规则都能自定义中文提示

三、Zod 基础用法

1安装 
cd ai-backend
npm install zod
2定义 Schema 并推导类型 
import { z } from 'zod'

// 定义 Schema
const LoginSchema = z.object({
  username: z.string().min(1, '用户名不能为空'),
  password: z.string().min(6, '密码至少 6 位'),
})

// 自动推导 TypeScript 类型，无需手写 interface
type LoginInput = z.infer<typeof LoginSchema>
// 等价于：{ username: string; password: string }
3safeParse vs parse
方法成功失败适用场景
parse(data)返回解析后的数据抛出异常失败必须中断的场景
safeParse(data){ success: true, data }{ success: false, error }HTTP 接口——失败应该返回 400，不是 500
const result = LoginSchema.safeParse(body)

if (!result.success) {
  // result.error.issues 是错误列表，取第一条给用户看
  return c.json({ error: result.error.issues[0].message }, 400)
}

// result.data 是类型安全的，TypeScript 知道它的形状
const { username, password } = result.data

四、常用 Zod 规则速查

规则作用
z.string()必须是字符串
.min(n, '提示')最少 n 个字符
.max(n, '提示')最多 n 个字符
.regex(/pattern/, '提示')匹配正则
.trim()去掉首尾空格后再校验
z.number().int().positive()正整数
z.enum(['a', 'b'])枚举值
.optional()字段可选
.default(value)缺省时用默认值

五、实践：给现有接口加 Zod 校验

1新建 Schema 文件

集中管理所有 Schema，放在 ai-backend/src/schemas.ts：

import { z } from 'zod'

export const RegisterSchema = z.object({
  username: z
    .string()
    .trim()
    .min(3, '用户名至少 3 位')
    .max(30, '用户名最多 30 位')
    .regex(/^[a-zA-Z0-9_]+$/, '用户名只能包含字母、数字和下划线'),
  password: z
    .string()
    .min(6, '密码至少 6 位')
    .max(72, '密码最多 72 位'),   // bcrypt 只处理前 72 字节
})

export const LoginSchema = z.object({
  username: z.string().min(1, '请输入用户名'),
  password: z.string().min(1, '请输入密码'),
})

export const ChatSchema = z.object({
  message: z
    .string()
    .min(1, '消息不能为空')
    .max(4000, '消息最多 4000 字'),
  sessionId: z.number().int().positive('sessionId 必须是正整数'),
})
2修改 user.ts——注册和登录接口 
import { RegisterSchema, LoginSchema } from '../schemas'

// 注册
app.post('/register', async (c) => {
  const body = await c.req.json()
  const result = RegisterSchema.safeParse(body)
  if (!result.success) {
    return c.json({ error: result.error.issues[0].message }, 400)
  }
  const { username, password } = result.data
  // ... 原有的 bcrypt + createUser 逻辑不变
})

// 登录
app.post('/login', async (c) => {
  const body = await c.req.json()
  const result = LoginSchema.safeParse(body)
  if (!result.success) {
    return c.json({ error: result.error.issues[0].message }, 400)
  }
  const { username, password } = result.data
  // ... 原有的 findUser + bcrypt.compare 逻辑不变
})
3修改 chat.ts——聊天接口 
import { ChatSchema } from '../schemas'

app.post('/api/chat', async (c) => {

六、统一错误响应格式

目前我们的错误响应格式不统一——有时是 { error: '...' }，有时是其他结构。建立一个约定：

统一格式（在整个项目中坚持）： 
// 所有错误响应统一用这个结构
{ "error": "对用户友好的错误描述" }

// 4xx：客户端传了错误的东西，错误信息可以暴露给用户
c.json({ error: '用户名至少 3 位' }, 400)

// 5xx：服务器内部错误，绝对不暴露堆栈或内部信息
c.json({ error: '服务器内部错误，请稍后重试' }, 500)
绝对不要这样做： 
// 把异常堆栈或数据库错误暴露给客户端
} catch (e) {
  return c.json({ error: e.message }, 500)  // ❌ 可能泄露内部信息
}
正确做法：捕获异常后记录日志（下一课学习），返回通用错误消息给用户。

七、Hono 全局错误处理

除了每个路由单独处理错误，还可以在 index.ts 注册全局错误处理器，作为最后一道防线：

1注册全局 onError 
// index.ts — 放在所有路由注册之后
app.onError((err, c) => {
  console.error('[未处理异常]', err)
  return c.json({ error: '服务器内部错误，请稍后重试' }, 500)
})
这会捕获所有路由里没有被 try/catch 处理的异常，防止 Hono 默认的 500 响应暴露堆栈信息。
2注册 404 处理 
app.notFound((c) => {
  return c.json({ error: '接口不存在' }, 404)
})

八、JSON 解析失败的边界情况

如果客户端发来的不是合法 JSON（如空 body），c.req.json() 会抛异常。需要在 Zod 校验之前保护：

let body: unknown
try {
  body = await c.req.json()
} catch {
  return c.json({ error: '请求体必须是合法的 JSON' }, 400)
}

const result = LoginSchema.safeParse(body)
注意 body 声明为 unknown 类型——这是刻意的。unknown 强制你在使用前先做类型收窄（通过 Zod 的 safeParse），TypeScript 不允许你直接访问 unknown 类型的属性。

九、本课总结

  • 后端必须独立做输入验证，不信任任何外部输入，前端校验只是体验层
  • Zod 的 z.object().safeParse() 是 HTTP 接口里的最佳实践——失败返回 400，不抛异常
  • Schema 集中管理，类型自动推导（z.infer<typeof Schema>）
  • 错误响应统一格式：{ error: string }；5xx 不暴露内部信息
  • 用 app.onError 和 app.notFound 兜底未处理的异常和路由缺失
