一、为什么 AI 接口必须限流

不加限流会发生什么？
  1. 恶意用户写个脚本，每秒发 100 条消息 → DeepSeek API 费用爆炸，账单全由你承担
  2. 某个 bug 导致前端无限重试 → 服务器被自己的代码打垮
  3. 爬虫批量抓取对话 → 数据泄露、资源耗尽
  4. 一个用户占满所有并发 → 其他用户无法使用

速率限制（Rate Limiting）就是控制单个来源在单位时间内能发多少请求，超出就返回 429 Too Many Requests。

二、两种核心算法

固定窗口（Fixed Window）

每个时间窗口（如每分钟）内最多允许 N 次请求。实现最简单，但有"边界突刺"问题：窗口切换瞬间可能涌入 2N 次请求。

滑动窗口（Sliding Window）

时间窗口随当前时刻滑动，更精确，没有边界突刺。hono-rate-limiter 默认用固定窗口，对我们的场景已经足够。

算法优点缺点
固定窗口实现简单、内存低边界突刺
滑动窗口更平滑、精确内存稍高
令牌桶允许短时突发，长期平均实现复杂

三、安装与基础配置

1安装依赖 
cd ai-backend
npm install hono-rate-limiter
2在 index.ts 中引入 
import { rateLimiter } from 'hono-rate-limiter'
3最简单的用法——全局限流 
// 所有 /api/* 接口：每个 IP 每分钟最多 60 次请求
app.use('/api/*', rateLimiter({
  windowMs: 60 * 1000,   // 时间窗口：1 分钟
  limit: 60,              // 最多 60 次
  keyGenerator: (c) => c.req.header('x-forwarded-for') ?? 'unknown',
  standardHeaders: 'draft-6',  // 返回 RateLimit-* 响应头
}))
keyGenerator 决定"按什么维度计数"。这里用 IP 地址——同一 IP 共享配额。

四、对 AI 聊天接口精细限流

AI 调用比普通接口贵得多，应该单独设更严格的限制。

1按用户 ID 限流（已登录用户）

用 IP 限流有个问题：多人共用同一网络（公司、学校）会共享配额。对已登录用户，应该按 JWT 里的用户 ID 来计数：

import jwt from 'jsonwebtoken'

const chatLimiter = rateLimiter({
  windowMs: 60 * 1000,   // 1 分钟
  limit: 10,             // AI 接口每分钟最多 10 次
  keyGenerator: (c) => {
    const authHeader = c.req.header('Authorization')
    if (authHeader?.startsWith('Bearer ')) {
      try {
        const payload = jwt.verify(
          authHeader.slice(7),
          process.env.JWT_SECRET ?? 'dev-secret'
        ) as { userId: number }
        return `user:${payload.userId}`
      } catch {
        // token 无效，退回 IP
      }
    }
    return c.req.header('x-forwarded-for') ?? 'unknown'
  },
  standardHeaders: 'draft-6',
})
2只把 chatLimiter 挂到 AI 路由上

在 ai-backend/src/business/chat.ts 里，或者在 index.ts 里精确匹配路由：

// 只对聊天接口限流，其他接口不影响
app.use('/api/chat/*', chatLimiter)
中间件注册顺序很重要：limiter 要在 JWT 验证之后，否则未登录请求都走 IP 计数。但如果你想在鉴权前就拦截恶意 IP，也可以放在前面——看业务需求。

五、前端处理 429 响应

被限流时后端返回 HTTP 429，前端需要优雅提示，而不是让用户看到一个报错。

1在 fetch 封装里统一处理

找到前端发送聊天请求的地方（通常是 useChat.ts 或 API 封装），加上 429 判断：

const res = await fetch('/api/chat/send', { ... })

if (res.status === 429) {
  // 从响应头读出还需等多少秒
  const retryAfter = res.headers.get('Retry-After')
  const seconds = retryAfter ? parseInt(retryAfter) : 60
  throw new Error(`请求太频繁，请 ${seconds} 秒后再试`)
}

if (!res.ok) {
  const data = await res.json()
  throw new Error(data.error ?? '请求失败')
}
2在 UI 上显示友好提示 
<!-- 在聊天界面加上限流提示 -->
<div v-if="rateLimitError" class="rate-limit-tip">
  ⏳ {{ rateLimitError }}
</div>
const rateLimitError = ref<string | null>(null)

try {
  rateLimitError.value = null
  await sendMessage(input.value)
} catch (e) {
  if (e instanceof Error && e.message.includes('请求太频繁')) {
    rateLimitError.value = e.message
  }
}

六、429 响应头说明

standardHeaders: 'draft-6' 会自动在响应里加上标准限流头：

响应头含义
RateLimit-Limit当前窗口允许的最大次数
RateLimit-Remaining当前窗口剩余次数
RateLimit-Reset窗口重置的时间戳
Retry-After被限流后需要等待的秒数（429 时才有）

七、内存存储 vs Redis（生产考量）

hono-rate-limiter 默认把计数存在内存里，有两个局限：

  • 服务重启后计数清零
  • 多实例（水平扩展）时各自独立计数，限流形同虚设
单实例部署（Render 免费套餐）：内存存储完全够用
多实例 / 高可用：需要换成 Redis 存储（@hono-rate-limiter/redis）
目前我们在 Render 单实例部署，内存存储没问题。等业务增长需要多实例时再迁移 Redis——这是典型的"够用就好，不过早优化"原则。

八、本课实践：给项目加上限流

1安装依赖 
cd ai-backend
npm install hono-rate-limiter
2修改 ai-backend/src/index.ts

在 JWT 验证中间件之前加全局 IP 限流，AI 路由再加一层用户级精细限流：

import { rateLimiter } from 'hono-rate-limiter'

// 全局限流：每 IP 每分钟 60 次（在 JWT 验证之前注册）
app.use('/api/*', rateLimiter({
  windowMs: 60 * 1000,
  limit: 60,
  keyGenerator: (c) => c.req.header('x-forwarded-for') ?? 'unknown',
  standardHeaders: 'draft-6',
}))

// AI 接口精细限流：按用户 ID，每分钟 10 次
app.use('/api/chat/*', rateLimiter({
  windowMs: 60 * 1000,
  limit: 10,
  keyGenerator: (c) => {
    const auth = c.req.header('Authorization')
    if (auth?.startsWith('Bearer ')) {
      try {
        const payload = jwt.verify(auth.slice(7), JWT_SECRET) as { userId: number }
        return `user:${payload.userId}`
      } catch {}
    }
    return c.req.header('x-forwarded-for') ?? 'unknown'
  },
  standardHeaders: 'draft-6',
}))
3验证限流生效

用 curl 快速发 11 次请求，第 11 次应该拿到 429：

# 先登录拿 token（替换为你的账号）
TOKEN=$(curl -s -X POST http://localhost:3000/api/user/login \
  -H "Content-Type: application/json" \
  -d '{"username":"test","password":"123456"}' | jq -r .token)

# 循环发 12 次聊天请求
for i in $(seq 1 12); do
  STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
    -X POST http://localhost:3000/api/chat/send \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"message":"test","sessionId":1}')
  echo "请求 $i: $STATUS"
done

期望输出：前 10 次返回 200，第 11 次起返回 429。

十、本课总结

  • AI 接口必须限流，否则面临费用爆炸和服务被打垮的风险
  • hono-rate-limiter 一行代码加限流，keyGenerator 控制按什么维度计数
  • 全局按 IP 限流 + AI 接口按用户 ID 精细限流，两层防护
  • 前端统一处理 429，展示友好的"请稍后再试"提示
  • 单实例用内存存储，多实例扩展时再换 Redis
